# M5 성능 확인 — M5-22 둘째 측정(묶음 7 뒤, M5 끝)

이 문서는 잰 시점의 기록이다. 측정 방법은 `CONTRIBUTING.md` 「성능 기준선」 과 그 「M5 기록 항목」, 목표는 `docs/design/06-roadmap.md` 「성능 목표 (검증 기준)」, 완료 기준은 `docs/design/16-m5-plan.md` 의 M5-22 행(결정 M5-D19 — 가볍게)이 정본이다. 비교 대상은 M4 기준선 [`2026-11-10-m4-perf-report.md`](2026-11-10-m4-perf-report.md) §0 · §3 ①②(빈 프로젝트, 2026-11-11 재측정)와 첫 측정 [`2026-11-17-m5-perf-report.md`](2026-11-17-m5-perf-report.md)이다.

**상태: 목표 안. 넘는 항목이 없어 대응 행을 제안하지 않는다.** 콜드 스타트는 467 ms(M4 482 ms 대비 −15 ms, 첫 측정 442 ms 대비 +25 ms), 유휴 메모리는 234.9 MB(M4 226.7 MB 대비 +8.2 MB, 첫 측정 231.5 MB 대비 +3.4 MB)다. OS 는 첫 측정과 같은 **27.2.1 (26B131)** 이고, M4 기준선(27.2 26B123)과는 다르다. 그래서 M4 대비 증감을 코드 차이로만 읽지 않는다(§1).

**측정 방법이 이제 저장소에 있다.** 첫 측정이 커밋하지 않은 드라이버로 잰 기록 항목 둘은 이번에 `pw-perf-m5`(`crates/pw-perf/src/bin/pw-perf-m5.rs`)와 `scripts/perf-m5.mjs`(`mise run perf-m5`)로 쟀다. 판정 항목도 같은 스크립트가 `pw-perf` 로 잰다. 기록 항목은 `pw-perf` 의 판정 시나리오로 두지 않았다(결정 M5-D19). 방법은 첫 측정 드라이버와 같지만 MCP 세션 메모리는 첫 측정이 넘긴 대로 **붙은 뒤 40초 이후 표본**을 대조 회와 견준다(§3 ②).

읽는 법:

- **첫 측정 대비 증감은 잡음 크기다.** 콜드 스타트 +25 ms 중 8 ms 는 앱이 `main` 에 들어오기 전 몫이다. 이 몫은 앱 코드가 아니라 띄우기 · 떼어 띄우기 쪽이다. MCP 단계의 회 11개(같은 번들, 같은 띄우기)에서는 콜드 스타트가 437 – 465 ms(중앙값 449 ms)였다. 시작 load 가 첫 측정보다 조금 높았다(4.45 대 4.21). 유휴 메모리 +3.4 MB 는 `pitwall` 프로세스 약 +1.5 MB(회 1 – 5 중앙값 59.3 → 61.0)에 GPU 의 두 값(20.7 · 24.8 MB, 회마다 둘 중 하나가 나온다) 중 어느 쪽이 중앙값 회에 걸렸는가가 더해진 것이다. WebContent 의 보통 값은 첫 측정과 같은 범위다.
- **M4 대비**는 콜드 스타트 −15 ms, 유휴 메모리 +8.2 MB 다. 메모리 몫은 `pitwall` 약 +2.5 MB, WebContent 약 +3 MB 다. M5 가 앱에 더한 것(MCP 소켓 수신 · 세션 등록부 · 감사 로그 · 승인 허브 · 상태바 항목 · 「에이전트 활동」 툴 윈도우 · 묶음 7 의 툴)은 세션이 없을 때 빈 프로젝트 화면에 그려지지 않는다. 결정 M5-D14 의 「세션이 없을 때 상주 비용을 더하지 않는다」 와 맞는 크기다. OS 가 달라 이 증감을 코드 차이의 근거로 쓰지는 않는다.
- **WebContent 의 튐(164 MB)이 이번에는 5회 중 2회**다(첫 측정 1회). 중앙값 판정이라 판정은 그대로다. 같은 튐이 MCP 단계의 표본 0(첫 프레임 10초 뒤)에서도 11회 중 3회 있었고(162.7 – 176.3 MB), 모두 그다음 10초 안에 118 – 133 MB 로 내려왔다. 첫 측정 §3 ② 「10초 표본은 가라앉기 전이다」 와 같은 까닭으로 본다. 다음 측정에서 튐이 중앙값을 넘을 만큼(5회 중 3회) 잦아지면 06 의 표본 시점(10초)을 다시 볼 거리다. 지금은 판정 방법을 M4 와 같게 둔다.

## 3. 기록만 하는 것 — CLI 벽시계 · MCP 세션 메모리

드라이버 `pw-perf-m5` 가 `pw-perf` 의 회 준비를 라이브러리로 그대로 쓴다: 임시 `PITWALL_*_DIR` 넷, 미신뢰로 등록한 빈 프로젝트, 책임 프로세스를 끊은 띄우기, `first_frame` 표시, 책임 pid 묶음의 `phys_footprint` 합, pid 로 끄기와 그 회의 웹뷰 저장소 지우기. 물려받은 `PITWALL_*` 변수는 지운다. 첫 측정의 스크래치 드라이버와 같은 방법이다. 다른 점은 회마다 실패 조건(출력 · 로그 확인)을 더 엄격하게 본다는 것과, MCP 표본을 60초까지 한 단계로 묶었다는 것이다.

- **남는 증가분은 잡음 안이다.** 회 값의 범위가 세션 202.2 – 207.2, 대조 203.7 – 210.4 MB 로 겹친다. 중앙값의 차 +1.6 MB 는 대조 회끼리의 폭(6.7 MB)보다 작다. 첫 측정의 +0.6 MB 와 같은 결론이다. `pitwall` 프로세스는 세션이 붙어도 늘지 않는다. 한 회 안의 처음 → 끝이 세션 회 −0.7 – 0.0 MB, 대조 회 −0.9 – −0.2 MB 다. 세션 하나의 상주 비용은 **별도 프로세스인 `pitwall mcp` 프록시의 6.2 MB** 가 전부라는 첫 측정의 결론이 그대로다.
- **붙은 뒤 10초의 +18 MB 는 WebKit 의 가라앉음이 늦어진 것이다**(첫 측정 +35 MB 와 같은 현상이다. 크기가 다른 것은 대조 회의 10초 값이 이번에 조금 높았기 때문이다). 대조 회는 첫 프레임 10 – 20 초 사이에 WebContent 가 약 17 MB(136 → 119), GPU 가 약 6 – 8 MB(20.7 · 24.7 → 14.4 · 16.3) 줄어든다. 세션 회는 세션이 붙는 순간 상태바에 「MCP 1」 이 새로 그려져 그 10초 동안 WebContent 가 그대로 남고(133 – 161 MB) GPU 도 덜 줄며(18.4 – 20.5), 그 뒤 10초 안에 대조와 같은 값으로 내려온다. **회 7 은 가라앉음이 10초 더 늦어**(붙은 뒤 20초 232.2 MB, WebContent 145.5) 30초에야 내려왔다. 그래서 40초 이후로 견주는 것이 맞다. 10 – 20초 표본으로 견주었다면 이 회가 세션의 비용으로 읽혔을 것이다.
- **표본 0 의 튐**(262.5 · 256.0 · 274.5 MB 등)은 세션을 붙이기 전이라 세션과 무관하다. §2 의 「WebContent 의 튐」 과 같은 것이다.

## 5. 목표를 넘는 항목 · 대응 행

없다. 두 판정 항목이 목표 안이고, M4 기준선 대비 증가분은 콜드 스타트 −15 ms · 유휴 메모리 +8.2 MB 다. 기록 항목도 대응 행을 부르지 않는다. CLI 벽시계는 첫 측정과 같고, MCP 세션은 앱 쪽에 남는 증가분이 없다(§3 ②).

다음 성능 확인 행에 넘기는 것:

- `mise run perf-m5` 를 그대로 다시 쓰면 같은 방법이다. M5 다음 마일스톤의 확인 행이 같은 넷을 잰다면 스크립트 이름의 `m5` 는 「M5 에서 정한 방법」 으로 읽는다. 표본 시점 · 회 수는 스크립트 머리의 상수(`CLI_CALLS` · `MCP_PAIRS` · `MCP_FROM_SECS`)다.
- 유휴 메모리 10초 표본의 WebContent 튐이 이번에 5회 중 2회였다(§2). 3회가 되면 중앙값이 튐을 잡는다. 그때는 표본 시점을 06 · M4 와 견줄 수 있게 바꿀지 메인이 정한다.

## 6. 지침 · 브리프 · 계획에 비었던 곳

- **보고서 자리가 둘이다**(첫 측정 §6 과 같다). 브리프는 이 문서를, 공통 계약은 `.superpowers/handoff/<행>-report.md` 를 말한다. 이번에도 이 문서를 정본으로 하고, 핸드오프 쪽에는 계약의 항목을 이 문서를 가리키며 짧게 적었다. 계약 「보고」 에 「측정 행은 산출물 보고서를 정본으로 하고 핸드오프 보고서는 그것을 가리킨다」 한 줄을 넣자는 제안이 아직 반영되지 않았다.
- **「`scripts/` 에 넣는다」 와 Rust 드라이버.** 드라이버는 책임 프로세스를 끊은 띄우기 · `phys_footprint` · 책임 pid 를 써야 하는데, 이것들은 `pw-perf` 의 Rust 함수다(Node 로는 할 수 없다). 그래서 드라이버는 `pw-perf` 크레이트의 둘째 실행 파일(`src/bin/pw-perf-m5.rs`, 앞서 있던 `pw-perf-lsp` 와 같은 자리)로 두고, `scripts/perf-m5.mjs` 가 차례 · 대기 · 복사를 맡게 했다(perf-m2 · m3 · m4 와 같은 꼴). `pw-perf` 의 시나리오나 플래그로는 넣지 않았다. 브리프의 「scripts/ 에」 를 이렇게 나눠 읽었다.
- **측정 기준 load.** perf-m4 의 기다림은 「1분 load ≤ 코어 수(15)」 다. 첫 측정은 사람이 4.2 까지 기다렸다. 이번에는 스크립트에 `--max-load` 를 두어 4.5 를 주었다. 같은 기기에서 견줄 측정이면 시작 load 를 비슷하게 맞추는 편이 낫다. CONTRIBUTING.md 「M5 기록 항목」 에 이 옵션을 적었다.
