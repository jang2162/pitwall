# M6 성능 확인 — M6-22 (M6 계획 작업 전부 병합 뒤)

이 문서는 잰 시점의 기록이다. 측정 방법은 `CONTRIBUTING.md` 「성능 기준선」 과 그 「M6 측정」, 완료 기준은 `docs/design/17-m6-plan.md` 의 M6-22 행이 정본이다. 비교 대상은 M5 끝 측정 [`2026-11-17-m5-perf-report-2.md`](2026-11-17-m5-perf-report-2.md) 다.

## 남은 측정 — 기기를 비워 줄 때 돌릴 것

이번에는 **기준선 조건이 아니어서**(§1) 콜드 스타트 · 유휴 메모리 · 콘솔 프레임을 판정하지 않았다(메인 판정 2026-11-19, 「B」). 같은 하네스로 다시 잰다:

- **조건**: 내장 화면 하나(외부 모니터를 뺀다 — M5 기준선과 같다), 사람 입력 없음(깨어 있기 앱의 HID tickle 도 끈다), 1분 load ≤ 4.5, 다른 빌드 · IntelliJ 색인 같은 무거운 프로세스 없음, 깨끗한 커밋.
- **명령**: `mise run perf-m6 -- --max-load 4.5` — 번들을 짓고 디버그 어댑터가 없으면 받고, 단계마다 화면 잠금 · 화면 구성 · load 를 보고 맞을 때까지 기다린 뒤 `empty` → `idle-procs` → `idle-procs-trusted` → `run-flood` → `debug-end` 를 돌고 결과를 이 폴더로 복사한다. 앱 창은 회마다 앞에 뜨고 키 · 마우스 입력은 보내지 않는다.
- **시간**: 번들 빌드(증분 몇 분 · 처음이면 15분 남짓) + 측정 약 20분(이번 실행 16:30 – 16:47).
- 판정할 것: 콜드 스타트 · 유휴 메모리를 M5 끝 표와(아래 §2), 콘솔 프레임을 `withinVsync` ≥ 0.95 · `vsyncMs` ≤ 17 로(아래 §4).

## 2. ① 콜드 스타트 · 유휴 메모리(`pw-perf`, 기록만)

[`…-m6-perf-empty-163042.json`](2026-11-19-m6-perf-empty-163042.json) · [`.summary.md`](2026-11-19-m6-perf-empty-163042.summary.md). 첫 시도는 유효 1회뿐이라(4회 가려짐) 같은 명령을 다시 돈 둘째 시도의 것이다(유효 3, 제외 2).

| 항목 | 이번(외부 화면 둘, 판정 안 함) | M5 끝(내장 화면 하나) |
| --- | --- | --- |
| 콜드 스타트 | 528 ms (526 – 580) | 467 ms (458 – 471) |
| 유휴 메모리 footprint | 230.4 MB (228.5 – 273.6) | 234.9 MB (230.7 – 263.4) |
| 프로세스별 | WebContent 128.5 – 175.4, `pitwall` 67.5 – 69.2, GPU 18.1 – 18.2 | WebContent 136.4 – 164.9, `pitwall` 59.0 – 61.1, GPU 20.7 – 24.9 |
| 띄움 → `main` | 109 ms | 106 ms |

읽는 법: 외부 1x 화면에서는 WebKit(GPU · WebContent)이 작게 나와 메모리가 낮게 읽힌다(CONTRIBUTING 「화면 구성」). 그래서 합계가 M5 와 비슷해도 견주지 않는다. **`pitwall`(앱 + Host) 몫은 화면과 무관한데 59 – 61 → 67.5 – 69.2 MB 로 약 +8 MB** 다 — M6 의 실행 관리자 · 디버그 · 툴 34개가 든 몫으로 보이며, 기준선 조건에서 다시 볼 것. 콜드 스타트 +61 ms 는 load(8.7)와 사람 입력이 있던 때라 읽지 않는다.

## 3. ① 빈 프로젝트에서 아무것도 띄우지 않는가(`idle-procs`)

[`…-idle-procs-163042`](2026-11-19-m6-perf-idle-procs-163042.summary.md)(미신뢰) · [`…-idle-procs-trusted-163042`](2026-11-19-m6-perf-idle-procs-trusted-163042.summary.md)(신뢰, 실행 구성 없음). 첫 프레임 10초 뒤부터 30초, 1초마다. 가려짐은 메모리만 제외하고 프로세스 · 스레드 · 깨어남은 모든 회로 본다(가려짐이 바꾸지 않는다).

| | 미신뢰 3회 | 신뢰 3회 |
| --- | --- | --- |
| 앱의 자손 프로세스 | **0** | **0** |
| `run-ports` 스레드 | **없음** | **없음** |
| `pitwall` 스레드 수 | 28 (25 – 29) | 26 (26 – 30) |
| 유휴 깨어남 /s | 0.20 (0.07 – 0.20) | 0.17 (0.03 – 0.17) |
| 인터럽트 깨어남 /s | 6.03 (5.49 – 8.56) | 7.49 (6.19 – 9.56) |
| CPU ms/s | 0.46 (0.42 – 0.95) | 1.18 (0.58 – 1.44) |

스레드 이름(끝 시점): `tokio-rt-worker` × 16 – 17, `notify-rs fsevents loop` × 2, `pw-fs-watch`, `pw-index-events`, `main`, `com.apple.NSEventThread`, WebKit 의 셋, 이름 없는 4. 실행 · 디버그에 딸린 이름(`run-ports`, `login-shell-env` 등)이 없다.

**구분력**: 같은 번들 · 같은 프로젝트에서 실행이 도는 동안은 `run-ports` 가 매 표본 보였고(`run-flood` 6회 모두 `ports_thread_during_run` true) 실행이 끝나자 사라졌다(6회 모두 `ports_thread_at_end` false). 이 지표가 포트 폴링을 본다는 것과 폴링이 실행과 함께 멈춘다는 것이 함께 확인된다.

M5 에는 스레드 · 깨어남 기록이 없어 그 둘은 이번이 첫 값이다(견줄 것 없음). 신뢰 프로젝트는 열 때 런타임 환경을 읽는 로그인 셸(`zsh`)이 0.1 – 0.2초 뜬다 — M5 부터의 동작이고(`pw-runtime`), 재는 창(첫 프레임 10초 뒤) 밖이다. ③ 측정에서 그 셸이 보였다(§5).

## 4. ② 초당 10 MB 실행(`run-flood`)

본 측정 [`…-run-flood-163042`](2026-11-19-m6-perf-run-flood-163042.summary.md)(3회 모두 가려짐), 보조 [`…-run-flood-161243`](2026-11-19-m6-perf-run-flood-161243.summary.md)(1회 유효). `pw-perf-flood` 가 6회 모두 30초에 300,000,000 바이트를 썼다(3,000 틱 중 늦은 틱 0 – 4 — PTY 쓰기가 거의 막히지 않았다).

**Host 메모리(목표 안).** `pitwall` footprint 의 「실행 직전 → 최댓값」:

| 회 | 직전 | 최댓값 | 차 | 끝난 뒤 15초 |
| --- | --- | --- | --- | --- |
| 161243-0 | 53.5 | 102.3 | **48.8** | 84.6 |
| 161243-1 | 54.3 | 84.9 | 30.6 | 57.9 |
| 161243-2 | 54.6 | 82.8 | 28.2 | 61.1 |
| 163042-0 | 59.6 | 84.2 | 24.6 | 57.7 |
| 163042-1 | 58.8 | 87.7 | 28.9 | 63.0 |
| 163042-2 | 57.6 | 79.9 | 22.4 | 58.6 |

모두 Host 전체 상한 64 MiB(67.1 MB) 안이다. 그러나 **실행 하나의 링(8 MiB)보다 22 – 49 MB 크다** — 링 밖에서 범람 동안만 자라는 몫이 있다. 끝난 뒤 대부분 +1 – 7 MB 로 돌아오지만 161243-0 은 +31 MB 가 남았다. 원인 자리(고치지 않았다): 링 밖에서 바이트가 머무는 곳 — PTY 를 읽어 링에 넣는 쪽의 읽기 버퍼와 `run.attach` 스트림이 credit 을 기다리는 동안의 묶음 · base64 인코딩(`crates/pw-run/src/runs/log.rs` · `runs/methods.rs` 의 attach), 그리고 할당기가 OS 에 돌려주지 않은 페이지. 회마다 1초 표본이라 순간 최댓값은 더 클 수 있다. 실행 여럿(8 MiB × N)에서 이 몫이 실행 수에 비례하는지는 재지 않았다.

**콘솔 프레임(판정 안 함).** 유효한 회는 161243-0 하나: `withinVsync` 0.99, `vsyncMs` **19 ms**, p95 25 ms, 최대 39 ms, 가장 긴 메인 스레드 막힘 34 ms(50 ms 넘음 0회), rAF 콜백 p95 1 ms. 판정 규칙대로면 `vsyncMs` ≤ 17 을 넘지만 외부 화면의 주사율 · 사람 입력이 있던 때라 판정하지 않는다. 가려진 회는 rAF 가 멎어(`stalls` 23 – 28) 프레임 값이 무의미하다.

**관찰(판정 밖) 둘:**

1. **콘솔은 초당 약 0.7 MB 만 그린다**(20초에 13.9 MB, 유효 회). 실행은 초당 10 MB 를 써서, 콘솔이 뒤처진 만큼 Host 링이 앞을 버리고 콘솔이 「앞 출력 5.6 – 12.1 MB 가 버려졌다」 줄을 20번 적었다(설계대로의 동작 — run-stream.ts). 즉 범람 중 콘솔이 보이는 것은 출력의 약 7 % 다. 프레임은 지켰으니 흐름 제어는 돈다. 처리량의 원인 자리: xterm 쓰기 + `LevelHighlighter.scan`(`run-levels.ts`) + base64 디코드 — 세 몫을 나눠 재지 않았다.
2. **범람 중 WebContent 가 +340 MB**(160 – 170 → 501 – 518 MB, 6회 모두), 끝난 뒤 187 – 250 MB 로 내려온다. 콘솔 scrollback 과 쓰기 대기열 몫으로 보인다(xterm `scrollback` 설정 · `HIGH_WATER` — `terminal-session.ts`). 앱 인스턴스 합계가 범람 동안 600 MB 를 넘는다. 06 의 목표 행(유휴 300 MB)은 유휴에만 걸리므로 판정 밖이다.

## 5. ③ 디버그 어댑터의 끝(`debug-end`)

[`…-debug-end-163042`](2026-11-19-m6-perf-debug-end-163042.summary.md). 어댑터 셋 × 끝맺음 둘 × 3회 = 18회, 모두 통과. 시각 기준: `exit` 는 웹뷰가 세션 끝을 본 때, `stop` 은 중지를 부른 때. 25 ms 마다 앱의 자손을 보았다.

| 어댑터 / 끝맺음 | 세션 끝 → 그 세션의 프로세스가 모두 사라짐 | 누르기 전에 떠 있던 자손 |
| --- | --- | --- |
| codelldb / exit | 21 ms (17 – 23) | 0 |
| codelldb / stop | 155 ms (152 – 162) | 0 |
| js-debug / exit | **1255 ms** (1253 – 1255) | 0 |
| js-debug / stop | **1276 ms** (1265 – 1276) | 0 |
| debugpy / exit | 6 ms (1 – 16) | 0 |
| debugpy / stop | 30 ms (28 – 45) | 0 |

- 어댑터는 누르기 전에 없었고 누른 뒤에 떴다(셋 모두). 누르면 런타임 환경을 읽는 로그인 셸(`zsh` 와 사용자 셸 설정이 띄우는 `git` · `mise` · `docker` 등)도 함께 뜨는데 세션 끝 전에 사라진다.
- js-debug 는 어댑터 `node` 하나가 세션 끝 뒤 **약 1.25초** 더 산다(대상 `node` 는 바로 끝난다). 2초 안이지만 여유가 0.7초다. 원인 자리: js-debug 의 `dapDebugServer.js` 가 연결이 끊긴 뒤 스스로 끝나기까지의 시간, 또는 Pitwall 이 어댑터를 끝내는 차례(`crates/pw-dap/src/process.rs` — disconnect 응답을 기다린 뒤 끝낸다면 그 기다림). 나눠 보지 않았다.
- 첫 측정(`161243`)에서 17회 중 3회가 「누르기 전의 자손」 으로 실패로 적혔다 — 신뢰 프로젝트를 연 직후의 로그인 셸이 누르기와 3 – 38 ms 차로 겹친 것이다. 시나리오를 첫 프레임 3초 뒤에 누르게 하고(`2b175494`), 판정을 「누르는 때에 살아 있던 자손」 으로 고쳤다(`60c2c43f`). 그 셸은 어댑터가 아니다.
