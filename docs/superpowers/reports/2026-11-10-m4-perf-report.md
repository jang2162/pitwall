# M4 성능 확인 — M4-19

이 문서는 잰 시점의 기록이다. 측정 방법은 `CONTRIBUTING.md` 「성능 기준선」(「LSP 시나리오」 포함), 목표는 `docs/design/06-roadmap.md` 「성능 목표 (검증 기준)」, 완료 기준은 `docs/design/15-m4-plan.md` 의 M4-19 행이 정본이다. 비교 대상 M3 기준선은 [`2026-11-01-m3-perf-report.md`](2026-11-01-m3-perf-report.md) §3.

**상태: 목표 밖 둘, 판정을 메인에 올리는 것 하나.** 목표 밖은 ⌘O · ⌘⌥O 의 키 입력당 시간(33 – 39 ms, 목표 30 ms — Host + IPC 는 8 – 10 ms 이고 나머지가 웹뷰 몫)과 타이핑 지연의 LSP 켬 − 끔(3 ms, 목표 2 ms)이다. 메인에 올리는 것은 유휴 메모리다. 정한 방법(빈 프로젝트)으로는 208.7 MB 로 목표 안이지만, 이 저장소에 rust-analyzer 를 켜고 파일 하나를 연 상태에서는 Pitwall 몫이 약 414 MB 다(§5 ③). 나머지 잰 칸은 모두 목표 안이다. 측정 중에 하네스 버그 셋을 찾아 고친 뒤 해당 단계를 다시 쟀다(§4).

읽는 법:

- **⑨ ⑩ 의 웹뷰 몫은 23 – 29 ms 다.** 키 → 결과 프레임 33 – 39 ms 에서 Host + IPC 왕복 8 – 10 ms 를 빼면 남는다. Host 만의 질의는 §2 에서 2.5 – 7 ms 이므로 IPC 는 약 3 – 4 ms 다. 이어지는 키의 중앙값이 회마다 33 ms 로 고정이다 — 두 프레임(2 × 16.7 ms)이다. 응답이 온 뒤 결과가 한 프레임 늦게 그려지는 것으로 보인다(추정 — §5 ①).
- **⑦ 은 rAF 해상도 1 ms 에서 3 ms 다.** p95 는 정수 ms 로 잘려 있고, 켬 17 – 18 · 끔 12 – 15 로 범위가 겹치지 않는다. 다섯 회 모두 켬이 끔보다 느렸다.
- 콜드 스타트 +50 ms(M3 427 → 477)는 1,500 ms 목표에 비하면 작다. 늘어난 곳을 따로 재지는 않았다. `pitwall` 프로세스의 유휴 메모리가 48 – 50 → 58 – 59 MB 로 는 것(LSP · 인덱스 코드)과 같은 방향이다.

## 4. 측정 경과 · 하네스 수정

**① symbols · classes 가 회마다 시간 초과했다 — 질의가 저장소에 없는 이름이었다(`5838f2d4`).** 앱 안 시나리오의 `SYMBOL_QUERY = "handleItem1234x5"` 는 합성 저장소에 없는 이름이다. 생성기가 메서드 k 의 동사를 `verbs[k % 6]` 로 고르므로 `x5` 는 `computeItem1234x5` 다. Rust 시험의 출력도 마지막 키에서 `0 matched` 였다. 시나리오는 키마다 그 질의의 결과 줄(`data-symbol-query`)을 기다리는데 결과가 0개면 줄이 없어서 30초 뒤 실패했다(6회 모두 같은 자리). classes 는 두 번째 팝업(⌘⌥O)에서 같은 이유로 실패했다. 질의를 `handleItem1234x6` 으로 바꿨다 — 길이 16자는 같고 모든 접두가 결과를 낸다. M4-15 시험의 낱말을 잠시 바꿔 돌려 `handleItem1234x6` 이 38 matched(접두 `handleItem1234x` 까지 152)인 것을 확인했고, 시험 파일은 되돌렸다. M4-15 시험 자체의 질의는 그대로다(Host 시간이라 결과 0개도 잴 수 있다). **다른 시나리오 상수를 훑은 결과:** `CLASS_QUERY = "Widget1234"` 는 Kotlin 파일의 클래스로 있다. classes 단계의 첫 팝업이 표지(`symbol_keys`)를 남기고 지나갔다. LSP 픽스처의 파일 · 줄 · 낱말(`MAIN_PATH` · `DEF_WORD` · `DIAG_MARK` · `COMPLETION_LABEL` 등)은 pw-perf 의 픽스처와 같은 값인지 이미 시험(`the_fixture_has_what_the_app_scenario_looks_for`)이 보고, lsp · typing 단계가 끝까지 돌았다. `IDLE_PATH`(`crates/pw-core/src/lib.rs`)는 사본에 있고 ra-idle 이 끝까지 돌았다. 없는 이름을 기다리는 곳은 이것 하나였다.

**② 언어 서버 메모리가 잘못 잡혔다(`287e190f`).** 서버 몫을 「앱의 책임 pid 그룹 안에서 `pitwall` 도 WebKit 도 아닌 것」 으로 셌는데, 언어 서버는 그 그룹에 들지 않는다. 고치기 전 ra-idle 표본에는 rust-analyzer(로그의 pid 16049)가 없었고, 서버 몫 7.68 MB 는 `com.apple.audio.SandboxHelper` 5.47 MB + `SetStoreUpdateService` 2.21 MB 였다. 가짜 서버 단계의 7.7 MB 도 같은 두 프로세스였다. 이제는 앱 프로세스의 자손(부모 pid 로 찾는다 — 손자 포함)을 표본에 더하고 그것을 서버 몫으로 센다. 그룹의 보조 프로세스는 앱 몫이다. 그래서 `lsp-205331` · `typing-*-211337` 의 「language server」 칸(7.7 MB)은 서버 값이 아니다. 그 회의 Pitwall 쪽 시간 수치에는 영향이 없다. 앱 몫에서 보조 프로세스 약 7.7 MB 가 빠져 있을 뿐이다.

**③ rust-analyzer 가 프로젝트 툴체인 없이 떴다(`11d265ba`).** Pitwall 은 프로젝트의 런타임을 `mise env` 로 구하는데, 사본(`target/perf-m4/repo`)의 `mise.toml` 을 mise 가 신뢰하지 않아(`NotTrusted`) 경고가 반복됐다. ra-idle 단계에만 `MISE_TRUSTED_CONFIG_PATHS=<사본>` 을 준다. 앱 → 로그인 셸 → `mise env` 로 이어지는 것을 손으로 확인했다. 사람의 trust 목록은 바꾸지 않았다(`mise trust --show` 에 사본 0건). 고치기 전 회(`ra-idle-211337`, 커밋하지 않음)는 서버 RSS 가 21 MB 라 작업 공간을 읽지 않은 것으로 보고 버렸다.

**④ 사람 입력 · 부하로 멈춘 회차.** 오전 11:42:37 · 11:47:38 · 11:52:37(맨 앞 앱 Chrome · Orca · Chrome)과 저녁 20:50:34 · 21:11:12 · 21:37:03 에 입력이 있어 그 단계를 멈췄다. `pmset -g log` 에 그 시각마다 WindowServer 의 `UserIsActive`(`AppleMultitouchDevice` — 오전 Magic Trackpad, 저녁 내장 키보드 · 트랙패드)가 남아 있다. 실제 장치 입력이다. 20:19 에는 사람의 Chromium 전체 빌드로 1분 load 가 74 라 기다렸다. 20:36 에 15 아래로 내려와 시작했다. 멈춘 단계의 결과와 고치기 전 회의 symbols · classes · ra-idle 결과는 이 폴더에 넣지 않았다(회별 표지 파일과 앱 로그는 `target/perf/m4-*-2026-11-10-*/run-<N>/`, 커밋하지 않음). 조건 파일 `…-211337.json` 은 그 회의 다섯 단계(symbols · classes 는 exit 3)를 그대로 적고 있다.

**하네스 시험(이 행).** pw-perf 44개 통과(이번에 더한 것: `lsp::tests::the_servers_are_every_descendant_of_the_app_process`, `macos::tests::a_child_reports_this_process_as_its_parent`, `memory_is_split_between_pitwall_and_the_server` 에 보조 프로세스 칸). scripts node `perf-m4.test.mjs` 4개 통과(ra-idle 단계만 사본 trust 환경을 갖는다는 단언을 더했다). vitest `perf-scenario-lsp.test.ts` 2개 통과. 되돌림 실증은 넷이다. 보조 프로세스를 서버로 세게 되돌리면 `memory_is_split_…`, 자손을 한 단계만 찾게 하면 `the_servers_are_every_descendant_…`, 부모 대신 자기 pid 를 돌려주게 하면 `a_child_reports_…`, ra-idle 의 env 를 빼면 `each step runs the scenario …` 가 실패했다. 복구 뒤 모두 통과했다. `11d265ba` 에서 `mise run test` 전체: nextest 2,353 통과(30 건너뜀) · vitest 1,820(데스크톱 1,674) · scripts node 54 · doctest 15, `mise run lint` 통과. 겹친 판정: `observe_lsp` 가 자손을 표본에 더하는 배선 자체는 단위 시험이 없다 — §3 ⑪ ⑫ 의 실측(서버 pid · 이름이 로그와 같다)이 그 확인이다.

## 6. 지침 제안

- `CONTRIBUTING.md` 「성능 기준선」 의 「LSP 시나리오」 끝에 다음 문장을 넣는다. 「앱 안 시나리오가 키마다 결과 줄을 기다리는 질의는 모든 접두가 결과를 내는 이름이어야 한다 — 합성 저장소에 없는 이름이면 0개 결과에서 시간 초과한다(`SYMBOL_QUERY`, M4-19).」
- 같은 절에 다음 문장을 넣는다. 「언어 서버는 앱의 책임 pid 그룹에 들지 않는다 — 서버 메모리는 앱 프로세스의 자손으로 센다(`pw-perf` `lsp::descendants`).」
- `docs/ops/` 또는 같은 절에 다음 문장을 넣는다. 「실기 측정 중 `HIDIdleTime` 이 짧아지면 그 단계를 버린다 — 트랙패드 접촉 하나로도 창이 가려지거나 앞 앱이 바뀐다(2026-11-10). `pmset -g log` 의 `UserIsActive` 로 입력원을 확인한다.」
