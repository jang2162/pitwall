# 원격 체크아웃 — 한 프로젝트 안에서 로컬과 원격을 고른다 (설계)

2026-11-13. 원격(M7, `docs/design/08-remote-mobile.md`)의 프로젝트 모델을 바꾸는 설계다. 승인되면 `docs/design/` 의 해당 문서에 옮겨 적고 `06-roadmap.md` 「결정 기록」 에 결정으로 남긴다 — 그 뒤로는 `docs/design/` 이 정본이고 이 문서는 그때의 판단 기록이다.

표기: **(사용자)** 는 사람이 정한 것, **(제안)** 은 이 문서를 쓴 쪽이 채운 것이다. 제안은 사람이 고칠 수 있다.

## 1. 의도

같은 저장소를 로컬과 원격 머신 양쪽에 두고 쓴다. 지금 설계에서는 그 둘이 서로 다른 프로젝트 두 개가 되어 창 · 열린 탭 · 목록이 갈린다. **프로젝트는 하나로 두고, 그 안에서 워크트리를 고르듯 원격 머신의 체크아웃을 고르게 한다** (사용자).

쓰임은 둘이다 (사용자).

1. **로컬에서 코드를 쓰고 원격에서 테스트한다.** 로컬 체크아웃에서 고치고 커밋한 뒤, 그 커밋을 원격 체크아웃으로 보내 거기서 테스트를 돌리고, 로컬에서 계속 고치면서 원격의 실행 로그를 본다.
2. **밖에서 원격 머신에 붙어 작업한다.** 노트북에는 그 저장소가 없을 수도 있다.

원격 체크아웃으로 가는 길이 워크트리를 바꾸는 것만큼 자연스러워야 한다 (사용자).

## 2. 용어

| 말 | 뜻 |
| --- | --- |
| 머신 | Host 하나. 이 Mac(로컬 Host) 또는 Relay 가 도는 원격 머신 |
| 체크아웃 | (머신, 워크트리) 한 쌍. 메인 체크아웃도 워크트리의 하나로 센다. 지금의 「활성 워크트리」 를 머신까지 넓힌 것이다 |
| 멤버 프로젝트 | 어느 한 머신의 레지스트리에 등록된 프로젝트. 지금의 프로젝트 레코드 그대로다(`pw_core::registry::Project`) |
| 묶음 | 한 저장소의 체크아웃들을 가진 멤버 프로젝트들의 모음. 사람에게는 이것이 「프로젝트」 다 |

「환경」 이라는 말은 쓰지 않는다 — 런타임 환경(`03-architecture.md` 「런타임 환경 (D26)」)과 실행 환경(`04-features.md` 「F7. 실행 환경 & 디버깅」)이 이미 쓴다 (제안).

## 3. 목표 · 비목표 · 반목표

**목표**

- 프로젝트 목록 · 스위처 · 창에서 로컬과 원격이 한 프로젝트로 보인다.
- 프로젝트 창 안에서 체크아웃을 바꾼다. 로컬 워크트리와 원격 머신의 체크아웃이 같은 목록에 있다.
- 한 창에서 서로 다른 체크아웃의 탭을 함께 둔다 — 로컬 파일 탭 옆에 원격 터미널 · 실행 로그 탭.
- 커밋을 한 머신의 체크아웃에서 다른 머신의 체크아웃으로 origin 을 거치지 않고 보내고 받는다.
- 로컬 체크아웃이 없는 프로젝트(원격만)를 연다.
- 에이전트가 MCP · CLI 로 대상 체크아웃을 골라 같은 일을 한다.

**비목표** (이 설계에서 하지 않는다)

- 커밋 안 한 변경을 다른 머신으로 옮기는 것(패치 보내기 · 작업 트리 동기화). 코드는 git 커밋으로만 건너간다 (사용자).
- 로컬 워크트리마다 원격 짝 워크트리를 자동으로 만드는 것. 보낼 때 대상을 고르고 기억한다 (사용자).
- origin 에 push 하고 원격에서 pull 하는 것을 한 번에 해 주는 버튼. 그 길은 git 화면에서 손으로 된다 (사용자).
- 컨테이너 · WSL 을 머신으로 다루는 것(`04-features.md` F9-13).
- 앱이 꺼진 상태에서 다른 머신의 체크아웃을 겨누는 툴 호출.
- 같은 프로젝트를 창 여러 개로 여는 것 — 「프로젝트당 한 창」 은 그대로다.

**반목표** (되더라도 실패로 본다)

- 지금 어느 머신을 보고 있는지 헷갈리는 화면. 다른 머신에 파괴적 작업을 하는 사고로 이어진다.
- git 이 거절한 것을 덮는 것. 대상 체크아웃의 커밋 안 한 변경 · 갈라진 브랜치는 그대로 남아야 한다.
- 로컬에서 준 신뢰가 원격 머신으로 번지는 것.
- 테스트용 중간 커밋이 origin 으로 새는 것.

## 4. 제약 (이미 정해진 것)

- Host 는 「한 머신에서 프로젝트를 다루는 헤드리스 서비스」 다(`03-architecture.md` 「전체 구조」). 다른 머신의 체크아웃을 알지 못한다.
- Host Router 는 연결 단위로 라우팅하고, 요청 · 스트림 · 구독 id 는 그 Host 세션 안에서만 유효하다(`03-architecture.md` 「RPC 설계」).
- ref · index · 작업 트리를 바꾸는 것은 git CLI 로 한다(`06-roadmap.md` 결정 D39).
- git 이 스스로 거절하는 것은 덮지 않고 원문을 보인다(결정 D42).
- 미신뢰 프로젝트에서도 사람이 누른 git 쓰기는 되고 훅은 git 이 하는 대로 돈다(결정 D43).
- 비밀은 Desktop 의 키체인에 두고 Relay 로는 세션 동안 필요한 것만 보낸다(결정 D47).
- 미신뢰 프로젝트는 DB 연결 · 언어 서버 · 런타임 제공자 · 실행을 하지 않는다(결정 D35 · D48 · D52).
- UI 상태(레이아웃 · 열린 탭 · 미저장 편집)는 Desktop 로컬에 둔다(`08-remote-mobile.md` 「로컬 / 원격 역할 분담」).
- 가벼움은 제품 목적이다(결정 D56) — 쓰지 않는 머신의 연결 · 감시 · 언어 서버를 미리 띄우지 않는다.

## 5. 접근

**① 묶음 방식 — 고른 것 (사용자).** 머신마다 프로젝트는 지금 설계대로 그 머신의 레지스트리에 따로 등록된다(멤버 프로젝트). Desktop 이 「이 멤버 프로젝트들은 한 저장소의 체크아웃들」 이라는 묶음을 기억하고, 창은 묶음을 프로젝트 하나로 보인다.

- 좋은 점: Host 의 정의 · RPC · 레지스트리가 그대로다. 신뢰가 머신별인 것이 저절로 된다. 기기 둘(노트북 · 데스크톱)이 같은 Relay 에 붙어도 부딪히지 않는다. 원격 머신의 에이전트는 그 머신의 레지스트리만으로 동작한다.
- 대가: 「프로젝트 하나」 라는 정체가 Desktop 에만 있다. 즐겨찾기 · 태그 · 최근 순서를 묶음 단위로 둬야 한다. 다른 머신의 체크아웃을 겨누는 툴 호출은 Desktop 이 묶음을 풀어 줘야 해서 앱이 떠 있을 때만 된다.

**② 프로젝트가 여러 머신에 걸친다 — 고르지 않음.** 프로젝트 레코드가 체크아웃 목록을 직접 갖고 모든 머신이 같은 프로젝트 id 를 쓴다. 개념은 가장 깔끔하지만 id 를 머신 사이에 맞춰야 해서 두 기기가 같은 원격 체크아웃을 각자 등록하면 부딪히고, Host 가 다른 머신의 체크아웃을 알게 되어 레지스트리 · 라우터 · 신뢰 저장을 다시 짜야 한다.

**③ 로컬 Host 가 원격을 대신 불러 준다 — 뺌.** 화면 변경은 가장 적지만 스트림 · 구독 · 세션을 로컬 Host 가 전부 중계해야 해서 「연결 단위 라우팅」 과 어긋나고, 로컬 체크아웃이 없는 프로젝트를 표현하지 못한다.

고른 이유: ① 은 이미 만든 Host 쪽을 건드리지 않고 Desktop 층에서 끝난다. ② 의 깔끔함은 기기가 하나일 때만 유지되는데 쓰임 2 는 기기가 둘 이상이라는 뜻이다.

## 6. 설계

### 6.1 묶음

- 묶음은 Desktop 이 가진다: 묶음 id, 목록 정보(이름 · 즐겨찾기 · 태그 · 마지막으로 연 시각), 멤버 목록 `(머신 id, 그 머신의 프로젝트 id)` (제안).
- 로컬 프로젝트 하나는 멤버가 하나인 묶음이다. 지금 등록된 프로젝트는 손대지 않아도 그대로 보인다 (제안).
- 묶음에 멤버를 더하는 것은 사람이 한다 — 「원격 체크아웃 추가」: 머신을 고르고(`08-remote-mobile.md` 의 원격 호스트 등록), 그 머신의 경로를 고르면(Relay 의 `roots` 안), 그 머신에 프로젝트로 등록하고(이미 등록돼 있으면 그 프로젝트) 묶음에 넣는다 (제안).
- 넣기 전에 같은 저장소인지 본다 — 묶음의 다른 멤버와 공통 커밋이 없으면 넣지 않고 까닭을 보인다. 보내기 · 가져오기가 성립하지 않기 때문이다. 멤버가 하나뿐인 묶음(원격만)은 볼 것이 없다 (제안).
- 한 머신에 멤버는 하나다. 그 머신의 다른 워크트리는 멤버 프로젝트의 연결 워크트리로 저절로 나온다(`04-features.md` 「워크트리 경로 처리 (F2-5)」 의 규칙을 그 머신의 Host 가 그대로 쓴다) (제안).
- 멤버를 묶음에서 빼는 것은 Desktop 의 묶음에서만 뺀다. 그 머신의 프로젝트 등록과 파일은 건드리지 않는다 (제안).
- **멤버 프로젝트는 묶음 하나에만 든다** (제안). 더하려는 멤버가 이미 다른 묶음에 있으면: 그 묶음의 멤버가 그것 하나뿐이면 옮긴다(옮겨 오는 쪽 묶음의 이름 · 즐겨찾기 · 태그가 남고, 비어 버린 묶음은 지운다. 탭 묶음은 체크아웃별이라 함께 온다), 멤버가 둘 이상이면 거절하고 먼저 거기서 빼라고 알린다. 쓰임 2 로 쓰던 「원격만」 묶음에 나중에 로컬 클론을 합치는 것이 앞의 경우다.
- **원격만 있는 묶음을 만드는 자리**는 웰컴 창의 원격 호스트다(`10-ui.md` 「화면 목록」 의 원격 호스트 화면): 머신 → 경로를 고르면 멤버 하나인 묶음이 생기고 창이 열린다. 거기에 로컬 멤버를 더할 때는 「체크아웃 추가」 에서 「이 Mac」 을 골라 이미 있는 폴더를 고른다 — 클론은 해 주지 않는다 (제안).

### 6.2 프로젝트 창과 체크아웃

고르는 자리는 상단 브랜치 팝업의 워크트리 목록이다(`10-ui.md` 「Git」 절의 브랜치 팝업) (제안).

```
 체크아웃
 ──────────────────────────────────────
 이 Mac
 ● 메인 체크아웃            feat/login
   .worktrees/fix-auth      fix/auth
 build-server   연결됨
   ~/work/pitwall           main
   ~/work/pitwall-wt/ci     ci/flaky
 home-pc        끊김
   ~/dev/pitwall            feat/login
 ──────────────────────────────────────
 + 원격 체크아웃 추가…
```

- **활성 체크아웃이 창의 기준이다** (제안). 파일 트리 · 검색 · git 화면 · 새 터미널 · 실행 · DB 탐색기 · 언어 서버가 그 머신의 그 워크트리를 본다. 지금 활성 워크트리가 하는 일을 머신까지 넓힌 것이다.
- **탭은 자기를 연 체크아웃을 기억한다** (제안). 지금 탭이 자기 워크트리를 기억하는 규칙(`10-ui.md` 「상태 복원」)을 그대로 넓힌다. 그래서 활성 체크아웃을 바꾸지 않고도 다른 체크아웃의 파일 · 터미널 · 실행 로그 · DB 문서 탭이 한 창에 함께 있다. 쓰임 1 의 「로컬에서 고치며 원격 테스트를 본다」 가 이것으로 된다.
- **탭 묶음은 체크아웃별로 기억한다** (제안). 체크아웃을 바꿀 때의 절차(지금 묶음 저장 → 탭 닫기(미저장 확인) → 그 체크아웃의 묶음 열기)는 지금 워크트리 전환과 같다. 저장은 Desktop 로컬이다.
- **실행 · 터미널은 대상 체크아웃을 골라 열 수 있다** (제안). 기본은 활성 체크아웃이지만, 활성 체크아웃을 바꾸지 않고 다른 체크아웃에 새 터미널을 열거나 실행 구성을 돌리는 길을 둔다(실행 구성 고르는 자리와 터미널 열기에 대상 체크아웃 고르기. 보내기가 끝난 알림에 [거기서 실행] · [거기서 터미널]). 전환은 에디터 탭을 닫고 그 머신의 파일 트리 · 감시 · 언어 서버를 띄우므로 쓰임 1 의 되풀이에는 무겁다. 터미널 · 실행 탭은 탭 묶음에 들지 않아 전환해도 남는다(지금 터미널이 그렇다).
- **닫는 것과 끊기는 것은 다르다** (제안). 연결이 끊긴 것(네트워크 · 덮개)은 Relay 가 그 머신의 실행 · 터미널을 유지하고 다시 붙으면 이어 본다(F9-7). 사람이 닫는 것(탭 · 창)은 지금 규칙대로 그 프로세스를 끝내되(실행 중이면 확인), 원격 머신의 것은 확인에 [끝내기] 와 함께 [두고 닫기] 를 둔다 — 두면 다음에 그 체크아웃을 열 때 이어 본다. 활성 체크아웃을 바꾸는 것은 닫는 것이 아니다. 「이어 보기」 와 「그 체크아웃에서 돌고 있는 것 목록」 은 F9-7 이 어차피 만들어야 하는 것(실행 · 터미널이 연결이 아니라 Host 에 속하고 목록을 묻는 RPC)을 쓴다 — 지금 터미널은 연결이 닫히면 끝나고 목록 RPC 가 없다(`crates/pw-run`).
- **어느 머신인지 늘 보인다** (제안 — 반목표 1). 활성 체크아웃이 원격이면 타이틀바 · 상태바에 머신 이름을 보이고, 활성 체크아웃과 다른 머신의 탭은 탭 머리에 머신 표지를 단다. 위험 작업의 확인 다이얼로그(결정 D42)는 대상 머신 이름을 문장에 넣는다.
- **연결은 쓰는 머신만 연다** (제안 — 가벼움). 창은 활성 체크아웃의 머신과, 탭이 열려 있는 체크아웃의 머신에만 Host 연결을 둔다. 목록의 연결 상태 표시는 머신 수준의 가벼운 확인으로 하고 프로젝트 연결 · 파일 감시 · 언어 서버를 띄우지 않는다.
- **끊긴 머신.** 목록에 「끊김」 으로 남고, 그 머신의 탭은 읽기 전용 표시와 함께 남으며 미저장 편집은 로컬에 보관된다(`04-features.md` F9-8). 다른 머신의 탭 · 활성 체크아웃은 영향이 없다. 원격에서 돌던 프로세스는 Relay 가 유지한다(F9-7) (제안).
- **프로젝트 목록 · 스위처**는 묶음 한 줄이다. 그 줄에 멤버 머신을 표지로 보인다. 원격만 있는 묶음은 그 머신이 끊겨 있으면 열 수는 있되 「끊김」 으로 뜬다 (제안).
- **열기 요청.** 로컬의 `pitwall <path>` 는 로컬 멤버의 체크아웃으로 푼다(지금과 같다). 원격 터미널의 `pitwall <file>`(`08-remote-mobile.md` 「원격 기능 범위」 의 마지막 행)은 그 머신의 멤버가 든 묶음의 창에서 **활성 체크아웃을 바꾸지 않고** 그 체크아웃의 탭으로 연다 — 최근 파일 · Search Everywhere 가 다른 워크트리의 파일을 여는 것과 같은 규칙이다. 원격의 에이전트가 파일을 열 때마다 로컬에서 보던 탭이 닫히면 안 된다 (제안).

### 6.3 커밋 보내기 · 가져오기

한 머신의 체크아웃에 있는 브랜치를 다른 머신의 체크아웃으로 옮기고, 대상 체크아웃을 그 브랜치의 그 커밋으로 맞춘다. origin 은 건드리지 않는다 (사용자).

- **보내기**는 활성 체크아웃 → 고른 체크아웃, **가져오기**는 고른 체크아웃 → 활성 체크아웃이다. 방식은 같다 (제안).
- **옮기는 것**은 원본 체크아웃의 지금 브랜치와 거기까지의 커밋이다. 커밋 안 한 변경은 가지 않는다 — 원본에 커밋 안 한 변경이 있으면 「N개 파일의 변경은 가지 않는다」 를 보이고 막지는 않는다 (제안).
- **전달 방법** (제안): 원본 머신에서 git 으로 묶음 파일을 만든다(`git bundle` — 대상이 이미 가진 커밋은 뺀다). 그것을 Pitwall 의 연결(RPC 스트림)로 대상 머신에 보낸다. 대상 머신에서 git 으로 그 파일을 받아 Pitwall 전용 ref(`refs/pitwall/incoming/…`)에 둔다. 양쪽 다 git CLI 다(결정 D39). 원격 ↔ 원격도 Desktop 이 사이에서 이으면 같은 방식이지만 이 설계의 완료 기준은 로컬 ↔ 원격이다.
- **대상 맞추기** (제안):
  - 대상 저장소에 그 브랜치가 없으면 만들고 대상 체크아웃을 그 브랜치로 바꾼다.
  - 있고 받은 커밋이 그 브랜치의 앞이면(fast-forward) 올리고 대상 체크아웃을 그 브랜치로 바꾼다.
  - 대상 브랜치에 원본에 없는 커밋이 있으면(갈라짐) **아무것도 바꾸지 않고 멈춘다.** 받은 커밋은 전용 ref 에 남기고 「대상에만 있는 커밋 N개」 를 알린다 — 사람이 대상 체크아웃의 git 화면에서 병합하거나 반대 방향으로 가져온다. 강제로 덮는 옵션은 두지 않는다.
  - 대상 작업 트리의 커밋 안 한 변경 때문에 git 이 브랜치 전환을 거절하면 원문을 보이고 멈춘다(결정 D42). 받은 커밋은 전용 ref 에 남는다.
  - 그 브랜치를 대상 머신의 다른 워크트리가 이미 체크아웃하고 있어 git 이 거절하면 같다 — 원문을 보이고 멈춘다.
- **대상 고르기.** 보낼 때 다른 머신의 체크아웃 중에서 고른다. 원본 체크아웃마다 마지막으로 고른 대상을 기억해 다음에는 그것이 먼저 골라져 있다 (사용자 — 기억, 제안 — 세부).
- **되돌리기.** 대상의 브랜치 ref 를 움직였으면 알림에 이전 해시와 [되돌리기]를 단다(결정 D42 의 ref 를 움직인 작업과 같은 규칙) (제안).
- **신뢰와의 관계.** 대상이 미신뢰 체크아웃이어도 보내기는 된다 — 사람이 누른 git 쓰기다(결정 D43). 훅은 대상 머신에서 git 이 하는 대로 돈다 (제안).
- **실행 중인 것.** 대상 체크아웃에서 돌고 있는 실행 · 터미널이 있으면 보내기 확인에 그 사실을 보인다. 막지는 않는다 (제안).

### 6.4 신뢰 · 설정 · 비밀

- **신뢰는 머신마다다** (제안). 멤버 프로젝트가 그 머신의 레지스트리에 자기 신뢰를 가진다(지금 구조 그대로). 원격 체크아웃을 처음 열 때 그 머신 기준으로 한 번 묻는다. 로컬에서 신뢰했다는 사실은 원격에 영향이 없고 그 반대도 같다.
- **프로젝트 설정**(`.pitwall/*.toml`)은 체크아웃마다 그 체크아웃의 파일을 읽는다. 브랜치가 다르면 내용이 다를 수 있다 — 그것이 맞다. `*.local.toml` 과 개인 전용 설정은 그 머신의 것이다(워크트리의 폴백 규칙은 그 머신 안에서 그대로) (제안).
- **DB 연결 · 실행 구성**은 활성 체크아웃의 머신에서 나간다. 같은 연결 정의(`localhost:5432`)가 머신마다 다른 서버를 가리킬 수 있다 — 연결 표지에 머신 이름을 함께 보인다 (제안).
- **비밀**은 Desktop 키체인에 (머신, 멤버 프로젝트, 연결)마다 둔다. 같은 연결 id 라도 머신이 다르면 다른 항목이다. 묶음 id 는 키에 넣지 않는다 — 멤버를 다른 묶음으로 옮겨도 비밀이 그대로 따라온다(지금 키는 프로젝트 id 로 만든다, `crates/pw-db/src/secret.rs` 의 `account`). Relay 로는 세션 동안 필요한 것만 보낸다(결정 D47) (제안).

### 6.5 MCP · CLI

- 세션의 체크아웃은 지금처럼 `--project` · cwd 가 가리키는 그 머신의 체크아웃이다. 원격 머신의 에이전트는 그 머신 Relay 의 MCP 에 붙어 그 머신의 체크아웃을 다루고, 승인 요청은 연결된 Desktop 으로 온다(`08-remote-mobile.md` 「원격 기능 범위」) (기존).
- **대상 지정** (제안): 프로젝트 툴에 선택 입력 `checkout`(머신 + 워크트리)을 더한다. 없으면 세션의 체크아웃이다. 다른 머신을 겨누는 호출은 Desktop 이 묶음을 풀어 그 머신의 Host 로 보낸다 — 앱이 떠 있고 그 머신이 연결돼 있을 때만 되고, 헤드리스에서는 거절한다. 선택 입력이라 M5 에서 만든 툴과 하위 호환이다(결정 D41 이 `repo` 에 쓴 것과 같은 규칙).
- **새 툴** (제안): `checkout_list`(read — 묶음의 체크아웃 · 머신 연결 상태 · 브랜치), `checkout_send`(write — 6.3 의 보내기. 원본 · 대상 체크아웃을 받는다). git 쓰기를 툴로 내놓지 않는다는 규칙(`05-mcp.md` 「Git」 표)의 예외다 — 에이전트가 git CLI 로는 다른 머신에 origin 없이 보낼 길이 없기 때문이다. 가져오기는 같은 툴에 원본 · 대상을 바꿔 준 것이다.
- **다른 머신을 겨눌 수 있는 것은 Desktop 의 세션뿐이다** (제안). 원격 머신 Relay 의 MCP 세션은 그 머신의 체크아웃만 다룬다 — `checkout` 에 다른 머신을 주면 거절하고 `checkout_send` 는 싣지 않는다. 묶음은 Desktop 만 알고, 원격 머신의 에이전트가 내 Mac 에 git 쓰기 · 실행을 하는 길을 열지 않는다. 원격에서 만든 커밋을 로컬로 옮기는 것은 Desktop 쪽에서 가져오기로 한다.
- **「연결돼 있을 때」 의 뜻** (제안): 그 머신에 닿을 수 있으면 Desktop 이 그때 연결을 연다 — 이미 열린 연결이 있어야 하는 것이 아니다(「연결은 쓰는 머신만 연다」 와 함께 두면 그래야 에이전트 흐름이 된다). 승인을 물을 자리가 있어야 하므로 그 묶음의 창은 열려 있어야 한다(`05-mcp.md` 「권한 모델」 의 승인 요청 라우팅과 같다). 창이 없으면 거절한다. git 쓰기는 프로젝트로 연 연결만 받으므로(`pw_core::registry` 의 `scope_may_write`) Desktop 은 대상 멤버 프로젝트로 연 연결로 보낸다.
- **등급 판정** (제안): 다른 머신을 겨누는 호출도 등급 규칙은 같다. `exec` 의 「신뢰된 프로젝트」 는 대상 머신의 신뢰를 본다. 툴 노출은 지금처럼 세션 프로젝트의 설정이 정한다.
- **다른 머신을 겨누는 쓰기 · 실행의 승인** (사용자 — 머신마다 세션에 한 번): 설정의 `auto_approve` 는 다른 머신을 겨누는 호출에 적용하지 않는다. 그 세션에서 어느 머신을 처음 겨누는 `write` · `exec` 호출은 승인을 묻고, 사람이 「이 세션 동안 이 머신 허용」 을 고르면 그 세션의 그 머신에 한해 다시 묻지 않는다. 대상이 미신뢰 체크아웃이면 세션 허용과 상관없이 매번 묻는다 — 미신뢰에서도 git 쓰기가 되는 근거는 「사람이 누른 것」 이고(결정 D43) 에이전트의 호출에서는 승인이 그 자리를 맡는다. `dangerous` 는 지금처럼 매번이다. 대안: 매번 승인(쓰임 1 의 되풀이마다 사람이 누른다) · 로컬과 같은 규칙(`auto_approve` 까지 — 승인 없이 다른 머신에서 코드가 도는 길이 열린다).
- **쓰임 1 을 에이전트가 하면**: 로컬에서 커밋 → `checkout_send` → 대상 체크아웃으로 `run_start` → `run_logs`. CLI 로는 `pitwall tool checkout_send …`, `pitwall tool run_start --checkout … …` 이다.
- **감사 로그**는 호출을 받은 쪽에 남고 인자 요약에 대상 체크아웃이 든다 (제안).

## 8. 만드는 쪽에 맡기는 것

- 묶음을 어디에 어떤 꼴로 저장하나 — 로컬 Host 의 레지스트리 표를 넓힐지 Desktop 전용 저장소를 둘지. 지금 프로젝트 상태(`project.state.*`)를 묶음 단위로 옮기는 방법과 기존 프로젝트의 이전.
- 화면 코드가 체크아웃마다 Host 연결을 고르는 구조. 지금은 창이 연결 하나를 쓴다(`apps/desktop/src/rpc/host.tsx` 의 `useHost`).
- 보내기의 RPC 꼴(묶음 파일을 만드는 쪽 · 받는 쪽의 스트림 메서드), 전용 ref 의 이름과 치우는 때, 「대상이 이미 가진 커밋」 을 아는 방법.
- 「같은 저장소」 판정의 정확한 방법(얕은 클론 등 예외 포함).
- 머신 연결 상태를 가볍게 확인하는 방법과 주기.
- 탭 · 타이틀바 · 상태바의 머신 표지 모양, 체크아웃 목록의 키 조작.
- Desktop 여럿이 같은 Relay 에 붙어 있을 때 승인 요청 · 원격의 열기 요청이 어느 Desktop 으로 가는가. 이 설계가 만든 문제가 아니라 `08-remote-mobile.md` 가 「연결된 Desktop」 이라고만 적어 둔 자리다 — M7 작업 분할에서 정한다.
- 옛 모델의 말(「원격 프로젝트」)을 쓰는 코드 주석 — `pw_core::registry` 의 `LOCAL_HOST`, `crates/pw-core/src/registry/state.rs` 머리 주석, `apps/desktop/src/tasks/tasks.tsx` 의 작업 표 주석. 무엇으로 고칠지는 묶음의 저장 꼴에 달려 있어 그것을 정하는 작업이 함께 고친다.
- 작업 분할과 순서 — M7 작업 분할 문서에서.

## 9. 딛고 서는 것 (아직 없다)

이 설계는 M7 의 다른 부분과 그 앞 마일스톤이 만드는 것 위에 선다: 머신 사이 연결(`pw-link`)과 Relay 데몬(`pw-relay` · `apps/relay`), MCP 의 `write` 이상 승인 경로(M5 — 지금은 거절한다), 실행 구성과 실행 로그(M6 — 지금 `pw-run` 에는 터미널만 있다), 끊겨도 유지되는 실행 · 터미널과 그 목록(F9-7). 작업 분할은 이것들을 선행으로 놓는다.
