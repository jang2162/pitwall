# 01. 제품 정의

## 1. 배경

- 기존: IntelliJ 중심 개발 → 최근: Orca + 에이전트 중심 개발로 이동, IntelliJ 사용량 감소
- 그러나 IntelliJ를 버리기 어려운 이유:
  - DB 조회 (DataGrip 기능)
  - Git 관리 (그래프, 필터링, 병합, 커밋, 라인별 이력)
  - 실행 · 디버깅 환경 (Run Configuration, 브레이크포인트)
  - 인덱싱 · 쾌적한 LSP (정의 이동, 참조 찾기, 심볼 검색)
- 이 기능들은 각각 별도 앱(DataGrip, Fork/GitKraken, VS Code 등)으로 쪼개면 **프로젝트 컨텍스트가 흩어진다.**

## 2. 목표

**"프로젝트 하나를 열면, 그 프로젝트의 깃 · DB · 실행 · 코드 탐색이 한 창에 모여 있는 가벼운 앱"**

1. IntelliJ 대비 빠른 기동(목표: 콜드 스타트 < 1.5s, 유휴 메모리 < 300MB, LSP 제외)
2. 프로젝트 단위의 완전한 컨텍스트 분리
3. 에이전트(MCP)가 프로젝트 설정(실행 구성, DB 연결 등)을 대신 구성 가능
4. 다른 도구(Orca, Zed, IntelliJ, VS Code)로 즉시 전환 가능 — **대체가 아니라 허브**
5. 멀티 OS 지원, **macOS 우선** (macOS를 1급 플랫폼으로 개발 · QA)
6. 확장 가능: 테마, UI 언어, 코드 언어, 플러그인
7. 원격 머신(Relay 설치)과 모바일(확인 · 간단 조작)까지 같은 프로젝트 컨텍스트로 연결

## 3. 비목표 (IntelliJ에서 뺄 것)

| 제외 | 이유 |
|---|---|
| 고급 리팩터링 (rename across project, extract method 등) | 에이전트가 담당. LSP가 제공하는 rename 정도만 지원 |
| 코드 생성 · 템플릿 · 라이브 템플릿 | 에이전트가 담당 |
| 프레임워크별 전용 지원 (Spring 빈 그래프 등) | 범용성 우선. 필요 시 플러그인 단계에서 검토 |
| 플러그인 마켓플레이스 | 공개 레지스트리는 v2 이후. 단, 확장 구조(테마 · 언어 · 플러그인)는 처음부터 설계 (07-extensibility) |
| 빌드 시스템 자체 구현 (Gradle 모델 임포트 등) | 외부 빌드 툴 호출 + 태스크 자동 감지로 대체 |
| 무거운 자체 인덱서 (PSI) | LSP + tree-sitter 경량 인덱스로 대체 |

## 4. 핵심 원칙

1. **Viewer-first, light editing** — 읽기 · 탐색 · 비교가 1급, 편집은 "작은 수정" 수준이면 충분
2. **Headless core** — 모든 기능은 UI 없이 API로 호출 가능해야 한다 (MCP · 원격 · 테스트를 위해)
3. **파일 기반 설정** — 프로젝트 설정은 `.pitwall/` 아래 사람이/에이전트가 읽고 고칠 수 있는 텍스트(TOML)로
4. **비밀은 파일에 두지 않는다** — 비밀번호 · 토큰은 OS 키체인
5. **외부 도구 존중** — git은 사용자의 git 설정(훅, 서명, credential helper)을 그대로 따르고, 빌드는 프로젝트의 툴을 그대로 호출

## 5. 주요 사용 시나리오

### S1. 파일로 진입
1. Finder/탐색기/터미널에서 `foo/src/main.rs`를 Pitwall로 연다 (`pitwall foo/src/main.rs`)
2. 등록된 프로젝트 중 해당 경로를 포함하는 프로젝트가 있으면 → 그 프로젝트 창을 열고 파일 표시
3. 없으면 상단 커맨드 팔레트가 열리며 "프로젝트 찾기" 상태:
   - 후보: 상위 폴더 중 VCS 루트(`.git`), 빌드 파일(`package.json`, `Cargo.toml`, `build.gradle`...)이 있는 폴더를 추천
   - 선택 또는 폴더 직접 선택 → 프로젝트 생성 + 자동 감지(언어, 실행 태스크, DB 설정 파일)

### S2. 에이전트 작업 후 리뷰
1. Orca에서 에이전트가 작업 → Pitwall Git 탭에서 변경 파일 diff 확인
2. 부분 스테이징 → 커밋 → 그래프에서 브랜치 확인 → 머지

### S3. 버그 재현
1. 실행 구성 선택 → 디버그 실행 → 브레이크포인트에서 변수 확인
2. DB 탭에서 관련 테이블 조회
3. 해당 라인의 git blame으로 언제/누가/어떤 커밋에서 바뀌었는지 확인

### S4. 에이전트가 프로젝트 설정
1. 에이전트: "이 프로젝트 dev 서버 실행 구성과 로컬 Postgres 연결 추가해줘"
2. MCP로 `run_config.upsert`, `db.connection.upsert` 호출 → UI에 승인 요청 → 반영

### S5. 원격 서버의 프로젝트
1. 원격 머신에 Pitwall Relay 설치 (한 줄 설치 또는 Desktop에서 "SSH로 설치") → QR/코드로 페어링
2. Relay가 노출한 경로를 프로젝트로 등록
3. 파일 트리 · git · LSP · 실행이 원격에서 동작, UI는 로컬. 연결이 끊겨도 원격 프로세스는 유지

### S6. 자리를 비운 동안 (모바일)
1. 에이전트가 장시간 작업 중 → 실행 구성 추가를 MCP로 요청
2. 휴대폰에 승인 알림 → diff 확인 후 승인
3. 빌드 실패 알림 → 로그 확인, 재시작
