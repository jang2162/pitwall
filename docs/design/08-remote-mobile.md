# 08. 원격 & 모바일 연동

## 1. 개요

- **원격**: 원격 머신에 **Pitwall Relay**를 설치해서 연결한다. 연결은 **직접 연결(LAN · Tailscale)**만 사용하고, SSH는 Relay 설치 보조와 대체 연결 수단으로 쓴다 — 만드는 순서는 SSH 연결이 먼저다(18-m7-plan 결정 M7-D1 · 06-roadmap.md D73). 둘 다 있으면 직접 연결을 먼저 시도한다
- **모바일**: **보류 (D13)** — 6절은 향후 검토용 초안. 연결 계층(`pw-link`)과 role 구조만 모바일을 고려해 유지
- 원격 설치 · 재연결 방식은 **Zed 원격 개발 구조**를 참고 (UI 로컬 / 헤드리스 서버 원격, 버전 일치 서버 자동 설치, 데몬 재사용)
- **중계 서버(Relay Hub)는 만들지 않는다.** NAT · 방화벽 문제는 Tailscale에 맡긴다. 단, 전송 계층을 추상화해 두어 필요해지면 Hub를 나중에 추가할 수 있게 한다
- **원격 머신의 체크아웃은 따로 된 프로젝트가 아니다.** 같은 저장소의 로컬 · 원격 체크아웃은 한 프로젝트로 묶이고, 프로젝트 창 안에서 워크트리를 고르듯 고른다 — 「프로젝트와 체크아웃 (D57)」 절

## 2. 구성 요소

| 구성 요소 | 설치 위치 | 역할 |
|---|---|---|
| **Pitwall Desktop** | 개발자 PC | 메인 UI. 내부에 Local Host + 내장 Relay 엔드포인트(모바일 접속용) |
| **Pitwall Relay** (`pitwall-relay`) | 원격 서버 / 개발 VM / 집 PC | Host 코어(fs/git/lsp/dap/run/db)를 데몬으로 실행 + 암호화된 연결 엔드포인트. 사람이 「상주시키기」 를 고르면 launchd · systemd user 로 상주, 아니면 SSH 로 띄운 데몬이 유휴 규칙까지 산다(18-m7-plan 결정 M7-D2 · 06 D74). Windows 원격은 이후 |
| **Pitwall Mobile** | Android (이후 iOS) | 컴패니언 앱 |

## 3. 연결 방식

| 우선순위 | 방식 | 조건 |
|---|---|---|
| 1 | **직접 연결** (QUIC, 기본 포트 7420) | 같은 LAN 또는 **Tailscale** tailnet. 주소는 Tailscale MagicDNS 이름 / IP / mDNS(LAN) |
| 2 | **SSH 터널** | Relay를 데몬으로 둘 수 없거나 직접 연결이 막힌 환경 — `ssh host pitwall-relay --stdio` |

- **Tailscale 연동 (D)**
  - Relay는 기본적으로 **Tailscale 인터페이스와 LAN에만 바인드** (공인 IP에 열지 않음)
  - Desktop/Mobile은 tailnet 기기 목록(로컬 Tailscale API)에서 Relay가 떠 있는 기기를 자동 검색
  - Tailscale이 없는 환경은 LAN(mDNS) 또는 SSH로 동작
- Tailscale이 이미 WireGuard로 암호화하지만, **Pitwall 자체 인증(Noise + 기기 키)도 항상 적용** → tailnet의 다른 기기라도 페어링하지 않으면 접근 불가
- 전송 위 프로토콜은 03-architecture의 JSON-RPC 그대로 → UI/MCP 입장에서는 로컬과 원격이 같다
- `pw-link`의 전송은 `Transport` trait으로 추상화 (`Quic`, `Ssh`, 추후 `Hub`)

## 4. 설치 & 페어링

### Relay 설치

**방법 A. 원격에서 직접 설치** — `curl -fsSL https://.../install.sh | sh` (또는 Homebrew/apt/단일 바이너리) → 서비스 등록(v1.0 전 — 18-m7-plan 「3」. M7 에서는 릴리스 바이너리를 아래 경로 · 이름 규칙으로 직접 배치하고 `pitwall-relay pair` 코드로 페어링한다)

**방법 B. Desktop에서 SSH로 설치 (Zed 방식)**
1. 시스템 `ssh` 바이너리 사용 (사용자의 `~/.ssh/config`, 에이전트, ProxyJump, ControlMaster를 그대로 존중). 비밀번호는 설정에 저장하지 않고 키 인증 권장, 프롬프트는 GUI askpass로 처리. 처음 보는 호스트 키는 ssh 의 확인이 askpass 로 창에 간다 — 그 질문은 `SSH_ASKPASS_PROMPT` 힌트 없이 오고 `yes`(또는 지문)를 돌려야 받는다(빈 답 · `no` 는 거절). 확인을 끄는 옵션(`StrictHostKeyChecking=no` · `UserKnownHostsFile=/dev/null` 등)은 Pitwall 이 넘기지 않으며 사람의 `ssh_args` 에 있으면 흔한 꼴은 거절한다(사람의 `~/.ssh/config` · `-F` 로 준 설정 파일은 ssh 가 그대로 따른다). 바뀐 호스트 키는 ssh 의 거절 원문을 보인다(18-m7-plan M7-06 · M7-P17 — 구현 `pw_link::ssh`)
2. 원격 OS/아키텍처 감지 (`uname -sm`)
3. `~/.local/share/pitwall/relay/pitwall-relay-{channel}-{version}` 존재 여부 확인 (원격의 `$XDG_DATA_HOME` 존중) — **Desktop 버전과 정확히 일치**해야 함. 자리는 원격 셸이 Relay 와 같은 순서로 푼다(`PITWALL_DATA_DIR` → `$XDG_DATA_HOME/pitwall` → `$HOME/.local/share/pitwall`, 그 아래 `relay/`). 있어도 해시가 매니페스트와 다르면 다시 올린다
4. 없으면 설치:
   - 기본: Desktop 이 받아(서명 매니페스트로 검증, `$CACHE/relay-dist/`) SSH 로 올린다. 개발 빌드(debug)는 그 빌드 결과를 올린다(18-m7-plan 결정 M7-D5 · 06 D77). 릴리스 자산은 `pitwall-relay-<판>-<플랫폼>`(`linux-x86_64` · `linux-aarch64` musl 정적, `macos-aarch64` · `macos-x86_64`)과 `relay-manifest.json`(이름 · sha256 · 크기를 (OS, 아키텍처)마다) · 그 `.sig`(updater 운영 키, 서명에 판이 실린다)다. Desktop 은 앱의 updater 공개키로 서명 · 판을 본 뒤 그 (OS, 아키텍처)의 해시와 같은 바이너리만 올린다(`pw_release::relay` — 18-m7-plan M7-05). 개발 빌드 갈래(`mise run relay-build` 의 `target/relay-dist/`)는 debug 빌드에만 있다
   - 올리기: 같은 폴더의 임시 이름(`<이름>.part.<pid>`)에 쓰고 원격에서 해시를 다시 본 뒤(`sha256sum` · `shasum -a 256`, 둘 다 없으면 올린 바이너리의 `--verify`)에만 0700 · rename. 올릴 바이트는 한 번 읽어 해시와 전송에 함께 쓴다(구현 `pw_link::install`)
   - 수동: 릴리스 바이너리를 위 경로 · 이름 규칙으로 직접 배치
   - 페어링: SSH 로 붙을 때마다 `pitwall-relay pair --from-ssh <Desktop 공개키>` 로 그 Desktop 키를 페어링 표에 `owner` 로(없을 때만) 넣고 머신 id 를 받는다 — 데몬 소켓 명령이 아니라 페어링 표 파일에 잠금(`pairings.lock`)을 쥐고 직접 쓴다. 해제는 `pitwall-relay unpair <기기 id>`(18-m7-plan M7-06 ⑧ ⑨)
5. 상주 서비스 등록(systemd user / launchd) 또는 SSH 세션 기반 데몬으로 기동
6. 오래된 버전 바이너리 정리 (최근 2개 유지) — 이 Desktop 의 판과, 나머지 가운데 판(semver)이 가장 높은 하나를 남긴다. 원격 `$DATA/relay/` 의 `pitwall-relay-*` 만 보고(같은 폴더의 `state.db` · `device.key` · `pairings.json` 은 건드리지 않는다), 판을 읽을 수 없는 이름은 지우지 않는다. **떠 있는 데몬의 바이너리는 지우지 않는다** — 지우기 직전 원격 셸이 그 바이너리의 `status` 를 불러 데몬이 없는 것이 확실할 때(종료 3 — 소켓이 없거나 받는 쪽이 없다)만 지운다. 답이 없으면(4 — 증명 전 연결 상한 · 바쁨 · 5초 시간 초과) 남긴다. 셸이 끝난 올리기 임시 파일(`.part.<pid>`)도 지운다(18-m7-plan M7-07 ③ — 구현 `pw_link::upgrade`)

### 연결 · 재연결 (프록시 모드)
- 연결할 때마다 `pitwall-relay proxy`를 실행 → 데몬이 없으면 띄우고, 있으면 기존 데몬에 붙음
- 데몬은 (채널, 판)마다 따로다 — 소켓 `$STATE/relay/<채널>-<판>.sock`(구현 `pw_relay::socket::endpoint`), 바이너리 `pitwall-relay-{channel}-{version}`, 핸드셰이크도 판 · 채널을 견준다. Desktop 이 새 판이면 새 판을 깔고 새 판 데몬이 따로 뜬다 — **옛 판 데몬에 붙지 않고 끝내지도 않는다**(18-m7-plan 결정 M7-D6 ①)
- 옛 판 데몬은 링크 · 실행 · 터미널이 모두 없어지면 유휴 규칙으로 스스로 끝난다. 그동안 Desktop 은 옛 판 바이너리의 `pitwall-relay status`(판에 묶이지 않는 최소 질의 — JSON 한 줄, 칸은 덧붙이기만 한다. 종료 코드 0 답 · 3 데몬이 없는 것이 확실함 · 4 답 없음)로 남은 실행 · 터미널 · 붙은 링크 수를 읽어 「옛 판 Relay 에 n개 남음」 과 [옛 판 끝내기] 를 보인다. 끝내기는 사람이 본 그 데몬(pid · 실행 · 터미널 · 링크 수)이 그대로일 때만 — 답하지 않는 데몬에는 보내지 않는다 — SIGTERM 을 보내고 — 그사이 바뀌었으면 보내지 않고 새 수를 다시 보인다 — 실행 트리 끝내기는 그 데몬이 한다. 옛 판의 실행은 새 Desktop 에서 보이지 않는다(18-m7-plan M7-07 ② — 구현 `pw_link::upgrade`). **붙을 때마다 한 번** 조사 → (`~/.local/bin/pitwall` 이 Pitwall 이 둔 링크 — 대상이 정확히 `$DATA/relay/pitwall-relay-<채널>-<판>` — 이고 옛 판을 가리키면 이 판으로 옮김. 사람이 손으로 둔 다른 링크는 건드리지 않는다. 옮기지 못하면 그 판은 이번 정리에서 남김) → 정리가 돈다. 조사 · 정리 · 끝내기 · 링크 바꾸기는 링크와 따로 된 ssh 라, 각 원격 스크립트는 먼저 이 판 Relay 의 머신 id(`pitwall-relay machine` — 기기 키 지문)가 링크가 증명한 머신 id 와 같은지 보고 다르면 아무것도 하지 않는다(Desktop 은 「다른 머신」 으로 알린다 — 원격이 말한 id 는 같은지 확인에만 쓴다). 결과는 그 링크의 증명된 머신 id 와 함께 원격 호스트 화면의 그 호스트 줄에 보이고(`remote.relays` · 이벤트 `remote.relays`), [옛 판 끝내기](`remote.stopOld`)는 그 호스트가 지금 그 머신에 붙어 있고 보인 값(pid · 실행 · 터미널 · 링크 수)이 그대로일 때만 끝낸다. 다른 Desktop 이 그 옛 판에 붙어 있으면 그 수와 「그 연결도 끊긴다」 를 보인다. `pitwall` 명령 링크는 같은 줄의 칸에서 사람이 고를 때만 둔다(`remote.linkCommand` — 18-m7-plan M7-07b)
- Tailscale/LAN 직접 연결(QUIC)이 가능하면 데이터 경로는 직접 연결, 불가하면 SSH 채널 위로 그대로 운영

### 페어링 (직접 연결용)
1. `pitwall-relay pair [--role owner|mobile|readonly] [--name <이름>]` → 터미널에 **6자리 코드** 표시 (SSH로 설치한 경우 Desktop이 SSH 채널로 자동 페어링). 붙은 owner Desktop 의 기기 칸에서 [코드 띄우기] 로도 만든다(`relay.pairCode`). QR 은 아직 없다(터미널 QR 렌더러 의존이 든다 — 18-m7-plan M7-23 보고)
2. 새 기기에서 코드 입력 → 페어링 완료. 입력 화면은 직접 연결 주소와 함께 M7-24 다(프로토콜은 `pw_link::pair_with_code`). Relay 가 코드를 받는 직접 연결 받기도 M7-24 다 — 그 전에 만든 코드는 쓰이지 않고 5분 뒤 끝난다(기기 칸은 만료 때 화면에서 지운다)
- 코드는 Relay 에 하나만 대기한다(`$DATA/relay/pairing-code.json`, 0600 — 새 코드를 만들면 앞 코드는 끝난다). **5분 만료 · 틀린 시도 세 번이면 끝 · 한 번 쓰면 끝**이고, 시도는 연결마다가 아니라 그 코드에 대해 Relay 전체에서 센다(데몬이 다시 떠도 이어진다). 시도는 Relay 가 답을 보내기 전에 센다
- 코드 페어링은 **Noise XX 세션 위에서만** 받는다(데몬 소켓 · SSH 링크의 `pair` 첫 틀은 거절). 코드는 PAKE(SPAKE2)의 암호로만 쓰고 그 대본과 두 방향 키 확인을 Noise 핸드셰이크 해시에 묶는다 — 처음 붙는 능동 중간자가 받은 값으로 코드를 오프라인 대입하거나, 코드 교환을 다른 세션으로 옮겨 자기 키를 넣지 못한다. 페어링되는 키는 그 Noise 세션이 증명한 키이고 role 은 코드를 만든 사람이 고른 것이다(구현 `pw_link::pair` · `pw_relay::codes`)
- 코드는 로그 · 감사 · 에이전트가 읽는 글에 남지 않는다(사람에게 보이는 터미널 · 기기 칸에만)
- 대가: 시도를 코드 단위 · Relay 전체에서 세므로, 직접 연결 포트에 닿는 누구든 아무 값으로 세 번 붙으면 대기 코드가 끝난다(페어링 DoS — 무차별 대입을 막는 설계의 대가). 사람은 새 코드를 띄운다. 완화는 주소별 증명 전 자리 상한(18-m7-plan M7-24)이다

### 보안 모델
- **SSH 로 붙은 링크도 Desktop 기기 키를 증명한다** — 원격 머신의 같은 사용자 프로세스가 데몬 소켓으로 Desktop 행세를 하지 못하게(18-m7-plan M7-02 · 결정 M7-D13). Desktop 도 Relay 의 기기 키로 머신 id 를 확인한다(M7-P6). 같은 uid 로 Relay 의 데이터 폴더에 쓸 수 있는 프로세스는 이 증명으로 막지 못한다
- 기기마다 Ed25519 키쌍 생성, 페어링 시 공개키 교환 (TOFU + 짧은 코드로 확인)
- 세션 암호화/인증: **Noise 프로토콜(XX 패턴)** — 직접 연결(QUIC — M7-24)의 것이다. 정적 키는 같은 기기 Ed25519 키를 X25519 로 바꾼 것이고, 그 위 링크 프로토콜(판 · 도전 서명 · role)은 SSH 링크와 같다. 안쪽 `hello` 의 기기 키가 Noise 상대 정적 키와 같아야 받는다 — 털린 Relay 가 다른 Relay 의 핸드셰이크를 중계해 틀을 끼워 넣지 못한다(구현 `pw_link::noise`). SSH 링크는 Noise 를 쓰지 않는다(ssh 가 암호화 · 호스트 인증을 하고 기기 키는 도전 서명으로 증명한다)
- Relay는 페어링된 기기 목록과 **기기별 권한 범위(role)**를 보유
  - `owner`(Desktop): 전체
  - `mobile`: 조회 + 허용된 조작만 (6절)
  - `readonly`: 조회만
- 기기 해제(revoke) 즉시 반영 — 그 기기의 열린 링크(SSH 링크 포함) · 구독 · 터미널 붙기와, 전송을 잃고 멈춘 링크의 이어 붙기 토큰까지 곧바로 끊긴다. 해제된 기기는 이어 붙기로도 새로 붙기로도 돌아오지 못한다. 페어링 코드는 5분 만료
- 기기 보기 · 해제 · 코드 띄우기(`relay.devices` · `relay.unpair` · `relay.pairCode`)는 **기기 키를 증명한 owner 링크의 RPC** 만 한다 — `mobile` · `readonly` 기기는 다른 기기를 페어링 · 해제하지 못한다. 데몬 소켓의 좁은 명령(`open` · `askpass` · `status`)으로는 표를 바꾸지 못한다. Desktop 의 웰컴 「원격 호스트」 탭이 붙은 호스트마다 그 표를 보인다(`remote.devices` 등 — 붙은 그 머신일 때만 중계, role 은 Relay 가 판정). 마지막 owner 기기를 스스로 해제하면 다시 닿는 길이 SSH 재페어링뿐이라는 경고를 보인다(막지 않는다)
- **같은 uid 의 대가**(결정 M7-D13): 같은 사용자로 Relay 의 데이터 폴더(`$DATA/relay/`)를 읽고 쓸 수 있는 프로세스는 이 모든 것을 비켜 간다 — 페어링 표에 자기 키를 직접 넣고, 대기 코드 파일의 평문 코드(PAKE 는 양쪽이 같은 암호를 쥐어야 한다)를 읽는다. 그 프로세스는 이미 그 사용자의 셸 권한이다. 막는 것은 소켓만 열 수 있는 프로세스와 네트워크 너머의 상대다
- Relay가 노출하는 프로젝트 경로는 화이트리스트 (`relay.toml`의 `roots`)
- **포트 포워딩**(18-m7-plan M7-22): 방향은 Desktop → 원격 하나다 — Desktop 의 루프백 포트로 들어온 연결을 owner 링크의 채널로 Relay 에 보내고 Relay 가 그 머신의 루프백(`localhost` · `127.0.0.1` · `::1`)으로 잇는다. Relay 는 Desktop 쪽으로 포워딩을 열 수 없고(링크 규칙 위반으로 끊긴다), 원격을 거쳐 다른 호스트로 가지 않으며, `readonly` · `mobile` 기기 · MCP 툴로는 만들 수 없다. Desktop 쪽은 루프백에만 듣지만(결정 M7-D12) **이 컴퓨터의 다른 프로세스(같은 uid 든 아니든)는 그 루프백 포트에 붙어 원격 개발 서버 · 디버그 포트에 닿을 수 있다** — 루프백만으로 받아들인 대가다. 브라우저의 쿠키는 포트를 가르지 않으므로 포워딩한 원격 페이지는 이 컴퓨터의 다른 `localhost` 서비스와 쿠키를 함께 본다 원격 쪽 대상을 정하는 것은 원격 머신(신뢰한 Relay)이다 — Relay 가 털렸으면 그 머신에서 어디로든 이을 수 있고 청한 대상을 그대로 되돌려 말할 수도 있다(원격 쪽은 그 머신의 신뢰 경계다). Desktop 이 지키는 것은 듣는 쪽이 이 컴퓨터의 루프백뿐이고 포워딩 설정이 전역 설정에서만 온다는 것이다. `accepted` 의 대상 비교는 버그 · 판 어긋남을 잡는 확인이지 보호가 아니다. 듣는 소켓은 `SO_REUSEADDR` 없이 연다 — macOS 에서 켜면 이 컴퓨터의 다른 프로그램이 `0.0.0.0` · `::` 로 쥔 포트 위 루프백에 바인드돼 그 서버를 가린다

### 원격 호스트 등록 예 (Desktop 쪽)

```toml
# ~/.config/pitwall/settings.toml
[[remote_hosts]]
nickname = "build-server"
host = "build.tail1234.ts.net"     # Tailscale MagicDNS 또는 ~/.ssh/config 호스트명
username = "dev"                   # 기본: 로컬 사용자명
port = 22
ssh_args = ["-o", "ServerAliveInterval=30"]

[[remote_hosts.port_forwards]]
local_port = 8080
remote_port = 8080

[[remote_hosts.port_forwards]]
local_port = 5005                  # 원격 JVM 디버그 포트
remote_port = 5005
remote_host = "localhost"          # 그 머신의 루프백만(localhost · 127.0.0.1 · ::1) — Docker 는 컨테이너 포트를 그 머신 localhost 에 publish 해서 쓴다(18-m7-plan M7-P15)
local_host = "127.0.0.1"           # 루프백(127.0.0.1 · ::1)만 받는다 — 다른 값은 그 포워딩을 열지 않고 경고(18-m7-plan 결정 M7-D12)
```

원격 호스트 설정에는 프로젝트 경로를 적지 않는다. 그 머신의 어느 폴더가 어느 프로젝트의 체크아웃인지는 묶음이 기억한다(「프로젝트와 체크아웃 (D57)」 절).

### Relay 설정 예 (원격 쪽)

```toml
# ~/.config/pitwall/relay/relay.toml
schema = 1
name = "build-server"
roots = ["~/work"]                 # 이 아래만 프로젝트로 노출
[listen]
port = 7420
interfaces = ["tailscale", "lan"]  # 기본값. "all"은 명시적으로만
[idle]
exit_after = "30m"                 # 링크 · 실행 · 터미널이 없으면 이만큼 뒤 데몬이 끝난다
stop_lsp_after = "30m"
```

`roots` 가 없으면 아무것도 등록하지 않는다. `relay.toml`(`$CONFIG/relay/relay.toml`)은 그 머신의 사람이 쓰거나, 처음 「체크아웃 추가」 때 Desktop 이 사람에게 물어 SSH 로 쓴다 — RPC 로는 쓰지 않는다. `[idle] exit_after`(기본 30분)(18-m7-plan M7-04 · M7-06). 지금 읽는 키는 `schema` · `name` · `roots` · `[idle]` 이다 — 모르는 키 · 틀린 값이면 데몬이 뜨지 않는다. `[listen]` 은 M7-24 가 더할 때까지 경고만 남기고 무시한다(네트워크로 받지 않는다). `roots` 를 좁히면 이미 등록된 밖의 프로젝트는 지우지 않고 숨긴다 — 목록 · 열기 · 경로 풀기에 나오지 않고, 데몬이 시작할 때 그 수와 루트를 경고로 남긴다. `roots` 를 다시 넓히면 보인다(18-m7-plan M7-12).

## 5. 원격 기능 범위

| 기능 | 원격 동작 |
|---|---|
| 파일 트리 · 에디터 · 검색 | Relay에서 처리, 파일 내용은 요청 시 전송 + 로컬 캐시 |
| Git | Relay에서 처리 (그래프 데이터는 스트리밍) |
| LSP · 인덱스 | Relay에서 언어 서버 실행 |
| 런타임 환경 | Relay의 `runtime` 모듈이 원격 머신의 mise/셸 환경으로 해석 (F14-7) |
| 실행 · 디버그 | Relay에서 프로세스 실행, DAP 중계, **포트 포워딩**(원격 웹서버 포트 → 로컬 루프백 — 사람의 브라우저 · 도구용. 디버그 attach 는 원격 Host 에서 붙는다, 18-m7-plan M7-22 ⑥) |
| 터미널 | Relay의 PTY |
| DB | Relay에서 직접 연결 (내부망 DB 접근에 유리) |
| MCP | 원격 머신의 에이전트도 Relay의 로컬 MCP 엔드포인트 사용 → 승인 요청은 연결된 Desktop으로 전달. 그 세션은 그 머신의 체크아웃만 다룬다(05-mcp.md 「체크아웃」). 원격 에이전트는 `pitwall-relay mcp` 로 붙는다(18-m7-plan M7-P12 — 사람이 고른 `pitwall` 링크면 `pitwall mcp`). 붙은 owner Desktop 이 없는 동안 `write` 이상은 거절(M7-D10). Streamable HTTP 는 그 머신 `$CONFIG/relay/settings.toml` 의 `[mcp.http]` 를 손으로 켤 때만 루프백에 듣는다(Desktop 화면 없음 — 18-m7-plan M7-25, 05-mcp.md 「전송 방식」) |
| 커밋 보내기 · 가져오기 | 한 머신의 체크아웃에 있는 브랜치를 다른 머신의 체크아웃으로 origin 을 거치지 않고 옮긴다(「프로젝트와 체크아웃 (D57)」 의 「커밋 보내기 · 가져오기」) |
| 세션 유지 | Relay가 상주하므로 연결이 끊겨도 실행 중 프로세스 · 로그 유지, 재접속 시 이어보기. 사람이 탭 · 창을 닫을 때는 원격의 것에 [끝내기] · [두고 닫기] 를 묻는다 |
| 미저장 편집 | **Desktop 웹뷰에 창이 사는 동안 보관** (연결 끊김에도 유실 없음 — 앱 종료는 지금처럼 미저장 확인, 18-m7-plan 결정 M7-D8), 재접속 시 복원 · 원격 파일이 그사이 바뀌었으면 diff로 충돌 해결 |
| 원격 터미널에서 `pitwall <file>` | 원격 Relay가 연결된 Desktop에 "파일 열기" 이벤트 전달 (Zed가 지원하지 못하는 부분 — 에이전트가 원격에서 작업할 때 유용). 그 프로젝트의 창에서 활성 체크아웃을 바꾸지 않고 그 체크아웃의 탭으로 연다(18-m7-plan M7-11b — `apps/desktop/src/layout/worktree-session.ts`). 행선지는 붙은 owner Desktop 가운데 마지막으로 사람 입력이 있던 것 하나 — Relay 는 요청마다 듣는 Desktop(`open.listen`, owner 링크의 Host 범위 연결만)에 「입력 뒤 지난 시간」 만 묻고, Desktop 은 창 목록을 보내지 않는다. 그 Desktop 에 묶음 창이 없으면 앞으로 가져오지 않고 연다. 듣는 Desktop 이 없으면 거절하고 원격에 까닭을 찍는다(구현 `pw_core::open::desks` · `pw_relay::narrow` · `apps/desktop/src-tauri/src/remote_open.rs`, 18-m7-plan M7-15) |

### 로컬 / 원격 역할 분담 (Zed와 동일 원칙)

| Desktop (로컬) | Relay (원격) |
|---|---|
| UI, 테마, 키맵, 레이아웃 | 소스 코드, 파일 감시 |
| tree-sitter 하이라이트(열린 파일) | LSP, 심볼 인덱스, 텍스트 검색 |
| 미저장 편집, 최근 프로젝트 | git, 실행 · 디버그, 터미널, DB 연결 |
| 비밀(키체인) — 필요한 것만 세션 동안 전달 | 프로젝트 설정(`.pitwall/`) |

### 설정 위치
- **로컬 설정**: UI 관련 (폰트, 테마)
- **Relay 설정**: 서버 영향 (`relay.toml` — LSP 경로, 프록시, roots)
- **프로젝트 설정**: `.pitwall/` — Desktop과 Relay 양쪽이 읽음

### 제약
- 파일 10만 개 이상인 루트(`~`, `/`)는 성능 저하 → 프로젝트 폴더 단위로 열도록 유도 (F9-10)
- 지원 원격 플랫폼: Linux x64/arm64(musl 정적), macOS. 32bit 미지원, Windows 원격은 이후

## 5-1. 프로젝트와 체크아웃 (D57)

같은 저장소를 로컬과 원격 머신 양쪽에 두고 쓴다 — 로컬에서 코드를 쓰고 원격에서 테스트하거나, 밖에서 원격 머신에 붙어 작업한다. 그 둘을 프로젝트 둘로 가르지 않고 **프로젝트 하나 안에서 워크트리를 고르듯 고른다.** 판단의 경과와 고르지 않은 길은 `docs/superpowers/specs/2026-11-13-remote-checkouts-design.md`(그때의 기록)에 있다.

| 말 | 뜻 |
|---|---|
| 머신 | Host 하나. 이 Mac(로컬 Host) 또는 Relay 가 도는 원격 머신 |
| 체크아웃 | (머신, 워크트리) 한 쌍. 메인 체크아웃도 워크트리의 하나로 센다. 「활성 워크트리」(04-features.md 「워크트리 경로 처리 (F2-5)」)를 머신까지 넓힌 것이다 |
| 멤버 프로젝트 | 어느 한 머신의 레지스트리에 등록된 프로젝트 |
| 묶음 | 한 저장소의 체크아웃들을 가진 멤버 프로젝트들의 모음. 사람에게는 이것이 「프로젝트」 다 |

「환경」 이라고 부르지 않는다 — 런타임 환경(03-architecture.md 「런타임 환경 (D26)」)과 실행 환경(04-features.md 「F7. 실행 환경 & 디버깅」)이 이미 쓰는 말이다.

### 묶음

- **머신마다 프로젝트는 그 머신의 레지스트리에 따로 등록된다**(멤버 프로젝트). Desktop 이 「이 멤버 프로젝트들은 한 저장소의 체크아웃들」 이라는 묶음을 기억하고 묶음을 프로젝트 하나로 보인다. Host 는 다른 머신의 체크아웃을 알지 못한다 — Host 의 정의(03-architecture.md 「전체 구조」)와 RPC 가 그대로다
  - **Why:** 프로젝트 하나가 여러 머신에 걸치게 하면(모든 머신이 같은 프로젝트 id) 두 기기가 같은 원격 체크아웃을 각자 등록할 때 부딪히고, 신뢰 · 레지스트리 · 라우터를 다시 짜야 한다. 밖에서 원격으로 작업한다는 것은 기기가 둘 이상이라는 뜻이다
- 묶음은 Desktop 이 가진다: 목록 정보(이름 · 즐겨찾기 · 태그 · 마지막으로 연 시각)와 멤버 `(머신, 그 머신의 프로젝트)` 목록. 로컬 프로젝트 하나는 멤버가 하나인 묶음이다
- 한 머신에 멤버는 하나다. 그 머신의 다른 워크트리는 멤버 프로젝트의 연결 워크트리로 나온다(F2-5 의 규칙을 그 머신의 Host 가 쓴다). **멤버 프로젝트는 묶음 하나에만 든다**
- 멤버를 더하는 것은 사람이 한다(「체크아웃 추가」 — 머신과 그 머신의 경로, 경로는 Relay 의 `roots` 안). 묶음의 다른 멤버와 공통 커밋이 없으면 넣지 않는다 — 보내기 · 가져오기가 성립하지 않는다. 더하려는 멤버가 멤버 하나뿐인 다른 묶음에 있으면 옮겨 오고, 둘 이상인 묶음에 있으면 거절한다
- 로컬 체크아웃이 없는 묶음(원격만)이 있을 수 있다. 웰컴 창의 원격 호스트에서 머신과 경로를 골라 만든다. 로컬 멤버는 나중에 이미 있는 폴더를 골라 더한다 — 클론은 해 주지 않는다
- 멤버를 빼는 것은 묶음에서만 뺀다. 그 머신의 프로젝트 등록과 파일은 건드리지 않는다

### 창과 활성 체크아웃

화면은 10-ui.md 「체크아웃 고르기 · 머신 표지 (M7)」.

- 프로젝트당 한 창은 그대로다. 창은 묶음 하나를 본다 — 창 label 은 `project-<묶음 id>` 이고, 암묵 묶음이던 때 연 `project-<로컬 프로젝트 id>` 창이 남아 있으면 그 묶음이 행을 얻은 뒤에도 그 창을 쓴다(열린 창의 label 은 바꿀 수 없다 — 18-m7-plan M7-11b, `apps/desktop/src-tauri/src/launch.rs` `open_bundle_as`). 원격만인 묶음의 창은 처음 활성 체크아웃이 그 묶음 첫 멤버의 메인 체크아웃이다
- **활성 체크아웃이 창의 기준이다.** 파일 트리 · 검색 · git 화면 · DB 탐색기 · 언어 서버가 그 머신의 그 워크트리를 본다
- **탭은 자기를 연 체크아웃을 기억한다.** 그래서 활성 체크아웃을 바꾸지 않고 다른 체크아웃의 파일 · 터미널 · 실행 로그 · DB 문서 탭이 한 창에 함께 있다. 탭 묶음은 체크아웃별로 Desktop 로컬에 기억한다
- **실행 · 터미널은 대상 체크아웃을 골라 열 수 있다**(기본은 활성 체크아웃). 활성 체크아웃을 바꾸는 것은 탭을 닫고 그 머신의 파일 트리 · 감시 · 언어 서버를 띄우는 일이라, 로컬에서 고치며 원격에서 테스트하는 되풀이에는 무겁다
- **연결은 쓰는 머신만 연다**(D56 — 가벼움). 창은 활성 체크아웃의 머신과 탭이 열린 체크아웃의 머신에만 Host 연결을 둔다. 체크아웃 목록의 연결 상태는 머신 수준의 가벼운 확인으로 보이고, 그것 때문에 프로젝트 연결 · 파일 감시 · 언어 서버를 띄우지 않는다
- **어느 머신인지 늘 보인다.** 헷갈리면 다른 머신에 파괴적 작업을 하는 사고가 난다 — 위험 작업의 확인(06-roadmap.md 결정 D42)은 대상 머신 이름을 문장에 넣는다
- **끊기는 것과 닫는 것은 다르다.** 연결이 끊기면 Relay 가 그 머신의 실행 · 터미널을 유지하고 다시 붙으면 이어 본다. 그 머신의 탭은 읽기 전용 표시와 함께 남고 미저장 편집은 로컬에 보관된다. 다른 머신의 탭은 영향이 없다. 사람이 탭 · 창을 닫는 것은 그 프로세스를 끝내는 일이고(03-architecture.md 「프로세스 · 창 모델」), 원격 머신의 것은 확인에 [두고 닫기] 를 함께 둔다 — 두면 다음에 그 체크아웃을 열 때 이어 본다. 활성 체크아웃을 바꾸는 것은 닫는 것이 아니다

### 커밋 보내기 · 가져오기

**코드는 git 커밋으로만 머신 사이를 건넌다.** 커밋 안 한 변경을 옮기거나 작업 트리를 동기화하지 않는다. 보내기는 활성 체크아웃 → 고른 체크아웃, 가져오기는 그 반대이고 방식은 같다.

- **origin 을 거치지 않는다.** 원본 머신에서 git 으로 묶음 파일(`git bundle` — 대상이 이미 가진 커밋은 뺀다)을 만들어 Pitwall 의 연결로 대상 머신에 보내고, 대상 머신에서 git 으로 받아 Pitwall 전용 ref 에 둔다. 양쪽 다 git CLI 다(결정 D39)
  - **Why:** 쓰고 테스트하기를 덜 된 커밋으로 하루에 여러 번 되풀이한다. origin 을 거치면 그 중간 커밋이 팀에 보이고 CI 가 돈다. origin 에 push 하고 원격에서 pull 하는 길은 git 화면에서 손으로 된다
- 옮기는 것은 원본 체크아웃의 지금 브랜치와 거기까지의 커밋이다. 원본에 커밋 안 한 변경이 있으면 가지 않는다고 알리고 막지는 않는다
- **대상 맞추기**: 대상 저장소에 그 브랜치가 없으면 만들고, 있고 받은 커밋이 그 앞이면(fast-forward) 올린 뒤, 대상 체크아웃을 그 브랜치로 바꾼다
- **git 이 거절하면 덮지 않는다**(결정 D42). 대상 브랜치에 원본에 없는 커밋이 있거나(갈라짐), 대상 작업 트리의 커밋 안 한 변경이 브랜치 전환을 막거나, 그 브랜치를 대상 머신의 다른 워크트리가 쓰고 있으면 아무것도 바꾸지 않고 멈춘다. 받은 커밋은 전용 ref 에 남아 사람이 대상 체크아웃의 git 화면에서 병합하거나 반대 방향으로 가져온다. 강제로 덮는 옵션은 없다
- 대상의 브랜치 ref 를 움직였으면 알림에 이전 해시와 [되돌리기] 를 단다(결정 D42)
- **대상은 보낼 때 고르고 기억한다.** 원본 체크아웃마다 마지막으로 고른 대상이 다음에 먼저 골라져 있다. 로컬 워크트리마다 원격 짝 워크트리를 자동으로 만들지 않는다 — 워크트리를 만들고 지우는 일과 짝의 수명이 딸려 온다
- 대상이 미신뢰 체크아웃이어도 사람이 누른 보내기는 된다(결정 D43). 훅은 대상 머신에서 git 이 하는 대로 돈다
- 대상 체크아웃에서 돌고 있는 실행 · 터미널이 있으면 확인에 보인다. 막지는 않는다
- 원격 ↔ 원격도 Desktop 이 사이에서 이으면 같은 방식이지만 M7 의 완료 기준은 로컬 ↔ 원격이다

### 신뢰 · 설정 · 비밀

- **신뢰는 머신마다다.** 멤버 프로젝트가 그 머신의 레지스트리에 자기 신뢰를 가진다. 원격 체크아웃을 처음 열 때 그 머신 기준으로 한 번 묻는다. 로컬에서 준 신뢰는 원격으로 번지지 않고 그 반대도 같다 — 신뢰는 「이 머신에서 이 프로젝트의 코드를 실행해도 된다」 는 허가다
- 프로젝트 설정(`.pitwall/*.toml`)은 체크아웃마다 그 체크아웃의 파일을 읽는다. `*.local.toml` 과 개인 전용 설정은 그 머신의 것이다
- DB 연결 · 실행 구성은 그 체크아웃의 머신에서 나간다. 같은 연결 정의(`localhost:5432`)가 머신마다 다른 서버를 가리킬 수 있어 연결 표지에 머신 이름을 함께 보인다
- 비밀은 Desktop 키체인에 (머신, 멤버 프로젝트, 연결)마다 둔다. 묶음은 키에 넣지 않는다 — 멤버를 다른 묶음으로 옮겨도 비밀이 따라온다. Relay 로는 세션 동안 필요한 것만 보낸다(결정 D47)
  - 구현(18-m7-plan M7-12): 머신은 링크가 도전 서명으로 증명한 머신 id 다(Relay 가 대는 값이 아니다). Relay 는 비밀을 디스크 · 메모리에 두지 않고, 연결을 열 때마다 붙은 Desktop 에 청한다 — Desktop 이 owner · Host 범위 연결로 연 `secret.requests` 스트림으로 청이 가고 같은 연결의 `secret.answer` 로 답이 온다. 청에는 그 비밀을 부른 창의 요청(창 · 요청 id)이 실리고, Desktop 은 그 요청이 지금 답을 기다리는 중이고 비밀이 필요한 메서드(연결 열기 · 연결 시험 · 탐색 · 쪽 읽기는 읽기, `db.secret.set` 은 두기, `db.secret.clear` · 연결 지우기는 지우기 — 창이 저절로 보내는 읽기는 아니다)이며 청의 연결 · 종류가 그 요청과 맞을 때 한 번만 답한다. 기준은 「그 창이 스스로 보여 주는 그 연결 하나를 위해 연결을 여는 요청」 이다 — 복원된 DDL 문서 · 스키마가 바뀐 뒤 탐색기가 다시 읽는 요청처럼 저절로 나가는 것도 그 연결 하나의 것이면 청을 열고, 여러 연결을 훑는 읽기(표지 · 목록)는 열지 않는다. 에이전트 범위에서 비롯된 흐름은 Relay 가 청하지 않고 Desktop 도 세지 않는다. 받은 비밀은 연결을 여는 드라이버로만 가고 그 DB 세션이 끝나면 함께 버려진다. 「이 머신을 새로 믿기」 는 옛 머신 id 의 키체인 비밀을 지운다

에이전트가 MCP · CLI 로 다른 머신의 체크아웃을 겨누는 규칙은 05-mcp.md 「체크아웃」.
