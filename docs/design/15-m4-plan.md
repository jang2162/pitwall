# 15. M4 (LSP · 편집) 작업 분할

M4 목표: **「코드를 읽고 고치는 데 IDE 를 열 이유를 없앤다」 — 언어 서버(LSP)로 hover · 정의 · 사용처 · 진단 · 아웃라인을 보고, 자동완성 · 시그니처 · rename · 코드 액션 · 포맷 · 멀티 커서로 L2 수준까지 고친다(D7).** 언어 지원은 확장 정의 위의 범용 구조이고(D6 · 07-extensibility.md 「코드 언어 지원」), 기본 번들 넷 — Rust · TypeScript/JavaScript · Python · Java/Kotlin — 이 「따로 찾아 설치하지 않아도 되는」 언어이자 M4 의 시험 기준이다(결정 M4-D1). 언어 서버가 클론한 저장소의 코드를 돌리지 않게 하는 것(신뢰), 서버가 없거나 아직 뜨지 않았을 때도 tree-sitter 심볼 인덱스로 「심볼로 이동」 · 아웃라인이 되는 것이 이 단계의 중심이다.

이 문서는 **초안**이다(2026-11-02). §4 의 「미정 — 사람 확인」 결정 9개가 정해지면 그 결정을 가리키는 행을 고친 뒤 착수한다 — 그 결정에 걸리지 않는 묶음 1 의 행은 바로 시작할 수 있다(§2).

완료 시 할 수 있는 것(사람이 손으로 확인하는 시나리오):

1. 이 저장소(Rust · TypeScript)를 신뢰한 채 열고 `.rs` 파일을 열면 상태바에 `rust-analyzer` 항목이 「시작 중 → 인덱싱 37% → 준비」 로 바뀐다(런타임 환경의 PATH 에 있는 것을 쓰거나, 없으면 한 번 묻고 설치한다 — 결정 M4-D2). `⌘+호버` 로 선언 미리보기, `F1` 빠른 문서, `⌘B` 로 정의(표준 라이브러리 소스면 읽기 전용 탭 — 결정 M4-D13), `⌘⌥B` 구현, `⌥F7` 사용처 팝업 → 「검색 결과」 툴 윈도우에 고정. `F2` 로 다음 오류, 하단 「문제」 에 프로젝트의 진단이 파일별로 모인다.
2. `.ts` 파일에서 `⌃Space` 자동완성(문서 · 자동 import 포함), `(` 에서 시그니처 도움말(`⌘P` 로 다시), `⇧F6` 으로 여러 파일에 걸친 rename → 바뀔 파일 미리보기 → 적용하면 바뀐 파일이 미저장으로 남고 「모두 저장」 으로 쓴다(결정 M4-D14). `⌥↩` 코드 액션으로 빠른 수정, `⌘⌥L` 포맷.
3. 언어 서버가 설치돼 있지 않은 Python 프로젝트에서 `.py` 를 열면 「Python 언어 서버 basedpyright(MIT)를 설치」 제안 → 출처 · 라이선스 확인(처음 한 번) → 상태바 진행 → 진단이 뜬다. `⌘⌥L` 은 ruff 로 포맷한다(결정 M4-D3).
4. mise 로 `java@21` 을 고정한 Gradle 프로젝트에서 `.java` · `.kt` 를 열면 jdtls · kotlin-lsp 가 뜨고(느리다 — 진행이 보인다), JDK 가 없는 프로젝트면 「JDK 21 이 필요하다 — `mise use java@21`」 를 보이고 서버를 띄우지 않는다(결정 M4-D4 · D5 · D6).
5. 클론한 저장소를 신뢰하지 않은 채 열면 어떤 언어 서버 프로세스도 뜨지 않는다(`ps` 로 확인). 그래도 `⌘⌥O` 심볼로 이동 · `⌘O` 클래스로 이동 · 구조 툴 윈도우 · `⌘F12` 는 tree-sitter 인덱스로 된다(결정 M4-D8).
6. `⌃G` 로 다음 일치에 커서를 더하고 `⌃⇧G` 로 빼고, `⌃⌘G` 로 모든 일치를 고르고, `⌥+드래그` 로 사각 선택, `⌥⇧+클릭` 으로 커서를 더하고 `Esc` 로 하나로. 커서 여럿에서 한글을 친다.
7. 설정 창 「도구」 에서 설치된 언어 서버의 판 · 라이선스 · 크기를 보고, 업데이트 · 이전 판으로 되돌리기 · 제거를 한다.
8. 프로젝트 창을 닫으면 그 창이 띄운 언어 서버가 2초 안에 모두 끝난다.

**M4 의 완료 조건에는 CI 의 실 서버 시험이 들어간다**: CI 의 `lsp-live` 잡(틀은 M4-01)이 기본 번들 서버마다(rust-analyzer · typescript-language-server · Python 서버 · jdtls · Kotlin 서버 — 결정 M4-D3 ~ D5 의 답대로) 실제 서버를 Pitwall 의 설치기로 받아 따로 돌리고, 하나라도 실행 개수가 0 이면 잡이 실패한다(M3 의 `db-live` 와 같은 규칙 — M3-D16). 서버마다의 하한은 M4-18 이 정하고, 기능 행은 빠른 두 서버(rust-analyzer · typescript-language-server)로 자기 기능의 live 시험을 하나 이상 단다.

대상 플랫폼: macOS(개발 · 검증), Linux/Windows 는 CI 빌드 · 시험(06-roadmap.md 「결정 기록」 D38). `lsp-live` 는 ubuntu 에서 돌고(JVM 서버의 받기 · 기동 시간 때문에 한 잡에 묶지 않고 서버별 단계로 나눈다), macOS 는 rust-analyzer · typescript-language-server 두 서버만 같은 시험을 돈다. 로컬은 `mise run test-lsp`(환경에 없는 서버는 건너뛴다고 알린다 — 통과로 적지 않는다).

M3 까지 된 것은 다시 계획하지 않는다 — 에디터와 문서 모델(웹뷰의 `DocumentStore` · `LiveText`, 저장은 `⌘S` 만 — D34), 언어 판별(`lang.detect` · 문서 언어 — M1-18), 구문 분석 서비스와 그 문서 세션(`syntax.*` · `apps/desktop/src/editor/syntax-sessions.ts` — M1-17), 에디터 기능 칸(`EDITOR_FEATURES` — `apps/desktop/src/editor/extensions/index.ts`), 툴 윈도우 자리 `structure` · `problems`(M0-13 · `apps/desktop/src/layout/project-layout.ts` — 지금은 빈 자리), 「검색 결과」 툴 윈도우(M1-20), Search Everywhere 의 탭 틀(M1-19), 런타임 환경(`pw-runtime` — 로그인 셸 · mise, 신뢰 게이트 — M1-16 · M1-05), 실행의 연결 범위(`pw_core::registry::exec::exec_grant` — 03-architecture.md 「실행의 연결 범위」), 작업(`Task`)과 상태바 작업 항목, 알림, 마크다운 렌더(M1 미리보기), 확장 레지스트리(`pw-ext`), 내장 문법 19개와 출처표(`scripts/grammars.toml` · `mise run grammars`), 설정 창, MCP 노출 규칙(`mcp: true` 를 단 것만 툴). 아래 표는 그 위에 얹는 것이다.

### 공유 부품의 주인

## 4. 착수 전 준비물 · 결정

### 준비물

- **참고 구현 — 읽기만, 코드는 옮기지 않는다.** 받은 코드는 미신뢰로 다룬다 — 빈 폴더에 `git -c core.hooksPath=/dev/null clone --no-recurse-submodules --depth 1` 로 받아 읽기만 하고 그 폴더에서 빌드 · 스크립트를 돌리지 않는다(14-m3-plan.md 「준비물」 의 DBX 검토와 같은 방식). 라이선스로 갈린다: **Zed** 의 `lsp` · `language` 크레이트는 GPL-3.0-or-later, **Helix** 의 `helix-lsp` 는 MPL-2.0 — D10 · D31(MPL 거절)에 따라 코드 · 쿼리를 옮기지 않고 구조만 참고한다. **VS Code** `vscode-languageserver-node`(MIT)는 옮길 수 있으나 TS · Node 전용이라 동작(동기화 · 취소 · 진행 규칙)의 참고로만. **mason.nvim**(Apache-2.0)은 쓰지 않고 registry 데이터 형식만 본다(D29). 무엇을 어디서 참고했는지 행의 보고에 적는다
- **새 의존과 라이선스**(CONTRIBUTING.md 「의존성과 라이선스」): `lsp-types`(MIT — 들일 판을 정할 때 0.97 의 URI 타입 변경을 본다), `@codemirror/autocomplete`(MIT), 압축 풀기 · HTTP 크레이트(이미 쓰는 것이 있으면 그것 — `cargo tree` 로 먼저 본다), 선택 `@codemirror/lint`(MIT). Mason registry 데이터(Apache-2.0 로 알려짐 — M4-03 이 확인)는 내장 스냅숏으로 배포물에 들어가므로 고지. 서버 바이너리 자체(jdtls 의 EPL-2.0 등)는 앱에 링크 · 동봉하지 않는 별도 설치 도구라 `deny.toml` 의 대상이 아니다 — 대신 설치 전 확인 다이얼로그에 라이선스를 보인다(D29 · 결정 M4-D2)
- **CI `lsp-live` 의 준비**: ubuntu 러너의 툴체인(rust — 이미 있다, node · python · JDK 21 — mise 로 고정), 서버 설치본 캐시(키 = registry 판 + 서버 판), Gradle 캐시. JVM 서버의 받기 크기 · 첫 기동 시간을 M4-18 착수 전에 한 번 재서 잡 시한을 정한다. `lsp-live` 를 필수 검사로 더하는 것은 사람이 한다(저장소 설정 — M3 의 `db-live` 와 같다)
- **서버 크기 · 런타임 실측**(M4-03 의 첫 보고에): 기본 번들 후보의 대상별 받기 크기 · 풀린 크기 · 런타임 요구(Node · Python · JDK 판) — 결정 M4-D2 ~ D5 의 답을 위한 근거. 이 계획의 크기 언급은 실측 전이다
- **Kotlin 서버 확인**(결정 M4-D5 의 답 전): JetBrains `kotlin-lsp` 의 저장소 라이선스 표기(Apache-2.0)와 「일부 비공개 코드」 안내가 지금 어떤지, 배포 묶음의 라이선스, pre-alpha 의 지원 범위(JVM 전용 Gradle 프로젝트 — Maven?), Mason registry 에 있는지를 착수 전에 확인해 결정 표에 적는다
- **사람 확인 한 번씩**: ① 실제 Spring Boot(Gradle · Kotlin + Java) 프로젝트에서 jdtls · kotlin-lsp 의 기동 · 메모리(06 「리스크」 의 LSP 서버 메모리) ② 실제 Python 프로젝트(venv)에서 basedpyright 가 그 venv 를 찾는지 ③ 한글 IME + 자동완성 팝업 + 멀티 커서 ④ `⌥⌥` 누른 채 화살표 제스처(키맵 엔진의 새 시퀀스) ⑤ 실제 네트워크로 설치 · 업데이트 · 되돌리기
