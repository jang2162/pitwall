# 05. MCP 서버 설계

에이전트(Claude Code, Orca 내 에이전트 등)가 Pitwall을 통해 **프로젝트 구성 · 설정 · 조회**를 할 수 있게 한다.
코드 편집 자체는 에이전트가 파일시스템에서 직접 하므로, MCP는 "IDE만 아는 정보와 설정"에 집중한다.
같은 툴을 명령줄(`pitwall tool`)로도 부른다 — 「CLI (`pitwall tool`)」 절.

## 1. 전송 방식

| 방식 | 사용 | 비고 |
|---|---|---|
| stdio | `pitwall mcp [--project <path>]` | 실행 중 앱에 로컬 소켓으로 붙는 얇은 프록시. 앱이 꺼져 있으면 헤드리스 host 기동 |
| Streamable HTTP | `http://127.0.0.1:<port>/mcp` | M7 — Relay 의 MCP 엔드포인트와 함께 온다(06-roadmap.md 결정 D59). 앱 실행 중에만. Bearer 토큰 필수. 기본 꺼짐 · Desktop 과 Relay(18-m7-plan 결정 M7-D11) |

- `--project` 미지정 시 cwd로 프로젝트 자동 해석 (F2와 같은 규칙)
- 앱 미실행 + 헤드리스 모드: 코어 툴만 있고 승인이 필요한 툴은 거부한다(「로컬 소켓과 헤드리스」). 승인을 건너뛰는 플래그는 두지 않는다
- MCP 서버는 Host 별 연결 풀을 두고 툴 호출의 `projectId` 와 `checkout` 입력으로 라우팅한다([03-architecture.md](03-architecture.md) 「RPC 설계」). **지금 구현**(18-m7-plan M7-18 — `pw_mcp::checkout`): 세션은 이 머신 Host 연결 하나로 열리고, 다른 머신을 처음 겨눌 때 그 머신 Host 에 `Agent` 범위 연결을 열어 세션이 끝날 때까지 쥔다(머신마다 하나). 다른 머신 · 묶음 · 머신 별명 · 링크는 Desktop 이 꽂는 `pw_mcp::checkout::Machines`(`Services::machines` — 앱만, 구현 `apps/desktop/src-tauri/src/mcp/machines.rs`)가 안다 — 없는 세션(헤드리스 · Windows)은 다른 머신을 겨누는 호출을 모두 거절한다

### 로컬 소켓과 헤드리스

구현: `crates/pw-mcp`(`socket` · `proxy` · `server`), `apps/desktop/src-tauri/src/mcp.rs`.

- **앱 쪽**: 주 인스턴스가 시작하면 로컬 소켓을 연다. 세션 · 툴 · 감사 로그는 앱 안에서 돈다. 네트워크 포트는 열지 않는다
- **`pitwall mcp`**: 그 소켓이 있으면 붙어서 stdio 줄을 그대로 잇는 프록시다. 소켓이 없거나 받지 않으면 **헤드리스** — 같은 프로세스에 `LocalHost` 를 만들어 stdio 로 직접 서비스한다. 앱을 띄우지 않는다
  - 헤드리스는 레지스트리를 **읽기만** 한다: 파일이 없으면 빈 목록, 손상 · 마이그레이션이 필요한 파일도 건드리지 않고 빈 목록이다(복구 · 마이그레이션은 레지스트리를 소유한 앱의 일). 헤드리스에는 **코어 툴만** 있다(「툴 레지스트리」 의 「세션의 툴은 그 Host 가 처리하는 것만」) — `project_list` · `project_info` · `settings_get`. 승인 경로가 없으므로 그 가운데 `read` 툴만 성공한다. 그 밖의 툴(git · DB · 코드)은 앱이 실행 중이어야 한다 — 연 연결 · 승인 창 · 언어 서버 · 심볼 색인이 앱에 있다(06-roadmap.md 결정 D61)
    - 연결은 쓰기 가능한 플래그(파일은 만들지 않는다)로 열고 질의를 `query_only` 로 막는다. state.db 가 WAL 이라(03 「state.db」) `SQLITE_OPEN_READ_ONLY` 로 열면 앱이 꺼져 있을 때 `-wal` · `-shm` 을 만들고 닫으며 지우지 못해 남긴다. 쓸 수 있는 연결은 열려 있는 동안만 둘을 두고 마지막으로 닫힐 때 걷는다. 앱이 비정상 종료로 남긴 `-wal` 이 있으면 닫히며 그 내용(이미 커밋된 쓰기)을 파일에 옮긴다. 쓸 수 없는 폴더면 읽기 전용 · `immutable` 연결로 연다
  - Windows 는 소켓이 아직 없어 언제나 헤드리스다
  - **헤드리스로 시작한 뒤 앱이 뜨면** 그 뒤의 요청을 앱으로 넘긴다(16-m5-plan M5-20, `apps/desktop/src-tauri/src/mcp/handover.rs`). 에이전트 클라이언트는 세션을 시작할 때 `pitwall mcp` 를 띄우므로 앱보다 에이전트를 먼저 켜는 순서가 흔하다. 헤드리스 세션은 stdio 에 바로 붙지 않고 프로세스 안 duplex 에 붙으며, 그 앞의 층이 줄을 옮긴다(고치지 않는다)
    - **앱 찾기는 요청 하나에 한 번**: 넘기기 전에 `tools/list` · `tools/call` 요청이 올 때마다 시작할 때와 같은 길(`connect_app` — 같은 핸드셰이크, 앱 쪽은 같은 에이전트 범위로 세션을 연다)로 소켓을 한 번 본다. 주기적으로 보지 않고(요청이 없으면 일도 없다), 그 밖의 요청(`ping` 등)과 넘긴 뒤에는 보지 않는다. 「한 번」 은 상한이다 — 앱 자리에 붙지 못했거나(폴더 검사 · 소켓 핸드셰이크 시한 · 거절) 앱이 다시 보낸 `initialize` 에 답하지 않거나 거절하면 30초 동안 다시 찾지 않는다(`mcp::handover::RETRY_AFTER`). 멈춘 앱이 tools 요청마다 최대 10초씩 세션을 붙잡지 않게 하고, 그 경고는 한 번만 남긴다. 앱이 없는 것(소켓이 없거나 받지 않음)은 물러나지 않는다
    - **넘겨 붙기**: 앱이 받으면 클라이언트가 처음 보낸 `initialize` 와 `notifications/initialized` 를 그대로 앱에 다시 보내 앱 쪽 세션을 연다(같은 클라이언트 이름 — 앱의 `initialize` 응답은 클라이언트에 보내지 않는다). 앱이 5초 안에 답하지 않거나 거절하면 넘기지 않고 헤드리스로 남는다(다음 요청이 다시 본다). 그 뒤 `notifications/tools/list_changed` 를 클라이언트에 보내고, 넘기게 한 요청부터 앱이 받는다. 2026-07-28 클라이언트는 `initialize` 가 없어 다시 보낼 것이 없고, 헤드리스에 열어 둔 `subscriptions/listen` 을 같은 줄(같은 요청 id)로 앱에 다시 열어 구독을 옮기고, 툴 목록 변경을 받겠다고 한 구독마다 그 구독 id(`_meta` 의 `io.modelcontextprotocol/subscriptionId`)를 실은 `tools/list_changed` 를 보낸다. **수락 알림이 언제나 먼저다** — 클라이언트(rmcp 의 `listen`)는 수락 전에 다른 알림이 오면 구독을 실패로 끝낸다. 헤드리스의 수락을 이미 클라이언트에 옮긴 구독은 앱의 두 번째 수락을 삼키고 곧바로 `list_changed` 를 보낸다. 수락 전에 옮긴 구독은 헤드리스의 수락을 버리고 앱의 수락을 첫 수락으로 통과시킨 뒤 그 바로 뒤에 `list_changed` 를 쓴다(클라이언트로 가는 줄은 넘겨 붙기 층의 한 루프가 차례로 쓴다)
    - **넘기기 전에 시작된 호출은 헤드리스에서 끝난다**: 요청 id 마다 받은 쪽을 적어 응답 · 취소 알림을 그쪽으로 돌리고, 헤드리스에 남은 요청이 없어지면 헤드리스의 입력을 닫는다. 헤드리스 세션은 감사 기록을 다 쓴 뒤 끝나고 프로세스는 그것을 기다린다. 넘긴 뒤 헤드리스가 내는 툴 목록 알림은 버린다. 감사 로그의 세션 id 는 넘기며 바뀐다 — 넘긴 뒤의 행은 앱 세션의 것이다(앱의 세션 등록부에 오르는 id)
    - **넘긴 뒤는 프록시와 같다**: 앱이 닫히면 아래 「끊김」 그대로다(기다리던 요청에 `-32001`, 종료 코드 1). CLI(`pitwall tool`)는 호출마다 새로 붙어 넘겨 붙기와 무관하다
    - 헤드리스 세션의 서버 안내문(`instructions`)은 「앱이 꺼져 있어 코어 툴만 있다. 앱을 켜면 다시 시작하지 않아도 이 세션에 나머지 툴이 나온다」 를 알린다(`pw_mcp::server::HEADLESS_NOTICE`). 안내문은 `initialize` 때 한 번 나가 넘긴 뒤에도 바뀌지 않는다. 앱 세션에는 싣지 않는다. 헤드리스인지는 연결 방식(stdio · 소켓 · 프로세스 안 duplex)이 아니라 세션을 서비스하는 Host 의 성질이다 — 세션을 만드는 쪽이 `pw_mcp::Services` 의 `host_kind`(`HostKind::App` · `HostKind::Headless`, 기본값 없음)로 알린다. `write` 이상 거절의 까닭 `headless_write` 도 이것으로 가른다
- **위치**: `$STATE/run/<해시>.sock`. 경로가 `sun_path` 한도(103바이트, macOS 104 · Linux 108 의 작은 쪽)를 넘으면 `<임시 폴더>/pitwall-<uid>/<해시>.sock`(macOS `$TMPDIR` 는 사용자 전용). 양쪽이 같은 규칙으로 고른다
- **그 사용자만 붙는다**: 폴더는 0700 · 이 사용자 소유 · 심링크 아님(서버는 만들거나 0700 으로 고치고, 다른 사용자 소유 · 심링크면 소켓을 열지 않는다. 클라이언트는 같은 검사를 통과한 폴더에만 붙는다), 소켓 파일 0600, 연결마다 양쪽이 상대 uid(`getpeereid` · `SO_PEERCRED`)를 본다(`pw_mcp::socket::peer_allowed` — 다른 uid · 자격을 못 읽은 연결은 거절). macOS 는 소켓 파일 권한으로 connect 를 막지 않으므로 폴더 권한이 실제 방어선이다
- **워크트리 격리**: 소켓 이름의 해시는 단일 인스턴스 키(debug: 빌드 폴더 + `$DATA`, release: 앱 identifier — 기본이 아닌 `$DATA` 면 그 해시를 붙인 것, `apps/desktop/src-tauri/src/instance.rs`)와 `$STATE` 로 만든다. 다른 워크트리 · 다른 `$DATA` 의 `pitwall mcp` 는 다른 이름을 계산해 이 앱에 붙지 않고 헤드리스로 돈다
- **이미 있는 소켓**: 붙어 보고 받으면 다른 앱이 쓰는 중이라 열지 않는다. 받지 않으면(앱이 죽고 남은 파일) 지우고 연다. 소켓이 아닌 파일 · 심링크는 지우지 않는다. 앱이 끝날 때 소켓 파일이 남을 수 있는데, 다음 시작이 이 규칙으로 바꾼다
- **핸드셰이크**: 연결 직후 클라이언트가 JSON 한 줄(`protocol: "pitwall-mcp/1"`, `project`, `cwd`), 서버가 한 줄(`ok`, `error`)로 답한다. 그 뒤는 MCP 바이트다. 프로젝트 해석(`project.resolve`)은 앱이 한다
- **세션 등록부**(16-m5-plan M5-10, `pw_mcp::sessions`): 앱 안의 세션은 초기화를 마치면 등록되고 끝나면 빠진다 — id(감사 행의 `session`) · 클라이언트(`이름 버전` — 2025-11-25 까지의 클라이언트는 initialize 로, 2026-07-28 클라이언트는 첫 툴 호출로 안다) · 세션 프로젝트 · 전송 · 시작 시각 · 호출 수(감사 행 하나가 호출 하나). 사람의 화면은 `mcp.sessions`(read, owner — 에이전트 범위 연결은 거절한다)로 읽고, 열고 닫힐 때마다 Host 범위 이벤트 `mcp.sessionsChanged`(payload 는 열린 수 `total` 뿐)가 한 번씩 나간다. 앱 없이 뜬 헤드리스 세션은 그 프로세스의 등록부라 앱의 목록에 없다. 화면: 프로젝트 창 상태바의 「MCP n」(그 프로젝트를 세션 프로젝트로 가진 세션 수, 0 이면 없음 — 누르면 「에이전트 활동」 툴 윈도우 — 16-m5-plan M5-13, 10-ui.md 「2.5 주요 툴 윈도우 상세」) · 웰컴 창 아래 줄의 「MCP: 연결 n」(전부)
- **끊김**: 앱이 도중에 닫히면 프록시는 응답을 기다리던 요청마다 JSON-RPC 오류(`-32001`)를 stdout 에 쓰고 stderr 에 이유를 남긴 뒤 **종료 코드 1** 로 끝난다. 클라이언트가 stdin 을 닫으면 소켓의 쓰기 쪽을 닫아 앱 쪽 세션을 끝내고(남은 응답은 5초까지 옮긴다) 0 으로 끝난다. 앱 쪽 세션이 끝나면 그 세션의 Host 연결 · 설정 감시 · 버스 구독도 걷힌다
- **호출 취소**: 클라이언트가 호출을 취소하거나(`notifications/cancelled` — rmcp 가 그 요청의 취소 토큰을 건다) 세션이 끊기면 그 호출의 Host RPC 를 취소한다 — `pw_mcp::HostClient` 가 그 요청 id 로 `request.cancel` 을 보내고 Host 는 핸들러 future 를 버린다. 응답 전에 호출 future 가 버려져도 같다(`HostClient::call_until` · `call`). 세션이 끊긴 경우(전송이 닫힘)는 rmcp 가 남은 응답을 5초까지 기다린 뒤 취소 토큰을 건다 — 앱이 세션을 끝낸 경우(세션 토큰 취소)는 2초다(rmcp 3.9 `serve_inner` 의 drain). 취소된 호출은 감사 로그에 결과 `error` · 상세 `cancelled` 로 남고 결과 표지의 까닭도 `cancelled` 다. CLI 의 Ctrl+C · `db_query` 의 취소 · 승인 대기 거두기는 이 길만 쓴다. **되돌릴 수 없는 지점**(16-m5-plan M5-18b): 핸들러가 되돌릴 수 없는 효과를 내기 직전에 `pw_rpc::Ctx::point_of_no_return` 의 표지를 세우면(`PointOfNoReturn::pass`), 그 뒤의 취소(`request.cancel` · 세션 닫힘)에는 Host 가 핸들러를 버리지 않고 끝까지 돌려 그 결과로 답한다. 세움과 취소가 겹치면 한 잠금 안에서 갈린다 — 취소가 먼저면 표지가 서지 않고 핸들러는 효과를 내지 않는다. 취소를 무시하는 일반 수단이 아니고, 표지를 세우지 않는 핸들러의 취소는 그대로다. **표지를 세우는 핸들러는 이 목록에만 있다 — 지금은 `db_execute` 의 커밋 하나**(`crates/pw-db/src/execute_tool.rs`). 새로 세우는 핸들러는 이 목록에 더하고, 표지 뒤의 일을 시한으로 묶는다(`db_execute` 는 커밋 10초 — 연결 닫기는 답한 뒤에 한다). 선기록한 호출(`write` 이상 · 승인을 지난 호출)은 취소를 보낸 뒤에도 Host 의 답을 5초(`pw_mcp::server::SETTLE_AFTER_CANCEL` — 위의 「연결이 닫힌」 drain 과 같은 값)까지 기다려(`HostClient::call_until_settled`) 그 답으로 행을 끝낸다. 이때 취소는 id 를 붙인 `request.cancel` 요청으로 보낸다 — Host 는 취소를 적용한 자리에서 `null` 로 답하므로 그 확인과 툴의 답 가운데 무엇이 먼저 왔는지로 둘을 가른다. Host 가 `cancelled` 로 답하면 위와 같다. 확인 **뒤에** 결과로 답하면(표지를 넘은 호출) 결과 `ok`, 상세 끝에 「cancelled by the client after the point of no return; it ran to the end」. 확인 **전에** 답이 왔으면(취소가 닿기 전에 이미 끝난 호출 — 표지와 무관) 그 결과에 상세 끝 「cancelled by the client after the host had already finished it」. 핸들러가 Host 의 취소 적용과 거의 같은 순간에 끝나면 표지를 넘은 호출도 뒤의 글이 될 수 있다(둘 다 결과는 사실이다). 그 답이 오류면 결과 `error` 에 같은 꼬리 글이다. 시한까지 답이 없거나 그사이 Host 연결이 닫히면 결과 `error` · 까닭 `cancelled` 에 상세 「… whether it took effect … is unknown」 — 「취소됨」 과 「모름」 을 상세로 가른다. **에이전트는 취소를 보낸 그 호출의 응답을 받지 않는다** — rmcp 는 에이전트가 취소한 요청과 전송이 닫힌 세션의 늦은 응답을 버린다(rmcp 3.9 `serve_inner` 의 `local_ct_pool`). 다만 앱이 세션을 끝낸 경우(세션 토큰 취소)에는 그 2초 drain 안에 온 응답이 나갈 수 있다. 그래서 감사 행 · Host 로그가 정본이다. **한계**: 클라이언트가 끊긴 뒤의 drain(최대 5초)과 이 기다림(최대 5초) 사이에 앱이 끝나면 그 호출의 끝 기록이 쓰이지 않아 행이 `started` 로 남을 수 있다(앱 종료가 비우는 것은 살아 있는 세션의 감사 큐다 — 「감사 로그」). `started` 는 「끝을 모름」 이다
- **세션은 프로젝트 설정을 쓰지 않는다**: 노출 판정용으로 세션 프로젝트의 설정을 읽을 때 구버전 파일은 메모리에서만 올린다(`ConfigSource::without_writes`). 커밋된 `.pitwall/project.toml` 에 `schema` 가 써지거나 저장소에 `.backup/` 이 생기지 않는다. 그 설정의 이벤트는 세션 전용 버스로 내 앱의 버스에 같은 프로젝트의 `config.*` 가 한 번 더 나가지 않는다
- **stdout 에는 MCP 바이트만**: 로그는 `$STATE/logs/mcp.<날짜>.log`, 경고 이상은 stderr 에도 쓴다. `pitwall mcp` 는 확장을 읽지 않는다
- 사용법 오류는 종료 코드 2
- Relay 데몬은 붙은 owner Desktop 이 없는 동안 헤드리스와 같다 — 승인 경로가 없으므로 `auto_approve` · 정책 자동과 상관없이 `write` 이상은 거절한다(18-m7-plan 결정 M7-D10)

- `run_logs { projectId, runId, tail?, since?, grep? }`: `since` 가 없으면 마지막 `tail`(기본 200, 상한 10000)줄, 있으면 그 오프셋부터(`tail` 을 함께 주면 그 뒤의 마지막 몇 줄). 오프셋은 링 버퍼의 바이트 오프셋(`run.attach` 의 `since` 와 같다)이고 결과의 `nextSince` 로 잇는다 — 새 출력을 기다리는 폴링도 이것이다. `grep` 은 정규식(`regex`, 1000자 · 컴파일 크기 1 MiB 까지)이고 터미널 제어를 걷은 글에 맞춘다(`tail` 은 맞은 줄의 마지막 몇 줄). 터미널 제어(CSI · OSC · DCS 등 ANSI 이스케이프, 탭을 뺀 제어 문자)는 걷고, `\r` 은 줄 앞으로 돌아간다(진행 막대는 마지막 모습만). 출력 내용은 가리지 않는다 — 프로그램이 찍은 것이다. 응답의 글은 JSON 192 KiB 안에서 자른다(세션 상한 256 KiB 아래 — 결정 M5-D34): `tail` 은 앞(오래된 줄)을, `since` 는 뒤를 덜고 `nextSince` 가 덜어 낸 첫 줄이다. 한 줄이 상한보다 크면 그 줄을 잘라 싣고 다음 줄로 넘어간다. `since` 만 준 호출은 원래 바이트 1 MiB 까지만 훑고 나머지는 `nextSince` 로 잇는다. `since` 가 이미 버려진 오프셋이면 남은 처음부터 주고 `truncated` · `dropped`(버려진 바이트 수)를 싣는다 — 조용히 비우지 않는다. 범위는 링 버퍼의 줄 색인(`RunLog::tail_lines`)으로 정하고 그 범위만 복사한다(`grep` 은 남은 버퍼 전체를 훑는다)

**지금 구현 — 실행 툴**(17-m6-plan M6-14 — `pw_run::runs::exec_tool`, 툴 메서드 `run.tool.start` · `run.tool.stop` · `run.tool.restart`, 그룹 `run`, 앱 Host 에만 있다. `sql` 갈래는 `pw_db::run_sql::AgentSqlRuns` 가 실행 관리자에 붙인다 — pw-run 은 pw-db 에 의존하지 않는다):

- 입력 `run_start { projectId, worktree?, configId, profile? }`, `run_stop` · `run_restart { projectId, runId }`. 관문은 `agent_grant`, 미신뢰 프로젝트는 묻지 않고 거절한다(`untrusted` — 구성 · `.env` 를 읽기 전). `runId` 는 관문을 지난 프로젝트의 실행만 — 다른 프로젝트의 것은 없는 실행이다. 감지된 태스크는 `run_config_upsert` 로 저장한 뒤 돈다
- **노출**: `run_start` · `run_restart` 는 선언 `dangerous` 라 기본 프리셋(`standard`)에서 보이지 않는다(`db_execute` 와 같다 — 노출은 선언 등급). `full` 프리셋이나 `[mcp.tools] run_start = true` 로 켠다
- **계획 = 띄울 것 그대로**: 프로세스 구성은 계획 등급 `exec` 이고 계획 때 푼 `RunSpec`(argv · 작업 폴더 · env 값 · 프로필)을 싣는다 — 승인 뒤에는 그것만 띄운다(`agent_run_grant` → `Runs::start_agent_with`, 구성 · `.env` 를 다시 읽지 않는다). 사람에게는 「Run」(종류 · argv · 작업 폴더 · 프로필) · 「Environment」(이름 = 값과 출처 — 구성 · 프로필 · 그 `.env` 파일. 비밀 단어 이름과 URL 비밀번호는 `•••• (sha256 <앞 8자>)`, `GIT_CONFIG_KEY_<n>` 은 그대로) · 「Environment files」(경로와 sha256) · argv 가 비밀처럼 보이면 「Warning」 을 보인다. 대상 값은 구성의 내용 해시(「사람이 본 구성」 해시)다 — 승인 뒤 구성 · `.env` · 스크립트 본문 · 런타임 원천 파일이 바뀌면 `plan_changed`
- **정책 자동 · 기록**: 신뢰한 프로젝트이고 그 내용 해시가 「사람이 본 구성」 이면 `policy`. 계획에 (구성 열쇠, 해시)를 싣고, 사람이 그 프로젝트 창에서 [허용](`mcp.approval.answer` — 이번만 · 세션 · CLI 허용)하면 그 창의 연결 범위로 기록한다(`SeenPlace::Approval`). 툴 핸들러는 기록하지 않는다. [허용] 으로 기록된 뒤 둘째 호출이 다시 만든 계획은 정책 자동이 켜지므로, 툴은 정책 자동이 꺼진 같은 계획이 승인 표와 맞으면 지나보낸다
- **사람이 띄운 실행**(결정 D69): 창에서 띄웠거나 `restartOf` 를 따라간 앞 실행이 창에서 띄운 실행(`Run::launched_by_person`)이면 `run_stop` · `run_restart` 는 정책 자동 · `auto_approve` 없이 묻는다. 허용 열쇠는 `run_stop` 이 `human:<runId>`, `run_restart` 는 `human:<runId>:<내용 해시>` 다 — 그 실행을 그 내용으로 다시 띄우는 것에만 닿고, 허용 뒤 구성 · `.env` · `sql` 파일이 바뀌면 다시 묻는다(그 실행은 끝난 뒤에도 같은 `runId` 로 또 부를 수 있다). 에이전트가 띄운 실행의 `run_stop` 은 신뢰한 프로젝트면 `policy`, 열쇠는 `<구성 열쇠>` 다
- **`sql` 구성**: 관문은 `db_execute` 와 같다(사람이 연 연결만 — 아니면 `notOpenedByUser`, 프로덕션은 `block` 이면 `productionBlocked`). 파일을 지금 읽어 분류하고 묻기 전 거절(`db_execute` 와 같은 것)을 지난다. 조회만이면 계획 `read` · `policy`(읽기 전용 트랜잭션), 그 밖과 프로덕션 `ask` 는 매번 묻는다(세션 허용 없음). 끝날 때까지 기다려 `sql` 요약(문장 수 · 트랜잭션마다 끝 · 실패 · 중지 · 돌지 않은 파일)과 `run` 을 함께 돌려준다. MCP 취소는 그 실행의 중지(`QueryCancel`)이고, 커밋을 정한 뒤의 취소는 커밋을 끊지 않는다(감사 상세 끝 `CANCELLED_AFTER_THE_POINT`)
- `run_restart` 는 앞 실행이 끝난 것을 본 뒤(`stop_and_wait`) 그 구성(그 실행의 워크트리 · 프로필)을 지금 읽어 새 실행으로 띄운다(`restartOf`). 프로세스 · `sql` 실행만 — 디버그 실행은 거절한다
- **띄우는 순간 다시 읽는 원천**: `npm run` · `mise run` 은 띄울 때 `package.json` · `mise.toml` 을 스스로 다시 읽는다 — 내용 해시가 정의 본문을 덮어도 계획과 띄우기 사이의 짧은 틈에 바꾼 본문이 돌 수 있다. 명령이 실행하는 소스를 덮지 않는 것(06 결정 D68)과 같은 종류로 받아들인다
- **사슬 — `before` 와 복합 구성**(17-m6-plan M6-21 — 결정 D67 · D68, 메인 판정 2026-11-19, `pw_run::runs::chain` · `chain_tool`): 구성의 `before = [id, …]` 는 그 구성들이 차례로 끝 코드 0 으로 끝난 뒤 본 구성을 띄운다(`sql` 구성도 낀다 — 시드 · 마이그레이션 뒤 서버). `type = "compound"` 는 `configs` 를 `sequence`(앞이 0 으로 끝나야 다음) 또는 `parallel`(함께)로 띄운다. 실패하면 거기서 멈추고 남은 것을 띄우지 않는다. 없는 구성 · 쓸 수 없는 구성 · 순환(자기 자신 포함) · 깊이 8 · 단계 32 초과 · 한 사슬에 같은 `sql` 구성 두 번은 읽을 때 「쓸 수 없음」 이고, `run_config_upsert` 는 그런 `before` · `configs` 를 묻기 전에 거절한다(`badReference`) — 사람이 본 적 없는 구성은 가리켜도 된다(실행이 묻는다). `run_start` 의 계획은 모든 단계(프로세스는 `RunSpec` 과 보이는 내용, `sql` 은 `PlanChange::Sql`)와 차례를 싣고, 등급은 단계 가운데 가장 높은 것, **정책 자동은 모든 프로세스 단계와 지나는 복합 구성이 「사람이 본 구성」 이고 `sql` 단계가 모두 조회만일 때만**이다(복합 구성의 해시는 열쇠와 구성 전체 — `configs` · `mode` · `before`, `pw_run::seen::compound_hash`). [허용] 은 모든 단계 · 복합 구성을 기록한다. 승인 뒤에는 계획의 것만 띄우고, 앞 단계가 돈 뒤의 단계는 띄우기 전에 지금 내용을 다시 풀어 계획의 해시와 견준다 — 다르면(앞 단계가 뒤 단계의 구성 · `.env` · 명령 정의 · 런타임 원천 파일 · SQL 파일을 바꿈) 그 단계 앞에서 `planChanged` 로 멈춘다(대가: 코드 생성 뒤 마이그레이션을 돌리는 사슬은 그 단계 앞에서 끊긴다). 호출은 모든 단계를 띄울 때까지 기다리고 결과의 `chain` 에 띄운 실행을 차례로 싣는다. **중지**: 사슬이 아직 띄우는 중이면 그 사슬의 어느 실행을 멈춰도(사람 · `run_stop` · 창 닫기 · 호출 취소) 사슬 전체가 멈추고 남은 단계를 띄우지 않는다. 다 띄운 뒤에는 실행마다 따로다. 되돌릴 수 없는 지점(`sql` 단계의 커밋) 뒤의 취소는 다음 단계를 띄우기 전에 보고 남은 것을 띄우지 않는다. 사슬의 진행 · 실패 단계는 프로젝트 이벤트 `run.chain`(`RunChainEvent`)이다. 사람의 창(`run.start`)도 같은 사슬이고 **모든 확인을 첫 단계를 띄우기 전에** 받는다 — 첫 실행 확인(`7001`, `steps` · `order` 에 모든 단계)과 `sql` 단계마다의 위험 확인(`3001`, `data.config` 가 그 단계 — 다시 부를 때 `sqlConfirmed` 에 구성 열쇠별로 싣는다, 모든 확인을 지난 뒤에야 쓰이고 한 번만 쓰인다). `before` 가 있는 `sql` 구성은 `run.sql.start` 가 거절한다(`run.start` 로). **디버그 시작**(`debug.start` — 🐞 · ⌃D)도 구성의 `before` 사슬을 같은 확인으로 먼저 끝까지 돌리고(모두 끝 코드 0) 그 뒤에 디버그 세션을 연다 — `before` 가 실패하면 세션을 열지 않는다. 사슬의 `sql` 단계는 단독 `sql` 실행과 같이 요약(결과의 `sql` — 단계 구성 id → 요약)과 감사 상세(`step=<id>` 뒤에 파일 · 내용 해시 · 트랜잭션의 끝)를 남긴다 — 커밋 뒤 취소여도. 호출 취소는 그때 띄우는 중이던 단계까지 끝낸다(띄운 실행은 띄운 그 자리에서 사슬에 든다). 사슬이 멈춰 띄우지 않은 단계의 오류는 `CONFLICT`(`chainStopped`), 실패한 단계는 `CONFLICT`(`stepFailed`)이고, 병렬 갈래가 실패하면 처음 실패한 단계를 알린다. 결과의 `run` 은 마지막으로 띄운 실행이다(병렬이면 갈래 차례에 따라 다르다 — 전부는 `chain`). 감사 상세는 길이 상한에서 잘린다(단계가 많으면 뒤쪽 단계의 상세가 빠진다).
- 감사 상세는 구성 열쇠 · 내용 해시 · `runId`(`sql` 은 파일마다 경로와 내용 해시 · 트랜잭션의 끝)뿐이다 — 명령줄 원문 · env 값은 남기지 않는다

**`sql` 종류 실행 구성**(04 F7-1, 06-roadmap.md 결정 D55): DB 연결과 SQL 파일 목록을 저장한 구성도 위 툴로 만들고 돌리고 로그를 본다. 프로세스를 띄우지 않고 `db_query` · `db_execute` 와 같은 DB 실행 경로를 지난다.

- **등급은 `exec` 규칙이 아니라 실행하는 그때의 분류가 정한다.** `run_start` 가 부를 때마다 파일들을 읽어 분류하고, 조회만이면 `read`, 그 밖은 `dangerous`(매번 승인 · 프로덕션 기본 차단)다. 「이미 존재하는 구성은 자동」 은 `sql` 종류에 적용하지 않는다 — 구성이 그대로여도 파일 내용은 바뀔 수 있다
- 연결의 read-only · 프로덕션 태그 · 미신뢰 프로젝트의 연결 금지는 SQL 콘솔과 같이 적용된다
- `run_logs` 에는 문장마다 번호 · 영향 행 수(조회는 행 수와 앞쪽 몇 행) · 소요 · 오류가 남는다. 결과 행 전체가 필요하면 `db_query` 를 쓴다
- **지금 구현**(17-m6-plan M6-09 — 실행 경로와 사람의 길. 툴 `run_start` 의 `sql` 갈래는 M6-14 — 위 「지금 구현 — 실행 툴」): 구성은 `connection` · `files`(프로젝트 루트 기준, 순서대로) · `transaction`(`all` 기본 — 모든 파일이 트랜잭션 하나 · `per_file` — 파일마다 하나 · `none` — 문장마다 자동 커밋, 트랜잭션 안에서 못 도는 PG `CREATE INDEX CONCURRENTLY` · `VACUUM` 을 위한 것)이고, 실패하면 늘 멈춘다. 실행은 `pw_db::run_sql` 이 `pw_db::script` 의 파일 여럿 · 트랜잭션 방식(`run_files`)으로 돌리고, 실행 관리자의 실행 하나(`RunKind` 종류 `sql` — 프로세스가 없다, 중지는 그 연결의 인터럽트 `QueryCancel`, 커밋을 시작한 뒤의 중지는 커밋을 끊지 않는다)로 든다. 실행할 때마다 Host 가 파일들을 한 번 읽어 분류하고 그 글을 돌린다(파일을 다시 열지 않는다). 조회만이면 읽기 전용 트랜잭션 하나에서 돌고 롤백한다. 파일 안의 트랜잭션 제어 문장(`BEGIN` · `COMMIT` · `SAVEPOINT` 등)은 받지 않는다 — 구성의 `transaction` 이 정한다. 콘솔(`run_logs`) 형식은 문장마다 `#<번호> <파일>:<줄> <등급> <영향 행 수 또는 조회 행 수> <소요> ms`, 조회는 그 아래 앞 5행의 표와 남은 행 수, 오류는 `#<번호> <파일>:<줄> error [<코드>]: <DB 원문>`, 트랜잭션마다 끝(`committed` · `rolled back` · `commit outcome unknown` · `read-only, rolled back` · `no transaction`), 돌지 않은 파일(`not run:`), 마지막 줄 `done` · `failed` · `stopped` 과 돈 문장 수다(영어 — 에이전트도 읽는다). 끝 코드는 성공 0, 실패 · 중지 1. 사람이 창에서 돌리는 길은 `run.sql.start`(그 프로젝트 창만, 미신뢰 프로젝트는 구성 · 파일을 읽기 전에 거절 — 연결하지 않는다)다. 그 클릭이 D48 의 「사람이 누름」 이다(메인 판정 M6-P16 — 연결을 열면 「사람이 연 연결」 로 기록된다). read-only 연결의 조회 밖 문장은 거절(`readOnlyConnection`), 조회가 아닌 문장이 하나라도 있으면 SQL 콘솔과 같은 위험 확인(`3001`, `data` 는 `RunSqlConfirmRequired` — 창은 `db/safety/risk-confirm.tsx` 를 그대로 띄운다, 프로덕션 연결의 파괴 등급이면 연결 이름 치기)이다. 확인은 SQL 콘솔과 같이 **한 번만 쓰이고**(구성마다 확인 순번 — 확인을 써서 지나면 오른다, 같은 확인을 다시 실으면 다시 묻는다), 그때 읽은 내용의 해시(순번 · 연결 id · 연결 설정의 푼 대상 · 프로덕션 · 읽기 전용 표지 · 방언 · 방식 · 파일마다 경로와 내용 해시 · 문장 원문)에 묶여, 확인 뒤 파일이나 연결 설정(다른 서버 · 표지)이 바뀌면 돌지 않고 다시 묻는다(`rejected: "hashMismatch"`). 파일은 64개, 합계 5 MiB(`db_query` · `db_execute` 의 `file` 하나와 같다)까지 — 넘으면 띄우기 전에 거절한다(파일 수는 구성 「쓸 수 없음」, 합계는 invalid params `tooLarge`). 에이전트 호출의 「되돌릴 수 없는 지점」(`PointOfNoReturn`)은 트랜잭션이 있으면 커밋 앞에서, `none` 이면 첫 문장을 보내기 직전에 선다(서지 못하면 아무 문장도 보내지 않는다). 트랜잭션이 롤백됐어도 그 안에서 암묵 커밋 문장(MySQL · MariaDB 의 DDL — `db_execute` 의 `irreversible` 과 같은 판정)이 돌았으면 콘솔은 「rolled back after an implicit commit … the statement at <파일>:<줄> committed the statements before it」 이라고 쓴다(요약의 `implicitCommitAt`). 다시 실행(`run.restart`)은 없다 — 창은 `run.sql.start` 를 다시 부른다(확인을 다시 받는다). 에이전트의 길이 쓸 부품(`DbSessions::plan_sql_run` · `SqlRunPlan::refuse_before_asking` · `plan_change` · `audit_detail` · `DbSessions::start_sql_run`)과 승인 계획의 꼴(`PlanChange::Sql` 의 `files` · 문장마다 `file` · `transaction` · `keepsOnFailure` — 승인 다이얼로그가 「실패해도 앞 파일은 커밋된다」 · 「실패해도 앞 문장은 남는다」 를 보인다)은 있다

| `debug_state` | 현재 정지 위치, 스택, 지역 변수 스냅샷 | read |

조건 · 로그 메시지 · hit count 는 어댑터가 대상 프로세스 안에서 평가하는 식이라 `exec` 툴로 가른다(17-m6-plan 결정 M6-P17 — 결정 M5-D26 의 선언 등급 규칙). 에이전트가 스텝 · 계속 · 식 평가를 부르는 툴은 없다. 디버그 세션을 여는 툴(`debug.start` 는 MCP 툴이 아니다)과 디버그 어댑터를 설치하는 툴도 없다 — 디버그 세션은 사람이 🐞 · ⌃D 로만 열고, 어댑터 설치 확인도 그 길에만 있다(17-m6-plan M6-18, 메인 판정 2026-11-21).

- **지금 구현**(17-m6-plan M6-20 — `crates/pw-debug/src/tool.rs`, 앱 전용 · 그룹 `debug`): 넷 다 MCP 세션의 연결만 받는다(`agent_grant`). 경로는 프로젝트 루트(워크트리면 그 안의 프로젝트 루트) 안의 일반 파일만이고(절대 경로나 루트 기준 상대 경로 — 심링크를 푼 실제 경로, `pw_fs::scope::Roots::readable`), 저장은 루트 기준 상대 경로라 워크트리끼리 같은 목록이다(03 「데이터 저장」 의 `breakpoints.json`). `breakpoint_set { path, line, enabled?, remove? }` 의 입력에는 식의 칸이 없고(모르는 키는 거절), **식이 있는 꺼진 브레이크포인트를 켜지 못한다** — 끄기 · 지우기는 되고 끌 때 식은 그대로 남는다(메인 판정 2026-11-19 — 사람이 꺼 둔 식을 `write` 의 자동 승인으로 다시 돌게 하지 않는다). 계획은 그 줄의 앞뒤 브레이크포인트이고 식은 가리지 않고 그대로 보인다. `breakpoint_set_expr { path, line, condition?, logMessage?, hitCondition?, enabled? }` 는 식이 하나는 있어야 하고, 계획에 식을 하나씩 그대로 싣고 「이 세션 동안 허용」 은 그 식의 해시에만 닿는다(`Remember::Key`). 승인 뒤에는 계획 때 읽은 그 줄이 지금도 같을 때만 바꾼다(`Breakpoints::replace_line` — 다르면 `CONFLICT`). 열린 디버그 세션에는 곧바로 가고, 저장되므로 사람이 나중에 띄우는 세션에서도 돈다. 에이전트가 두거나 바꾼 브레이크포인트에는 표지(`agent`)가 남는다 — 사람이 창에서 그 파일을 다시 저장해도 같은 줄 · 같은 내용이면 남고, 그 줄을 바꾸면 사람 것이 된다. `debug_state { projectId, sessionId? }` 는 그 프로젝트의 디버그 세션만 본다 — 다른 프로젝트의 `sessionId` · 끝난 세션 · 없는 id 는 모두 오류가 아니라 `noSession` 이다. 상태는 `noSession` · `starting` · `running` · `stopped` 이고, 멈춰 있을 때만 어댑터에 묻는다: 정지 까닭 · 스레드(100개까지) · 멈춘 스레드의 위 20 프레임 · 맨 위 프레임의 영역마다 변수 한 단계(100개까지, 펼치지 않고 비싼 영역은 읽지 않는다), 글은 512자에서 자르고 응답은 192 KiB 안에서 덜어 낸다(`truncated`). 멈춤은 어댑터의 `stopped` 이벤트로 기록하고 `continued` · 사람의 계속 · 스텝 · 그 세션의 끝으로 지운다. 디버그 세션은 실행처럼 프로젝트에 속하므로 `worktree` 입력이 없다 — 서버가 빈 `worktree` 를 세션의 워크트리로 채우므로 그것으로 거르면 주 체크아웃에서 사람이 띄운 세션이 말없이 빠진다(`run_status` 와 같은 까닭, 메인 판정 2026-11-19). 미신뢰 프로젝트에서 평범한 브레이크포인트는 둘 수 있고(`breakpoint_set`), 식이 있는 것(`breakpoint_set_expr`)은 묻기 전에 `PERMISSION_DENIED`(`untrusted`)로 거절한다 — 신뢰한 뒤 사람의 세션에서 사람이 본 적 없는 식이 돌지 않게(「권한 모델」 `exec` 의 「신뢰된 프로젝트」, 메인 판정 2026-11-19 F1). 감사 행에는 입력의 식이 글자 수로만 남는다(`CONTENT_WORDS` 의 `condition` · `log`) — 결과(변수 값)는 감사에 남지 않는다

### DB
| 툴 | 설명 | 권한 |
|---|---|---|
| `db_connection_list` | 연결 목록 (비밀 제외) — 대상(호스트 · 포트 · DB · SQLite 경로), 에이전트에게 적용하는 read-only · 프로덕션 표지, 상태, 에이전트가 지금 쓸 수 있는가(`usable` · `unusableReason`). 미신뢰 프로젝트에서도 준다 | read |
| `db_connection_upsert` | 연결 추가/수정 — 비밀번호는 툴 인자로 받지 않고 UI 입력 요청 또는 env 참조 | write |
| `db_connection_test` | 연결 테스트 — 입력은 연결 id 뿐이다(저장 전 초안 · 비밀은 받지 않는다). 연 적 없는 연결이면 「이 연결 열기」 승인을 청한다 | write |
| `db_schema` | 스키마/테이블/컬럼/인덱스 조회 — `object` 가 없으면 한 단계의 목록 한 쪽(`kind`: `database` · `schema` · `table`(기본) · `view` 등, `filter` · `cursor` · `limit`), 있으면 그 객체의 열(기본 키 표시) · 인덱스 · FK, `detail: "ddl"` 이면 DDL. 창의 탐색기와 같은 메타데이터용 연결 · 캐시를 쓴다 | read |
| `db_query` | 조회 SQL 실행 — 입력은 `sql`(글) 또는 `file`(SQL 파일 경로) 중 하나와 `maxRows`(문장마다 행 상한 — 쪽 단위가 아니다, 메인 판정 2026-11-14). **읽기 전용 트랜잭션 + 행 제한**. 조회가 아닌 문장이 하나라도 있으면 거절한다 | read |
| `db_execute` | 쓰기를 포함한 SQL 실행 — 입력은 `db_query` 와 같다. SQL 위험도 분류(04 F6-9)의 문장과 등급을 보이고 **매번 승인**받는다 | dangerous |
| `db_kv_scan` | Redis 키를 쪽 단위로 찾는다(패턴 — 키 · 타입 · TTL · 크기) | read |
| `db_kv_get` | Redis 값 한 쪽(타입별) | read |

**툴의 등급은 툴 메서드의 선언이다.** UI 가 쓰는 RPC(`db.schema.*` · `db.query.page` · `db.connection.test`)는 연결을 열어 `exec` 로 선언돼 있고 툴이 아니다(「툴 레지스트리」 의 「툴 메서드」). DB 쓰기는 조회와 다른 툴이다 — `db_execute` 만 따로 끄고 켤 수 있다(06-roadmap.md 결정 D60). `db_schema` · `db_query` · `db_execute` 는 SQL 드라이버(PG · MySQL/MariaDB · SQLite)만 받고 Redis 연결이면 `unsupported` 다. Redis 는 조회 둘(`db_kv_scan` · `db_kv_get`)뿐이고 명령 실행 툴은 없다.

**에이전트의 DB 연결**(06-roadmap.md 결정 D60 — D48 「연결은 사람이 누를 때만」 의 에이전트 쪽):

- 연결을 여는 툴(`db_schema` · `db_query` · `db_execute` · Redis 조회 · `db_connection_test`)은 **사람이 그 프로젝트 창에서 이번 앱 실행 중에 같은 대상으로 연 연결**만 쓴다. 「같은 대상」 은 푼 대상(드라이버 · 호스트 · 포트 · DB · 사용자 · 터널 목적지)이 같다는 뜻이다 — 연결 설정은 워크트리마다 다른 파일에서 읽히므로, 워크트리의 같은 id 가 다른 대상을 가리키면 연 적 없는 연결이다
- 툴은 사람의 연결을 빌리지 않는다 — 호출마다 자기 연결을 새로 연다(스키마는 메타데이터용 연결). 사람이 DB 탭을 닫은 뒤에도 앱을 끌 때까지 된다
- 연 적 없는 연결은 `db_schema` · `db_query` · `db_execute` · Redis 조회가 거절한다. **`db_connection_test` 만 「이 연결 열기」 승인을 청한다** — 그 세션 동안 그 연결(같은 대상)에 한하고 `auto_approve` 를 적용하지 않는다. 승인받은 연결은 그 세션의 다른 DB 툴도 쓴다
- 프로덕션 태그 연결은 `[mcp.policy] production` 을 따른다 — `block`(기본)이면 조회도 쓰기도 막고, `ask` 면 **사람이 연** 프로덕션 연결에 한해 조회까지 매번 승인받는다. 연 적 없는 프로덕션 연결은 승인으로도 열리지 않는다. `ask` 는 사람의 설정에서만 켠다 — 커밋되는 공유 설정의 `[mcp.policy]` 는 읽지 않는다(「권한 모델」)
- **표지는 조여지기만 하고 대상에만 묶인다**(16-m5-plan 결정 M5-D37): Host 가 그 프로젝트의 연결 설정을 읽을 때마다(목록 · 열기 · 툴 호출 — 어느 워크트리의 것이든) 그 연결의 프로덕션 · read-only 표지를 푼 대상에 묶어 기억에 더한다 — 연결 id 와 무관하고 사람이 그 연결을 열었는지와도 무관하다(「사람이 연 연결」 은 그대로 연결 id 와 대상 둘에 묶인다). 에이전트의 DB 툴 호출 때는 그 저장소의 메인 체크아웃(연결 워크트리를 따로 등록한 프로젝트면 신뢰가 따르는 메인 저장소 프로젝트의 주 루트 — 메인 판정 2026-11-14)의 연결 설정도 함께 읽어 더한다. **표지의 열쇠**(메인 판정 2026-11-14 — M5-06 리뷰): 한 연결로 다른 DB 를 읽을 수 있는 드라이버(MySQL · MariaDB)는 표지의 열쇠에서 DB 이름을 뺀다 — 열쇠는 드라이버 · 호스트 · 포트 · 사용자 · 터널 목적지다. 그 서버의 어느 DB 가 프로덕션이면 그 서버 · 사용자로 가는 에이전트 호출은 모두 프로덕션이다(`db_query` 가 SQL 글 안의 다른 DB 를 지킬 수 없다). Redis 도 DB 번호를 뺀다(메인 판정 2026-11-17 — 16-m5-plan M5-19): 한 연결이 `SELECT` 로 다른 번호로 옮겨 가고 번호 사이에 권한 경계가 없으며, 번호를 열쇠에 두면 같은 번호의 다른 표기(`database` 입력 `"00"`, 번호를 뺀 설정과 `"0"`)로 표지를 비껴간다 — 그 서버의 어느 번호가 프로덕션이면 그 서버 · 사용자의 모든 번호가 프로덕션이다. PG 는 DB 이름을 열쇠에 둔다(한 연결이 다른 DB 를 읽지 못한다). SQLite 는 파일이 열쇠다(`ATTACH` 는 M5-07 의 실행 분류가 다룬다). 「사람이 연 연결」 의 열쇠는 그대로 푼 대상 전체다. 에이전트에게 적용하는 표지는 그 대상에서 본 것(앞 실행들의 것 포함 — 아래 「표지 기억은 앱 실행을 넘어 영속한다」) 가운데 가장 엄한 것이다. 설정에서 `production` 이나 `read_only` 를 지워도, 자기 워크트리에서 표지 있는 연결을 지우고 표지 없는 새 연결 설정(다른 id)으로 같은 대상을 가리켜도, 메인 체크아웃의 설정이 그 대상을 프로덕션이라고 적고 있으면 에이전트에게는 프로덕션이다 — 조회 길과 「이 연결 열기」 승인 길 둘 다, 사람이 그 연결을 연 적이 없어도. 비밀과 확인이 대상에 묶이는 것과 같다(같은 대상은 같은 데이터다). 표지를 더하는 쪽은 곧바로 따른다. Pitwall 이 어느 프로젝트의 연결 설정에서도 표지를 본 적 없는 대상은 기억한 표지가 없어 지금 설정의 표지를 따른다(같은 서버의 다른 사용자 · PG 의 다른 DB 이름은 다른 대상이다) — 「이 연결 열기」 승인 다이얼로그가 대상(호스트 · DB)을 보인다는 것이 그 자리의 방어다
- **에이전트의 연결 쓰기는 표지를 조이기만 한다**(메인 판정 2026-11-17 — 16-m5-plan M5-17 리뷰 B1). 에이전트가 Pitwall 을 거쳐 설정 파일의 표지를 내리는 길을 막는다(이 판정은 표지 기억이 이번 실행 동안만이던 때 생겼고, 기억이 영속한 뒤에도 그대로 둔다 — 파일과 기억이 다른 표지를 말하지 않게). `db_connection_upsert` 는 묻지 않고 거절한다(`PERMISSION_DENIED`): ① 그 연결 id 의 지금 표지 — 어느 레이어(공유 · 개인 `.local.toml` · 메인 체크아웃 폴백)든, 이 워크트리 · 메인 체크아웃 · 메인 저장소 프로젝트 어느 쪽 설정이든 — 를 끄거나 지우는 쓰기(`lowersMarks`) ② 표지가 붙은 연결의 푼 대상(호스트 · 포트 · DB · 사용자 · 터널 · 파일)을 바꾸는 쓰기(`movesMarkedTarget`) ③ 표지가 기억된 대상(표지 기억의 열쇠 — MySQL · MariaDB · Redis 는 서버 · 사용자)을 그 표지 없이 가리키는 쓰기(`lowersMarks`). 판정은 M5-06 의 표지 기억 · 열쇠 함수를 그대로 쓴다(`pw_db::gate::check_agent_write`). 표지를 내리거나 표지 붙은 연결을 옮기는 것은 사람이 Pitwall 의 연결 편집에서만 한다. **에이전트에게 적용하는 표지는 모든 레이어의 합이다**(메인 판정 2026-11-17 — M5-17 재리뷰 G2): 관문 · 표지 기억 · 쓰기 판정이 병합 값과 각 레이어 파일(공유 · 개인 `.local.toml` · 메인 체크아웃 폴백)에 적힌 `production` · `read_only` 를 OR 로 본다 — 개인 파일의 `production = false` 가 공유 파일의 `production = true` 를 에이전트에게는 끄지 못한다(앱을 다시 켠 뒤에도). 창의 표지는 병합 값 그대로다. 에이전트가 자기 파일 툴로 `.pitwall/db/*.toml` 을 고치거나 지우는 것은 이 판정을 지나지 않는다 — 그래도 한 번 읽힌 표지는 기억(영속)이 막는다(아래 항목). 남는 한계: Pitwall 이 한 번도 읽지 못한 표지(파일에 쓰이자마자 Pitwall 이 읽기 전에 지워진 것)는 기억되지 않는다. **셸 등으로 상태 DB 를 직접 고칠 수 있는 에이전트**(같은 사용자 권한)가 sqlite 로 `db_marks` 의 행을 지우면 기억은 조용히 풀린다 — 그 위협은 Pitwall 이 막지 못한다(표를 지우거나 모르는 판의 행을 넣으면 읽지 못해 거절한다). 상태 DB 파일을 지우거나 망가뜨리면(손상 복구로 새로 만들어짐) 프로젝트 등록 · 신뢰와 함께 기억도 사라진다 — 사람이 프로젝트를 다시 등록 · 신뢰한 뒤에는 파일이 말하는 표지를 따른다. SQLite 대상의 열쇠는 파일의 실제 경로라, 프로젝트 폴더를 옮기면 그 기억은 새 경로에 닿지 않는다
- **표지 기억은 앱 실행을 넘어 영속한다**(사용자 결정 2026-11-18 — 16-m5-plan M5-17 재리뷰 G2, M5-17b): 기억은 Host 의 상태 DB(`$DATA/state.db` 의 `db_marks`)에도 남고, 에이전트의 DB 툴 호출마다 그 표를 다시 읽어 더한다. 한 번 프로덕션 · read-only 였던 대상은 앱을 다시 켜도, 에이전트가 자기 파일 툴로 설정에서 표지를 지워도 에이전트에게는 그대로다. **푸는 것은 사람만** — 연결 편집 다이얼로그의 「옵션」 탭 「표지 기억 풀기」(확인 다이얼로그 뒤, RPC `db.connection.forgetMarks` — 그 프로젝트 창의 연결만 받고 MCP 세션 · 파일 범위는 거절, MCP 툴이 아니다). 기억은 프로젝트를 가리지 않으므로(같은 대상은 같은 데이터다) 한 프로젝트의 창에서 풀면 모든 프로젝트에 대해 풀린다(확인 다이얼로그가 그렇게 말한다). 그 연결 설정이 아직 표지를 달고 있으면 풀어도 곧바로 다시 기억된다(화면이 그렇게 말한다). 상태 DB 를 쓸 수 없거나(읽기 전용 · 메모리 대체 · 쓰기 실패) 읽지 못하면 에이전트의 DB 툴은 모두 거절한다(`STORAGE_UNAVAILABLE`, `data.reason = "markMemoryUnavailable"`, 결과 표지 `denied` · `mark_memory_unavailable` — fail-closed). 상태 DB 의 열쇠 글은 판 표지(`v1:`)를 달고 골든 시험이 지킨다 — 모르는 판의 행이 있으면 같은 거절이다. 사람의 창은 그대로 쓴다
- 미신뢰 프로젝트 · read-only 연결 · 비밀과 확인의 규칙은 창과 같다(04 F6-9). 비밀이나 확인이 필요하면 툴 오류로 끝난다 — 에이전트는 답할 수 없다

- **지금 구현**(16-m5-plan M5-17 — `pw_db::connection_tool`): **`db_connection_test`**(`db.tool.connectionTest`)의 입력은 `{ projectId, worktree?, connectionId }` 뿐이다(밑의 `db.connection.test` 와 따로 선언한 툴 메서드 — 따로 두며 에이전트의 증거로 연 연결은 그 기록에 더하지 않는다 — 다른 세션 · 사람의 기록에 닿지 않는다. 승인받은 연결은 프로덕션 대상을 지나지 못한다(승인 뒤 표지가 더해지면 거절). 승인 뒤 연결의 대상이 바뀌면(파일 · `db_connection_upsert`) 그 기록은 닿지 않아 다시 묻는다. 승인 뒤 · 연결 직전에 설정을 바꿔 끼우면 연결 테스트의 열기 자리도 증거와 견줘 열지 않는다. 사람이 연(또는 그 세션이 승인받은) 연결의 테스트는 `write` 의 보통 규칙이다(`auto_approve` · 세션 허용 = 그 툴), 사람이 연 프로덕션 연결을 `ask` 로 테스트하면 매번 묻는다. 비밀이 필요한 연결(키체인에 없음 · 대상이 바뀜)은 승인을 묻기 전에 그 프로젝트 창에 이벤트 다이얼로그를 비밀번호 칸에 포커스를 두고 연다. 확인(`env` · 터널 목적지 · 인증서 · 루트 밖 SQLite)이 필요하면 툴 오류(3102, `confirmationRequired`)다. **`db_connection_upsert`**(`db.tool.connectionUpsert`, `write`)는 `db.connection.upsert` 와 같은 함수(쓰기 계획 · 적용)이고 계획은 그 파일(`.pitwall/db/<id>.toml` 또는 개인 `<id>.local.toml`)의 앞뒤 내용이다. 승인 뒤에는 계획 때 읽은 내용이 그대로일 때만 쓴다(바뀌었으면 해시가 달라 `plan_changed`). 입력의 비밀번호 칸은 출처(`{ "kind": "keychain" }` · `{ "kind": "env", "variable" }`)뿐이고 모르는 키는 거절한다. 저장한 연결이 비밀이 필요하면 같은 이벤트를 내고 결과의 `state` 가 `secretRequired` 다. 저장은 확인을 대신하지 않는다

**`db_query` · `db_execute` 의 `file`**(04 F6-14, 06-roadmap.md 결정 D55) — 한 번 돌리고 결과를 행으로 받는 길이다. 되풀이하는 스크립트는 「실행 구성」 표의 `sql` 종류로 저장한다.

- `sql` 과 `file` 은 함께 줄 수 없다. `file` 은 프로젝트 루트 안의 파일만 받는다 — 상대 경로는 프로젝트 루트 기준이고(MCP · CLI 같다, 부른 프로세스의 cwd 가 아니다. 워크트리가 정해진 호출이면 그 워크트리 안의 프로젝트 루트다), 판정은 `fs.read` 와 같아 심링크로 루트 밖을 가리키면 거절한다. UTF-8 텍스트, 편집 상한(06 결정 D33 의 5 MiB)까지
- **Host 가 실행하는 그때 파일을 읽고, 읽은 그 내용을 분류해 그 내용을 실행한다.** 판정은 `sql` 로 같은 글을 보냈을 때와 같다 — `db_query` 는 조회가 아닌 문장이 하나라도 있으면 아무것도 돌리지 않고 거절하고, `db_execute` 의 등급은 파일 전체에서 가장 높은 문장의 등급이다. 분류기는 Host 의 것 하나다
- **파싱 실패 · 너무 큰 문장이 든 호출은 `db_execute` 도 승인을 묻지 않고 거절한다**(파괴 등급으로 닫는 06 결정 D45 — 무엇인지 모르는 문장을 승인 다이얼로그에 올리지 않는다). 사람은 SQL 콘솔에서 돌린다
- `db_execute` 의 승인 요청은 파일 경로와 조회가 아닌 문장들을 보이고, 승인은 읽은 내용의 해시에 묶인다 — 승인 뒤 파일이 바뀌면 그 승인으로 돌지 않는다. 해시는 연결의 대상 · 프로덕션 · read-only 표지도 덮는다(「권한 모델」 의 「승인은 계획의 해시에 묶는다」)
- 문장마다 결과 하나(열 · 행 또는 영향 행 수 · 소요)를 차례로 돌려주고 행 제한은 문장마다 건다. `db_query` 는 읽기 전용 트랜잭션 하나로 돌고, 문장 하나가 실패하면 거기서 멈추고 그때까지의 결과와 오류(문장 번호 · 위치)를 돌려준다. `db_execute` 는 호출 하나를 트랜잭션 하나로 묶고 문장 하나가 실패하면 롤백한다 — 암묵 커밋하는 문장이 있으면 승인 요청에 「되돌릴 수 없다」 를 보이고, 트랜잭션 안에서 못 도는 문장은 DB 의 오류로 끝난다(그것을 푸는 「트랜잭션 방식」 은 실행 구성 `sql` 종류의 것이다 — M6)
- **`db_query` 의 지금 구현**(16-m5-plan M5-07): 입력 `{ projectId, worktree?, connectionId, sql | file, maxRows? }`. `maxRows` 는 문장마다 돌려줄 행의 상한(기본 100, 1 ~ 10000)이고 쪽 단위가 아니다 — 잘린 문장은 `truncated` 이고 다음 쪽이 없다. 다시 부르면 다른 스냅숏이라 에이전트는 WHERE · LIMIT 로 좁혀 다시 부른다(메인 판정 2026-11-14 — 툴 메서드 규약의 `limit` 은 쪽 단위 툴의 것이라 이름을 가른다. `db_execute` 도 같은 이름을 쓴다). 관문은 M5-06 의 입구(`db_grant_for_agent`) 하나 → 연결의 드라이버 방언 → `file` 읽기 → 분류 → 조회가 아닌 문장이 있으면 연결을 열지 않고 `PERMISSION_DENIED`(`data.reason = "notAQuery"`, `data.statements` 는 그 문장들의 번호 · 범위 · 등급 · 까닭 — 결과 표지 `denied` · `permission_denied`, 오류 글에 첫 문장의 번호 · 줄 · 등급과 「쓰기는 `db_execute`」). 조회 판정은 `db.query.page` 와 같은 `is_strict_query` 다 — 부작용 함수(`nextval` · `pg_sleep` · pg_surgery `heap_force_kill` …) · `SET` · 트랜잭션 제어 · 파싱 실패 · `tooLarge` · SQLite `ATTACH` · `PRAGMA` 는 조회가 아니다. **한계**(리뷰 B1): 이 판정은 알려진 함수 목록이라(`pw_db_sql::risk` 의 `SERVER_ADMIN_FUNCTIONS` · `SIDE_EFFECT_FUNCTIONS` · `SQL_TEXT_FUNCTIONS` — 훑은 범위와 방법은 그 머리 주석: PG 17.6 의 contrib 전부 · MySQL 8.4 · MariaDB 11.8 · SQLite 의 내장 함수), 사람이 설치한 contrib 밖 확장의 C 함수가 읽기 전용 트랜잭션을 우회하면 막지 못한다. postgres_fdw 의 외부 표 읽기도 막지 못한다 — 원격 서버에서는 읽기 전용이 아닌 트랜잭션으로 돌아(PG 17 기준), 원격의 뷰 · 함수가 쓰면 쓰기가 남는다(분류기는 표가 외부 표인지 모른다. file_fdw 의 `program` 외부 표도 같다). 실행은 새 연결의 읽기 전용 트랜잭션 하나에서 차례로, 문장마다 결과 `{ index, line, grade, columns, rows, rowsAffected, truncated, elapsedMs }`, 실패하면 거기서 멈추고 `error { index, line, range, error }`. 셀은 4 KiB 에서 잘린다(`truncated` 값). 응답 예산 192 KiB(`pw_db::script::RESPONSE_BUDGET`)는 **행을 읽는 그때** 센다(리뷰 B2): 행의 JSON 크기를 더하다 넘는 순간 그 문장은 `truncated` 이고 커서를 버리며, 뒤 문장은 돌리지 않고 결과의 `notRun { index, line, count, reason: "responseBudget" }`(돌리지 않은 첫 문장과 그 뒤 문장 수)으로 알린다. 한 번에 읽는 몫도 남은 예산으로 줄여 Host 가 쥐는 행이 예산 몫(+ 한 묶음)에 머문다. 결과의 `audit` 은 감사 상세(「감사 로그」)다. 호출이 취소되면 그 연결에 드라이버 인터럽트를 보내고 롤백한 뒤 닫는다. 실행 파이프라인은 `pw_db::script` 이고 `db_execute`(M5-18)가 쓰기 갈래를 더한다
- **`db_kv_scan` · `db_kv_get` 의 지금 구현**(16-m5-plan M5-19 — 결정 M5-D7): 툴 메서드 `db.tool.kvScan` · `db.tool.kvGet`(`crates/pw-db/src/kv_tool.rs`), 둘 다 `read` · 그룹 `db` · 앱 Host 만. 입력은 `{ projectId, worktree?, connectionId, database?, match?, cursor?, limit? }` · `{ projectId, worktree?, connectionId, database?, key, cursor?, limit? }` 이고 **명령 칸이 없다**. 창의 세션 id 를 받지 않고 호출마다 자기 연결을 연다(M5-06 의 관문 `db_grant_for_agent` 를 지나고, `database` 입력도 관문에 넘긴다 — DB 번호마다 연결 하나). `db_kv_scan` 은 키 한 쪽(키 · 타입 · TTL · 크기)과 `nextCursor` 다 — 스트림 `db.kv.scan` 이 툴이 될 수 없어 `SCAN` 커서를 한 쪽씩 도는 unary 다. `limit`(1 ~ 500, 기본 100)은 쪽의 상한이고 `SCAN` 한 걸음이 혼자 더 준 때만 넘는다. 쪽이 비어도 `nextCursor` 가 있을 수 있다. **`SCAN` 의 중복은 한 쪽 안에서 거르고 쪽 사이에서는 그대로 준다**(툴 설명에 적는다 — 끝까지 있던 키는 빠지지 않는다). `db_kv_get` 은 값 한 쪽(타입별 — string 은 64 KiB 바이트 창, hash · set 은 스캔 쪽, list · zset 은 번호, stream 은 항목 id, RedisJSON 은 통째)과 타입 · TTL · `total` · `nextCursor` 이고, 없는 키는 `missing` 이다. 응답 예산은 `db_query` 와 같은 192 KiB 다 — 스캔은 넘칠 묶음을 다음 쪽으로 넘기고, 값은 쪽의 원소 수(string 은 창)를 줄이고, 그래도 넘치면 1 KiB 보다 긴 값을 같은 몫으로 앞부분만 남긴다(`truncated` — 몫이 1 KiB 아래여도 긴 값은 자르고, 감싸서 커지는 짧은 값은 자르지 않는다). 그래도 넘치면 뒤쪽을 덜고 결과의 `omitted { of, shown, total }` 에 남긴다: 필드가 아주 많은 스트림 항목 하나는 앞 필드만 싣고(`fields` — Redis 는 항목을 통째로 읽어 나머지 필드는 이 툴로 읽을 수 없다, `nextCursor` 는 다음 항목), Redis 가 한 걸음에 준 원소가 많은 hash · set 쪽은 앞 원소만 싣는다(`elements` — 덜어 낸 원소는 어느 쪽에도 나오지 않는다). 잘라도 하나도 들지 않으면 `shown: 0` 표지만 싣는다. **어느 경우든 `nextCursor` 는 이 쪽 뒤로 나아간다**(메인 판정 — 어떤 키 · 항목도 「읽을 수 없음」 으로 끝나지 않는다, 리뷰 F1 · D-F1). 거절은 예산 계산이 불가능한 꼴뿐이다 — 빈 쪽의 틀도 들지 않는 값 쪽, 키 이름 하나가 예산보다 큰 스캔 쪽(invalid params, `data.reason = "tooLarge"`). 그 거절에도 `data.nextCursor` 를 실어 그 뒤를 이어 읽는다(스캔은 그 `SCAN` 한 걸음의 키를 건너뛴다). 보내는 명령은 드라이버의 스캔 · 키 정보 · 값 읽기뿐이고(`SCAN` · `TYPE` · `PTTL` · `MEMORY USAGE` · 타입별 길이 · `GETRANGE` · `HSCAN` · `SSCAN` · `LRANGE` · `ZRANGE` · `XRANGE` · `JSON.GET`), 모두 분류기(`pw_db_sql::kv_command`)가 확인 없는 조회로 매긴다 — 연결을 열 때의 설정 명령(`AUTH` · `SELECT` · `CLIENT SETINFO` · `INFO server`)은 셈에 넣지 않는다(메인 판정 2026-11-17). 키 이름 · `match` 는 RESP 의 인자로만 간다(명령 글로 끼워 넣을 수 없다). 응답 타임아웃은 `[db] redis_response_timeout`. `db_schema` · `db_query` 는 Redis 연결에 `unsupported` 와 이 두 툴의 이름을 낸다
- **`db_execute` 의 지금 구현**(16-m5-plan M5-18 — 결정 M5-D4 · M5-D22 · M5-D35): 툴 메서드 `db.tool.execute`(`crates/pw-db/src/execute_tool.rs`), `dangerous` · 그룹 `db` · 앱 Host 만. 프리셋 `full` 이나 `[mcp.tools] db_execute = true` 에서만 보인다. 입력은 `db_query` 와 같고(`maxRows` 는 행을 내는 문장 — `RETURNING` · 조회 — 의 상한) 조회와 쓰기가 섞인 글도 받는다. 길은 M5-06 의 관문 → 방언 → `file` 읽기(한 번) → 분류 → **묻기 전의 거절** → 계획 → 승인 → 실행이다. 묻기 전에 거절하는 것(연결을 열지 않는다, `PERMISSION_DENIED`): 분류기가 읽지 못한 문장(파싱 실패 · `tooLarge` · `tooDeep` · 분류기가 못 읽은 읽기 — `data.reason = "unclassifiedStatement"`), 세션의 글 읽기를 바꾸는 문장(`changesSqlReading`), 트랜잭션 제어(`BEGIN` · `COMMIT` · `SAVEPOINT` · `SET TRANSACTION` 등 — `transactionStatement`), read-only 연결의 조회 밖 문장(`readOnlyConnection` — 표지는 그 대상에서 본 가장 엄한 것). 계획은 `PlanChange::Sql { connection { name, production, readOnly }, file? { path, sha256 }, statements [{ index, line, grade, text }], irreversible }` 이고(꼴은 메인 판정 2026-11-17 — 승인 다이얼로그와 함께 쓴다) 실제로 돌릴 문장 **전부**를 싣는다 — 부작용 함수 목록(`pw_db_sql::risk`)은 조회 판정용이라 이 툴에서는 모든 문장을 사람이 본다. 규칙은 매번(`auto_approve` 없음 · 기억 없음)이고, 해시는 연결 id · 워크트리 · 푼 대상 · 표지 · 방언을 덮는다(`pw_db::tool_plan`). 승인 뒤에는 그 호출에서 읽은 글을 돌린다 — `file` 을 다시 읽지 않고, 연결은 관문이 판정한 대상으로만 연다. 실행은 새 연결의 트랜잭션 하나: 모두 성공하면 커밋(`transaction: "committed"`), 문장 하나가 실패하면 그 자리에서 멈추고 롤백해 DB 의 오류를 그대로 돌려준다(`"rolledBack"`, `error { index, line, range, error }` — 트랜잭션 안에서 못 도는 PG `CREATE INDEX CONCURRENTLY` 도). 암묵 커밋 문장(MySQL · MariaDB 의 DDL 등과 안에서 커밋할 수 있는 `CALL`)이 있으면 계획 · 결과가 `irreversible` 이고, 그 문장이 트랜잭션을 끝내면 뒤 문장을 위해 새 트랜잭션을 연다(앞의 것은 커밋됐다). read-only 연결의 조회만 든 글은 읽기 전용 트랜잭션에서 돌고 롤백한다(`"readOnly"`). 결과는 문장마다 `db_query` 와 같은 꼴(쓰기는 `rowsAffected`)이고, 응답 예산은 읽는 그때 센다 — 다 써도 뒤 문장을 멈추지 않고(반만 돈 쓰기를 커밋하지 않게) 돌린 뒤 결과를 싣지 않고 `unlisted { index, line, count, rowsAffected }` 로 센다. DDL 등급 이상의 문장이 시작됐으면(실패 포함) 그 연결의 스키마 캐시를 버리고 `db.schemaChanged` 를 낸다. 감사 상세는 `db_query` 와 같고(SQL 원문 · 값 없음) 끝에 트랜잭션의 끝이 붙는다(아래). **취소**(메인 판정 2026-11-17): 문장이 도는 중에 호출이 취소되면 인터럽트 · 롤백 · 닫기다. 마지막 문장이 끝난 뒤 **커밋하기로 정하기 전에** 관측된 취소는 커밋하지 않고 롤백한다. 커밋하기로 정하는 자리에서 「되돌릴 수 없는 지점」 표지를 세우므로(「호출 취소」, 16-m5-plan M5-18b), 그 뒤의 취소는 커밋을 끊지 않고(인터럽트도 보내지 않는다) Host 는 커밋 결과로 답한다. **감사 행은 그 답으로 끝난다** — 결과 `ok`, 상세에 `transaction=committed` 와 「cancelled by the client after the point of no return」. 감사 상세는 끝까지 돈 호출이면 트랜잭션의 끝(`transaction=committed` · `rolledBack` · `readOnly`)을 늘 싣는다. **커밋이 실패하면** 결과 `error` 이고 둘로 갈린다(16-m5-plan M5-18b — 리뷰 F1): DB 가 COMMIT 을 거절했으면(지연 제약 위반 · SQLite `busy` 등 — 연결을 닫으면 트랜잭션이 버려진다) 상세 끝이 `transaction=rolledBack` 이고, **COMMIT 을 보낸 뒤 시한(10초)이 지났거나 연결이 끊겼으면 커밋됐는지 모른다** — 상세 끝이 `transaction=unknown` 이고 오류 글이 「commit sent, outcome unknown: … check with db_query before calling again」 이다(에이전트에게도 그 글이 간다). 「모름」 의 판정은 드라이버 오류의 종류다(시한 초과 · 끊김 · 중단 · 연결 — `rolledBack` 표시가 없을 때). 로그도 그때 「may or may not have committed」 라고 쓴다. **한계: 에이전트는 취소한 호출의 커밋 결과를 받지 않는다**(「호출 취소」 — rmcp 가 그 응답을 버린다) — 툴 설명은 에이전트에게 다시 부르기 전에 `db_query` 로 확인하라고 적는다. Host 가 5초 안에 답하지 않으면 감사 행은 취소이고 상세가 「커밋됐는지 모른다」 다. **연결 직전의 재확인**: 관문 · 승인 뒤 연결을 열 때 설정을 다시 풀어 대상과 표지를 판정한 것과 견준다 — 그사이(큰 SQL 의 분류 시간 등) 대상이 바뀌었으면 `notOpenedByUser`, 표지가 더해졌으면 `productionBlocked` · `readOnlyConnection` 이고 연결하지 않는다(승인 해시는 판정 때의 값이라 이 틈을 덮지 못한다). 외부 표(postgres_fdw 등)를 거치는 쓰기의 한계는 `db_query` 와 같다(결정 M5-D38)

### 체크아웃 (M7 — 원격과 함께 제공)

한 프로젝트의 체크아웃이 여러 머신에 있을 때(08-remote-mobile.md 「프로젝트와 체크아웃 (D57)」) 에이전트가 대상을 고른다.

| 툴 | 설명 | 권한 |
|---|---|---|
| `checkout_list` | 그 프로젝트의 체크아웃(머신 · 워크트리 · 브랜치)과 머신의 연결 상태 | read |
| `checkout_send` | 한 체크아웃의 브랜치를 다른 머신의 체크아웃으로 보내고 대상을 그 커밋으로 맞춘다(origin 을 거치지 않는다). 원본 · 대상을 받는다 — 가져오기는 둘을 바꿔 준 것이다 | write |

- **대상 지정**: 프로젝트 툴은 선택 입력 `checkout`(머신 + 워크트리)을 받는다. 없으면 세션의 체크아웃(`--project` · cwd 가 가리키는 그 머신의 체크아웃)이다. 선택 입력이라 그 전에 만든 툴과 하위 호환이다 — 프로젝트 툴과 그 RPC 의 입력은 struct 이고 워크트리를 선택 입력으로 받는 꼴을 지킨다(체크아웃을 보지 않고 프로젝트 레코드만 읽는 툴 `project_info` 는 워크트리 입력을 달지 않는다 — 입력이 struct 라 `checkout` 은 깨지 않고 더한다, 16-m5-plan 메인 판정 2026-11-13)
- **다른 머신을 겨눌 수 있는 것은 Desktop 의 세션뿐이다.** 묶음은 Desktop 만 안다 — Desktop 이 묶음을 풀어 그 머신의 Host 로 보낸다. 그 머신에 닿을 수 있으면 그때 연결을 열고(이미 열린 연결이 있어야 하는 것이 아니다), 승인을 물을 자리가 있어야 하므로 그 프로젝트의 창이 열려 있어야 한다. 창이 없거나 헤드리스면 거절한다
- **원격 머신 Relay 의 세션은 그 머신의 체크아웃만 다룬다.** `checkout` 에 다른 머신을 주면 거절하고 `checkout_send` 는 싣지 않는다. 원격 머신의 에이전트가 내 기기에 git 쓰기 · 실행을 하는 길을 열지 않는다 — 원격에서 만든 커밋을 로컬로 옮기는 것은 Desktop 쪽의 가져오기다
- `checkout_send` 는 git 쓰기를 툴로 내놓지 않는다는 규칙(「Git」 표)의 예외다. 에이전트가 git CLI 로는 다른 머신에 origin 없이 보낼 길이 없다. git 이 거절하면(갈라짐 · 대상의 커밋 안 한 변경) 덮지 않고 그 원문을 툴 오류로 돌려준다
- 로컬에서 쓰고 원격에서 테스트하는 흐름: 커밋 → `checkout_send` → 대상 체크아웃으로 `run_start` → `run_logs`. CLI 도 같다(`pitwall tool run_start --checkout …`)
- 승인은 「권한 모델」 의 「다른 머신을 겨누는 호출」, 감사 로그는 호출을 받은 쪽에 남고 인자 요약에 대상 체크아웃이 든다
- **지금 구현**(18-m7-plan M7-18 — `pw_mcp::checkout` · `pw_mcp::server`): 입력에 `worktree` 를 받는 툴의 스키마에만 선택 입력 `checkout { machine, worktree? }` 를 더한다(다른 머신을 아는 앱 세션에서만 — `project_info` 에는 없다). `machine` 은 Pitwall 의 머신 이름(원격 호스트 항목 이름 — 처음 붙을 때 기억한 머신 id 로 잇는다)이나 머신 id, 이 머신은 `local`. 세션이 `checkout` 을 떼고 묶음(`projectId` — 로컬 프로젝트 id 나 묶음 id)을 풀어 그 머신의 프로젝트 id 와 `worktree` 로 바꿔 보낸다 — 다른 머신의 프로젝트 id 를 `projectId` 로 주면 그 머신에 붙지 않고 거절한다. `checkout` 없이 묶음 id 를 주면 그 묶음의 이 머신 멤버다. 다른 머신 호출은 읽기도 그 묶음의 이 머신 멤버 창이 열려 있어야 하고(듣는 창이 없거나 이 머신 멤버가 없는 묶음이면 `machine_unavailable`), 그 머신의 프로젝트 설정(노출 · 정책)은 이 세션이 읽지 않는다. 링크가 없으면 **사람에게 묻지 않고 붙을 수 있을 때만** 연다 — ssh 공유 연결이 살아 있을 때(`remote.hosts.check` 와 같은 확인)이고, 처음 보는 머신 · 사람이 끊어 둔 호스트 · 다른 머신이 답한 호스트 · 누가 붙는 중인 호스트는 「Pitwall 에서 먼저 연결」 로 거절한다(메인 판정). 감사 행은 이 Desktop 의 감사에 프로젝트 = 묶음의 이 머신 멤버로, 인자 요약의 `checkout` 에 머신 id · 워크트리가 든다. `project_list` 는 묶음에 든 프로젝트에 `bundleId` · `checkouts`(머신 id · 이름)를 싣고, 이 머신 체크아웃이 없는 묶음을 `id` 가 묶음 id 인 항목으로 덧붙인다. CLI 는 `--checkout <machine>:<path>`(경로 없이 `<machine>` 이면 그 머신의 메인 체크아웃, 경로는 그 머신의 것이라 `~` 도 펼치지 않는다)

### 툴 레지스트리 (RPC → 툴)

툴은 손으로 등록하지 않고 RPC 선언(`rpc_method!`)에서 만든다. 구현: `crates/pw-mcp/src/catalog.rs`.

- **노출은 선언이 고른다**: `rpc_method!` 의 선택 필드 `mcp`(`mcp: true` 또는 `mcp: { group, name }`)를 단 메서드만 툴이 된다. 생략하면 꺼짐 — **새 RPC 는 말없이 툴이 되지 않는다**(UI 전용 메서드 `host.demoTask` · `project.markOpened` · `i18n.setLanguage` 등). 툴이 되는 메서드의 고정 목록은 모든 메서드 크레이트가 링크되는 데스크톱 크레이트의 `mcp_tools_are_exactly_these`(`apps/desktop/src-tauri/src/mcp_tests.rs`)가 Host 종류별 목록 둘(앱 · 헤드리스 — 헤드리스는 앱의 부분집합)로 지킨다 — 어느 크레이트의 선언에 `mcp` 를 달아도 거기서 실패하므로, 툴을 늘리려면 선언과 그 목록을 함께 고친다. 스트림 메서드에는 달 수 없다(컴파일 오류)
- **세션의 툴은 그 Host 가 처리하는 것만**: 카탈로그는 실행 파일에 링크된 선언에서 만들고, 세션을 여는 Host 의 라우터가 가진 메서드로 거른다. 헤드리스 Host 는 코어 메서드만 등록하므로 다른 크레이트의 툴이 생겨도 헤드리스 `tools/list` 에는 나오지 않는다
- **role 은 노출을 정하지 않는다**: role 은 「어느 기기가 부를 수 있나」다. MCP 세션은 Host 에 **owner** 로 붙고(로컬 소켓 · stdio 로만 오는 이 사용자의 프로세스다), 부를 수 있는지는 「툴 노출 설정」 → 「권한 모델」 절이 정한다. 세션은 **제 연결 범위**로 붙는다 — 창 범위가 필요한 RPC(쓰기 · 실행 · DB)는 MCP 세션을 거절하고, 툴 메서드만 MCP 세션용 관문을 받는다([03-architecture.md](03-architecture.md) 「RPC 설계」 의 연결 범위).
- **이름**: 선언이 `mcp` 에 이름을 적으면 그 이름, `mcp: true` 면 RPC 이름의 `.` → `_`, camelCase → snake_case(`project.list` → `project_list`, `project.markOpened` → `project_mark_opened`). `[a-z0-9_]` 64자 이내, 겹치면(적은 이름이 다른 선언의 규칙 이름과 겹쳐도) 시작 시 실패
- **그룹**: 선언의 `mcp` 가 툴 이름과 함께 싣는다(`mcp: { group: "code", name: "diagnostics" }`). `mcp: true` 면 RPC 이름의 첫 마디를 snake_case 로 옮긴 것이다(`openWith` → `open_with`). 「툴 노출 설정」 의 그룹 이름(`pw_mcp::catalog::GROUPS`)만 받고, 그 밖이면 시작 시 실패
- **툴 메서드**: 이 문서의 툴과 이름 · 등급 · 꼴이 다른 RPC 에는 `mcp` 를 달지 않고 그 기능 크레이트에 툴 메서드를 따로 선언한다 — 같은 내부 함수 · 같은 관문을 부르는 얇은 선언이다(16-m5-plan 결정 M5-D26). UI 가 쓰는 RPC 는 화면에 맞춘 꼴이고 등급도 다르다. 툴의 등급은 그 선언의 `tier` 이고, 감사 행에 남길 상세는 결과 · 오류 `data` 의 최상위 `audit` 글로 싣는다(「감사 로그」 의 「툴 메서드 규약 — 감사 상세」), 프로젝트 툴의 입력은 struct 에 선택 입력 `worktree` 를 둔다(「체크아웃」 — 프로젝트 레코드만 읽는 툴은 뺀다). 쪽 단위 툴은 선택 입력 `cursor` · `limit` 을 둘 다 받고 결과에 `nextCursor`(없으면 마지막 쪽)를 싣는다. 규약은 `crates/pw-mcp` 머리 주석, 시험은 `tools_follow_the_tool_method_convention`
- **설명 · 등급**: 선언의 문서 주석과 `tier`. `read` 툴에는 `readOnlyHint` 를 단다
- **입력 스키마**: 입력 타입의 schemars 스키마를 루트로 펼친다. struct 만 툴이 된다(MCP `inputSchema` 는 object). `()` 입력은 빈 object 로 내보내고 RPC 에는 `null` 을 보낸다. enum 루트는 툴로 만들 수 없다
- **출력**: 결과 스키마의 루트가 object 면 `outputSchema` 와 `structuredContent`, 아니면(배열 등) JSON 텍스트만
- **결과 표지**: `tools/call` 결과의 `_meta` 에 결과(`ok` · `error` · `denied`)와 까닭 코드를 싣는다(취소는 거절이 아니라 결과 `error` 의 까닭 `cancelled` 다 — 감사 로그와 같다). 키는 `pitwall/outcome`(감사 로그 `outcome` 의 `ok` · `error` · `denied` — 감사 행의 넷째 값 `started` 는 표지에 없다)과 `pitwall/reason`(까닭이 없으면 키가 없다). 노출 안 된 툴 호출(JSON-RPC invalid params)은 오류의 `data` 객체에 같은 두 키를 싣는다. CLI 의 종료 코드가 이것을 읽는다(「CLI」). 구현과 읽는 쪽: `pw_mcp::marker`(`Mark::read` — 모르는 까닭 코드는 까닭 없음으로 읽어 결과 값으로는 계속 가른다). 다른 행이 코드를 더하면 아래 표에 한 줄을 더한다

  **툴의 Host RPC 가 `PERMISSION_DENIED` 로 답하면 결과는 `denied` 다**(메인 판정 — 16-m5-plan M5-06): 까닭은 `data.reason`(camelCase)을 위 표의 코드로 옮긴 것이고(대응은 `pw_mcp::marker::Reason::of_permission_denied` 한 곳), 모르거나 없으면 `permission_denied` 다. 거절 까닭을 더하는 행은 `Reason` 과 그 대응에 한 줄씩 더하고 이 표에 한 줄을 더한다. `PERMISSION_DENIED` 가 아닌 오류(비밀 · 확인이 필요하다는 DB 의 3101 · 3102 등)는 `error` 다. 까닭이 없는 `error` 는 툴(Host RPC)이 실패한 것이다
- **응답 크기**: 툴 응답 한 건은 직렬화한 결과 JSON 256 KiB 까지(`pw_mcp::server::MAX_RESPONSE_BYTES`), 목록 툴의 `limit` 기본은 100(`DEFAULT_LIST_LIMIT` — `git_log` · `symbol_search` 50, `git_status` 200. 16-m5-plan 결정 M5-D34, 수는 출발값). 툴 메서드는 넘지 않게 자르고(`truncated` 와 다음 `cursor`), 그래도 넘은 응답은 세션이 결과 대신 「범위를 좁혀라」 오류(까닭 `too_large`)로 바꾼다. 재는 것은 Host RPC 의 결과 값이다 — object 결과는 `structuredContent` 와 `content` 의 텍스트로 두 번 실려 나가므로 클라이언트가 받는 글은 그 두 배를 넘을 수 있다. 감사 행은 결과 `error` 이고 크기 열에 넘은 크기를 남긴다
- **프로젝트 지정**: 입력에 `projectId` 가 있으면 프로젝트 툴이다. 세션에 프로젝트가 있으면(`--project` · cwd) `projectId` 를 필수에서 빼고 빠지면 서버가 채운다. 입력에 `worktree` 가 있고 비었으면(없음 · `null` · 빈 글자열) 세션의 활성 워크트리 꼭대기(`project.resolve` 의 `worktree.top`)로 채운다(세션을 연 경로가 미등록 워크트리 안일 때 — Orca 워크트리 안의 에이전트가 메인 체크아웃이 아니라 자기 워크트리를 본다). 준 값은 덮지 않고, 호출이 세션 프로젝트가 아닌 `projectId` 를 겨누면 채우지 않는다 — 세션의 워크트리는 세션 프로젝트의 것이다
- **지금 툴**: `project_list`(← `project.list`), `project_info`(← `project.info`: 프로젝트 · 루트 폴더 유무 · 빌드 파일 · 빌드 파일에서 짐작한 언어 · 설정 폴더와 그 안의 설정 파일 id. 설정 내용은 읽지 않는다 — 읽으면 구버전 파일의 마이그레이션이 따라와 조회 툴이 저장소를 고친다), `git_status` · `git_log` · `git_diff` · `git_blame` · `git_branch_list`(← `git.tool.*` 툴 메서드, 앱 Host 만 — 「Git」 절), `db_connection_list`(← 툴 메서드 `db.tool.connectionList`) · `db_schema`(← 툴 메서드 `db.tool.schema`) · `db_query`(← 툴 메서드 `db.tool.query`) · `db_kv_scan`(← 툴 메서드 `db.tool.kvScan`) · `db_kv_get`(← 툴 메서드 `db.tool.kvGet`) — 다섯 다 앱 Host 만, 「DB」, `settings_get`(← 툴 메서드 `config.tool.get`, 코어 툴) · `open_with_list`(← `openWith.list`, 앱 Host 만) · `project_open`(← 툴 메서드 `project.tool.open`, 앱 Host 만 — 「프로젝트」 · 「외부 도구」 표 아래 「지금 구현」)
- MCP 메시지(툴 설명 · 오류)는 번역하지 않는다
- **툴 설명 · 스키마 설명 · 툴의 오류 문장은 영어다**(사용자 결정 2026-11-17 — 에이전트가 읽는 글, 16-m5-plan 결정 M5-D39). 입출력 스키마의 설명은 `rpc_method!` 선언과 입출력 타입(그 타입이 쓰는 타입 포함)의 문서 주석에서 오므로 그 문서 주석을 영어로 쓴다. `apps/desktop/src-tauri/src/mcp_tests.rs` 의 `tool_descriptions_and_schemas_are_english` 가 툴 설명 · 입력 · 출력 스키마의 한글을 잡는다 — 툴이 런타임에 내는 오류 · 안내 글은 이 시험이 보지 않는다

## 3. 권한 모델

| 등급 | 예 | 기본 정책 |
|---|---|---|
| `read` | 조회 전부 | 자동 허용 |
| `write` | 설정 파일 변경 | **UI 승인** (diff 미리보기). "이 세션 동안 허용" 옵션 |
| `exec` | 프로세스 실행 | 신뢰된 프로젝트 + 이미 존재하는 구성(사람이 본 내용 해시 — 06-roadmap.md 결정 D68): 자동 / 방금 생성·수정된 구성: 승인 (`sql` 종류 구성은 이 줄이 아니라 실행 시점의 SQL 분류를 따른다 — 「실행 구성」 표 아래) |
| `dangerous` | DB 쓰기 쿼리, 프로덕션 태그 연결 접근 | 매번 승인, 프로덕션은 기본 차단 |

- 정책은 **사람의 설정(전역 · `.pitwall/*.local.toml` · 개인 전용 `project.toml`)** 에서 조정한다. `[mcp.policy]` 의 키는 둘이다 — `approval_timeout_secs`(승인 시한, 기본 300), `production`(프로덕션 태그 연결 — `block` 기본 · `ask`. 「DB」 표 아래 「에이전트의 DB 연결」). **커밋되는 공유 설정(`.pitwall/project.toml`)의 `[mcp.policy]` 는 읽지 않는다** — 효과가 없고 경고를 남긴다. 저장소를 클론해 연 것만으로 프로덕션 차단이 「매번 승인」 으로 풀리거나, 승인 시한이 줄어 모든 승인이 거절되는 일이 없게 한다. 그래서 `production = "ask"` 는 사람의 설정에서만 켠다(16-m5-plan 결정 M5-D31)
- **git 이 추적하거나 받아 온 `.local.toml` 은 사람의 설정이 아니다**(17-m6-plan m6-localpolicy, 메인 판정 2026-11-18): 저장소가 `.pitwall/**/*.local.toml` 을 강제로 커밋하면(또는 브랜치의 그 파일이 워크트리에 체크아웃되면) 클론 · 새 워크트리에서 남이 쓴 파일이 「사람의 설정」 으로 읽혀 `auto_approve` · `[mcp.policy]` · 노출을 넓힐 수 있었다. 그래서 **인덱스에 있거나 그 내용이 객체 DB 에 있는 개인 파일은 공유 레이어로 읽는다** — 인덱스에 있다는 것은 파일 자신이나 조상 경로가 인덱스 항목(커밋된 링크 `.pitwall`, sparse 폴더)이거나 링크를 지나 닿는 파일이 추적 파일인 것이고, 내용이 객체 DB 에 있다는 것은 git 이 받아 온 내용이라는 것이다 — checkout 이 중간에 실패한 클론 · pull · 브랜치 전환(git-lfs 의 받기 실패 등)은 커밋된 파일을 쓰고 인덱스에 올리지 못한다(리뷰 F1). 내용 판정의 오탐은 git 이 한 번이라도 저장한 내용과 바이트가 같은 개인 파일뿐이다(실수로 `add` 했다가 `rm --cached` 한 직후, 커밋된 `project.toml` 과 같은 `schema = 1` 한 줄) — 좁히는 쪽이고 고치면 풀린다 — 공유 설정 규칙 그대로 좁히기만 하고(`auto_approve` 는 상한 안에서만, `[mcp.policy]` 는 효과 없음), 사람의 화면(MCP 설정 창의 프로젝트 칸 경고 · 앱 로그)에 「git 이 추적하거나 받아 온 파일이라 공유 설정으로 읽었다 — `git rm --cached` 로 풀고 고치면 개인 설정」 을 알린다. **판정을 못 하면**(관리 폴더 · 인덱스 · 객체 DB · 대체 저장소(alternates)를 읽지 못함, SHA-1 이 아닌 저장소, `core.worktree` 가 다른 폴더, 인덱스가 없는데 HEAD 가 커밋을 가리킴 — 실패한 클론의 꼴, reftable 저장소, 그리고 객체가 다 있다고 할 수 없는 shallow · partial clone 저장소에서 인덱스에 없는 파일) 역시 공유 레이어다(fail-closed). `.git` 이 없는 폴더와 갓 `git init` 한 저장소(인덱스도 커밋도 없음)는 추적 파일이 없으므로 사람의 설정이다 — `.git` 없이 받은 압축본에 든 개인 파일은 가릴 수 없다. 연결 워크트리 · 서브모듈 · bare 저장소의 워크트리는 각자의 인덱스로 본다 — 워크트리의 추적 파일은 메인 체크아웃의 사람 파일(파일 단위 폴백)을 가리지 않고, 메인 체크아웃의 추적 파일은 폴백으로 읽지 않는다. Pitwall 은 추적 파일에도, 받아 온 내용의 파일에도 개인 값을 쓰지 않는다(`ConfigSource::prepare_local_write` 가 거절 — 받아 온 파일에 키 하나를 쓰면 내용이 바뀌어 그 안에 남은 남의 값까지 사람의 설정이 되므로, 사람이 손으로 보고 고친다). 세션의 노출은 `.pitwall` 감시(`config.changed`) 때뿐 아니라 `tools/list` · `tools/call` 마다 블로킹 스레드에서 다시 읽는다 — 인덱스만 바뀐 경우(`git add -f` · 체크아웃이 인덱스를 마지막에 쓰는 사이)는 `.pitwall` 에 이벤트가 없어서다(17-m6-plan M6-12 ⑥, `pw_mcp::server` 의 `ExposureFeed`). 바뀌었으면 `tools/list_changed` 도 나간다. 판정은 설정 계층이 레이어를 나눌 때 하므로 정책 · 노출 · `settings_get` 의 레이어 표시 · 미신뢰 프로젝트의 언어 서버 설정(03 「`[lsp.<서버 id>]`」)이 같은 규칙을 받는다. 구현: `pw_core::config::tracked`(git 을 띄우지 않고 `gix-index` 로 인덱스를, `gix-odb` 로 객체 DB 를 읽는다 — 읽은 경로 집합은 인덱스 끝의 체크섬을 열쇠로 캐시한다), 알림 `ConfigNotice::TrackedLocal` · `UnverifiedLocal`
- **프로젝트 설정을 읽지 못하면 그 프로젝트의 정책은 전역으로 떨어지지 않는다**(fail-closed — 17-m6-plan M6-01 리뷰 1, 메인 판정 2026-11-18): 그 프로젝트의 설정 파일 가운데 어느 레이어든(`.pitwall/project.toml` · `db/*.toml` · `*.local.toml`, 개인 전용 폴더의 것) 읽기 · 파싱에 실패하면(대상 없는 링크 — 옮겨진 dotfiles — 와 크기 상한 1 MiB 를 넘는 파일도 실패다, `pw_core::config::robust::MAX_CONFIG_BYTES`) `auto_approve` · `[mcp.policy]` 를 정할 수 없다. 전역으로 떨어지면 커밋된 공유 파일 하나를 깨뜨려 사람이 `.local.toml` 에 둔 좁히기(`auto_approve` · `production = "block"`)를 풀 수 있다. 그래서 MCP 세션은 그 프로젝트를 겨누는 에이전트 호출을 등급과 상관없이(`read` 포함) 툴을 부르지 않고 거절한다 — 결과 표지 `denied` · `project_config_unreadable`(「툴 레지스트리」 의 까닭 표), 에이전트에게 가는 글에는 파일 내용을 싣지 않는다. DB 툴의 관문(정책 읽기 · 연결 설정 읽기)도 같은 거절이다 — `PERMISSION_DENIED`, `data.reason = "projectConfigUnreadable"`. 연결 목록(`db_connection_list`)도 빈 목록이 아니라 그 거절이다. 사람의 화면(MCP 설정 창의 프로젝트 칸 · DB 연결 목록)은 읽지 못한 파일과 까닭을 그대로 보인다. 실행 구성(`run/*.toml`)은 이 판정에 들지 않는다 — 정책이 없는 파일이고, 구성마다 따로 읽어 깨진 것만 「쓸 수 없음」 이다(03-architecture.md 「설정 계층」). 구현: `pw_core::config::mcp_policy::ProjectConfigUnreadable`(읽는 함수 `read_project` 가 낸다), `pw_mcp::server` 의 호출 앞 판정, `pw_db::gate` 의 `production_policy` · `settings_unreadable`
- **「이 세션 동안 허용」** 은 그 세션 · 그 프로젝트 · 그 툴 · 그 계획 등급에 한한다(계획 등급은 17-m6-plan M6-10). `open_with_upsert` 에는 없다 — 명령을 정의하는 쓰기라 정의마다 사람이 본다. CLI 호출의 승인에서는 그 자리가 「이 프로젝트 창이 열려 있는 동안 CLI 허용」 이다(「CLI」). `run_start` · `run_restart` 는 그 구성의 그 내용에 한한다(17-m6-plan M6-14 ⑧ — 열쇠 `<구성 열쇠>@<내용 해시>`, 사람이 띄운 실행의 `run_restart` 는 `human:<runId>:<내용 해시>` 로 그 실행 하나의 그 내용)
- **승인은 계획의 해시에 묶는다**: 승인을 청하는 툴 메서드는 실행 전에 계획(등급 · 요약 · 바뀔 것 — 파일 diff 나 SQL 문장들)을 만들고, 승인은 그 해시에 묶인다. 해시는 툴 이름 · 서버가 채운 뒤의 입력 전체 · 툴이 더하는 대상 값(DB 는 연결의 푼 대상 · 방언 · 프로덕션 · read-only 표지, 파일을 고치는 툴은 고치기 전 파일 내용)을 덮는다. 실행 때 계획을 다시 만들어 해시가 다르면 돌리지 않는다. 해시를 싣는 자리는 툴 입력 스키마에 없다 — 에이전트가 승인을 스스로 실을 수 없다
- **다른 머신을 겨누는 호출**(「체크아웃」 의 `checkout` 입력 — M7): 등급 규칙은 같고 `exec` 의 「신뢰된 프로젝트」 는 대상 머신의 신뢰를 본다. **`auto_approve` 는 다른 머신을 겨누는 호출에 적용하지 않는다.** 정책 자동(툴이 판정한 자동 — 사람이 본 실행 구성 등, 17-m6-plan M6-10)도 다른 머신을 겨누는 호출에 적용하지 않는다. 머신 허용은 자동을 넓히지 않는다 — 미신뢰 대상 · `dangerous` · 사람이 띄운 실행의 `run_stop` · `run_restart`(D69) · 호출마다 승인을 청하는 툴은 머신 허용 뒤에도 묻는다(18-m7-plan 결정 M7-D9). 그 세션에서 어느 머신을 처음 겨누는 `write` · `exec` 호출은 승인을 묻고, 사람이 「이 세션 동안 이 머신 허용」 을 고르면 그 세션의 그 머신에 한해 다시 묻지 않는다(CLI 호출에서는 「CLI」 의 창 단위 허용과 같은 꼴이다 — 06-roadmap.md 결정 D61). 대상이 미신뢰 체크아웃이면 세션 허용과 상관없이 매번 묻는다. `dangerous` 는 매번이다
  - **지금 구현**(18-m7-plan M7-18 — `pw_mcp::server` 의 `approve_remote`): 답 `McpApprovalAnswer::Machine` 이 「이 세션 동안 이 머신 허용」(CLI 면 「창이 열려 있는 동안 CLI 에 이 머신 허용」 — 허브가 (프로젝트 창, 머신)으로 기억한다)이다. 닿는 것은 그 머신의 **신뢰한 프로젝트**(그 머신의 `project.trust` — 읽지 못하면 미신뢰)의 `write` · `exec` 계획 가운데 계획 규칙이 `auto_approve` 를 막지 않고(사람이 띄운 실행 — D69) 기억할 수 있는(`remember` 가 `never` 가 아닌) 것뿐이다. 원격이 낸 계획의 `policyAuto` · `auto_approve` 는 넓히는 데 읽지 않는다(M7-P19 — 좁히는 쪽만 쓴다). 호출마다 청하는 승인(`read` 계획 — 「이 연결 열기」 · 프로덕션 `ask`)은 지금 규칙대로 그 열쇠의 세션 허용을 받되 열쇠에 머신이 들어 이 머신 허용과 서로 닿지 않는다. 다이얼로그 · 「승인 대기」 는 대상 머신을 이 Desktop 의 별명으로 보인다(요청의 `machine` 은 머신 id). 감사의 승인 방식은 `session`(CLI 는 `window`)이다 — 대상 머신은 같은 행의 인자 요약에 있다(승인 방식 열의 `CHECK` 를 넓히는 감사 파일 이전은 하지 않았다). 프로젝트 창은 활성 체크아웃과 무관하게 창의 이 머신 연결 · 이 머신 프로젝트 id 로 이 Desktop 의 승인을 듣는다
  - **Why:** 로컬에서 쓰고 원격에서 테스트하는 되풀이를 에이전트가 하면 매번 승인은 쓸 수 없고, 로컬과 같은 자동 승인은 사람이 본 적 없는 커밋이 승인 없이 다른 머신에서 도는 길을 연다. 미신뢰 프로젝트에서도 git 쓰기가 되는 근거는 「사람이 누른 것」(06-roadmap.md 결정 D43)이고 에이전트의 호출에서는 승인이 그 자리를 맡는다
- **지금 구현**(16-m5-plan M5-12 — `pw_mcp::policy` · `pw_mcp::approval` · `pw_mcp::server`, 계획의 꼴은 `pw_core::registry::plan`): `read` 는 허용한다. `write` 이상과 툴이 호출마다 청하는 승인은 **두 단계**다 — 세션이 승인 표 없이 툴을 부르면 툴은 부작용 없이 계획을 만들어 「승인 필요」(`pw-mcp` 오류 6001, `data` 에 계획)로 답하고, 세션이 `auto_approve` · 세션 허용 · CLI 허용을 보거나 대상 프로젝트 창에 물은 뒤 승인 표(해시)를 입력의 예약 키 `pitwall/approval` 에 실어 다시 부른다. 툴은 계획을 다시 만들어 해시가 같을 때만 돌고, 다르면 세션은 다시 묻지 않고 `plan_changed` 로 거절한다. **`approve` 를 지난 뒤의 부작용은 계획을 만들 때 읽은 값(해시에 넣은 값)으로 한다 — 다시 읽지 않는다**(파일은 쓰기 직전에 내용이 그 값인지 비교한다). 세션은 받은 계획이 그 툴의 것인지 본다 — 계획의 메서드가 그 툴의 RPC 가 아니거나 등급이 선언 등급보다 높거나 `dangerous` 계획이 정책 자동을 달면 묻지도 돌리지도 않고 결과 `error`(툴의 버그)다. **승인 판정의 등급은 계획 등급이다**(선언 등급은 상한 — 넘으면 툴의 버그로 거절. 노출 · 프리셋 · 헤드리스 거절 · `readOnly` 표지는 선언 등급이다 — 17-m6-plan M6-10, 결정 M6-P9). 계획의 규칙 `policyAuto` 는 툴이 05 의 규칙(`exec` 의 신뢰 + 사람이 본 구성, `sql` 구성의 조회만)으로 묻지 않아도 된다고 판정한 것이다 — 세션은 묻지 않고 승인 표를 실어 다시 부르며 감사 행의 승인 방식은 `policy` 다(두 단계 · 선기록 · 해시 재확인은 그대로). `dangerous` 계획에는 둘 수 없다. 지금 계획을 내는 M5 툴은 모두 계획 등급이 선언 등급과 같아 이 판정으로 넓어지지 않는다 — 세션이 그것을 강제한다: 선언보다 낮은 계획 등급은 낮춤 목록(`pw_mcp::catalog::LOWERED_PLAN_TIERS` — 툴 이름 → 낼 수 있는 낮은 등급, 지금은 비었다)에 있는 툴 · 등급만 받고, 그 밖의 낮춤은 툴의 버그로 거절한다. 계획을 내는 툴마다 (선언 등급, 계획 등급)을 적은 회귀 표 시험이 목록과 맞춰 본다. 세션 허용 · CLI 허용의 단위에는 계획 등급도 든다 — 같은 툴이라도 낮은 계획에 준 허용은 다른 등급의 계획에 닿지 않는다. 에이전트가 프로세스를 띄우는 길은 승인을 지난 계획에 실린 실행 내용(`RunSpec`)을 `pw_core::registry::exec::agent_run_grant` 의 허가로 띄우는 것 하나다(17-m6-plan 결정 M6-P10). 예약 키는 툴 입력 스키마에 없고(입력 타입 `Planned` 의 스키마는 감싼 타입 그대로) 에이전트가 보낸 같은 키는 세션이 맨 앞에서 버린다. 「승인 필요」 오류와 계획은 에이전트에게 나가지 않는다. **`write` 이상 툴은 계획을 만들어야 한다** — 입력이 `Planned` 가 아니면 카탈로그가 시작 때 실패한다(`CatalogError::Unplanned`). `auto_approve` 는 등급 목록이고(`dangerous` 는 버리고 경고), 공유 레이어까지 읽은 값과 공유 레이어를 뺀 값에 둘 다 있는 등급만 자동이다. 계획이 `auto_approve` 를 끌 수 있다(`open_with_upsert` · 「이 연결 열기」). 「이 세션 동안 허용」 은 (그 세션, 그 프로젝트, 그 툴 — 계획이 열쇠를 정하면 그 툴의 그 열쇠)이고 다른 툴에는 닿지 않으며 `dangerous` · 기억하지 않는 계획에는 없다. CLI 호출(클라이언트 이름 `pitwall-cli`)은 셋째 답이 「창이 열려 있는 동안 CLI 허용」 이고 그 프로젝트를 듣는 창이 모두 닫히면 사라진다. `[mcp.policy]` 는 사람의 설정에서만 읽고(`approval_timeout_secs` · `production` — 읽는 함수는 `pw_core::config::mcp_policy` 하나이고 DB 툴의 관문도 그것을 부른다, 메인 판정 2026-11-17 · M5-18), 공유 `project.toml` 의 그 표는 경고만 남긴다. 모르는 `production` 값은 `block` 으로 읽고 경고한다. 판정은 대상 프로젝트의 설정이다(프로젝트 없는 호출은 전역). 헤드리스는 `write` 이상을 툴을 부르지 않고 거절한다(`headless_write`)
- 모든 MCP 호출은 감사 로그에 기록 → UI "에이전트 활동" 패널(지금 구현 — 16-m5-plan M5-13, 10-ui.md 「2.5 주요 툴 윈도우 상세」 의 「에이전트 활동」)

### 감사 로그

- **한 파일 `$STATE/mcp/audit.db`(SQLite)** 에 `project_id` 열을 둔다. 프로젝트를 정하지 않는 호출(`project_list`)은 `project_id` 가 `NULL` 이다. 프로젝트마다 파일을 두지 않는 이유: 어느 프로젝트에도 속하지 않는 호출이 있고, `$STATE` 가 감사 기록의 자리이며([03-architecture.md](03-architecture.md) 「데이터 저장」 표), 보관 기간 정리가 한 곳에서 끝난다. 「에이전트 활동」 패널은 `project_id` 로 거른다
- 파일 0600, 새로 만드는 폴더 0700(이미 있는 폴더의 권한은 바꾸지 않는다). 툴 이름은 64자, 오류 · 거절 이유는 512자까지 남긴다(노출 안 된 툴 호출은 클라이언트가 보낸 이름을 그대로 남기므로)
- 한 행 = `tools/call` 하나: 시각 · 세션 id · 클라이언트(`clientInfo` 이름 버전) · 프로젝트 · 툴 · 인자 요약 · 결과(`ok` · `error` · `denied` · `started`) · 오류나 거절 이유 · 결과 크기(바이트) · 소요(ms). **결과 내용은 남기지 않는다.** 노출되지 않은 툴 호출도 `denied` 로 남는다. `write` 이상의 호출(과 승인을 지난 호출)은 실행 전에 행을 `started` 로 쓰고 끝나면 같은 행을 고친다 — 끝을 못 쓴 행은 `started` 로 남는다. 승인을 지난 호출은 승인 방식(`auto` · `once` · `session` · `window`)과 계획 해시를 남긴다(`approval` · `plan_hash` — 승인 경로가 선기록하는 행에 쓴다, 16-m5-plan M5-12). 승인 방식 `policy` 는 툴이 05 의 규칙(사람이 본 실행 구성 · `sql` 구성의 조회만)으로 묻지 않은 호출이다(17-m6-plan M6-10 — 감사 파일 셋째 판)
- **인자 요약**: 키를 단어로 갈라(camelCase · `_` · `-`) `password` · `secret` · `token` · `key` · `auth` · `credential` · `cookie` · `private` 등이 있으면 값을 `[redacted]` 로 바꾼다. 글자열은 80자, 배열은 8개, 깊이 3, 전체 1024바이트까지. 키 이름으로 못 거르는 비밀이 남을 수 있으므로 비밀을 툴 인자로 받지 않는다는 규칙(`db_connection_upsert`)이 첫 방어선이다. 목록은 `pw_mcp::audit::SECRET_WORDS`. `db_query` · `db_execute` 는 SQL 원문 대신 문장 수 · 가장 높은 등급 · 문장 해시(`file` 이면 경로와 내용 해시)를 상세 칸에 남긴다 — 글자열 상한이 원문을 자르기 때문이다(16-m5-plan M5-07. 꼴은 `statements=2 grade=read sql=sha256:… file=queries/a.sql content=sha256:…`). 「원문 키」 는 인자 요약에서 값 대신 글자 수(`[<n> chars]` — 글자열이 아니면 `[not shown]`)만 남는다(`pw_mcp::audit::CONTENT_WORDS` — 키를 단어로 갈라 `sql` · `command` · `args` · `env` 가 있으면. 비밀 키이기도 하면 `[redacted]` 가 앞선다). `sql` 은 SQL 원문(16-m5-plan M5-07 리뷰 F1), `command` · `args` 는 명령줄 원문(`open_with_upsert` 의 argv, `run_config_upsert` 의 셸 명령 · 인자), `env` 는 env 의 값(구성의 `env` 표 · `envFile`)이다(17-m6-plan M6-13, 메인 판정 2026-11-18). **툴 메서드 규약 — 감사 상세**(메인 판정 2026-11-14): 툴이 결과(object)의 최상위 `audit` 칸에 글을 실으면 세션이 그 글을 성공 행의 상세 칸에 넣고, 오류 · 거절이면 오류 `data`(object)의 최상위 `audit` 을 「오류 글 · 상세」 로 넣는다(그때 `data` 를 통째로 싣지 않는다 — 서버 오류 글의 값이 섞인다). 상세 상한 512자에서 잘린다. 결과에 남으므로 에이전트에게도 보인다 — 원문 · 값 · 비밀을 넣지 않는다(`pw_mcp::server::AUDIT`, `crates/pw-mcp` 머리 주석). 칸이 없는 툴은 성공 행의 상세가 비고 오류 행은 오류 글 그대로다
- 여러 프로세스(앱, 헤드리스 `pitwall mcp` 여럿)가 같은 파일에 쓴다(`BEGIN IMMEDIATE`, 2초 대기). 기록이 실패해도 `read` 호출은 실패시키지 않고 경고 로그를 남긴다. **`write` 이상은 감사 행을 먼저 쓰고 못 쓰면 실행하지 않는다.** **보관은 기본 90일**(`[mcp.audit] retention_days`, 0 은 지우지 않음)이고 「에이전트 활동」 패널에서 지울 수 있다(06-roadmap.md 결정 D62). **`[mcp.audit]` 표는 전역 설정에서만 읽는다** — 감사 파일이 하나다. 프로젝트 설정(공유든 개인이든)의 그 표는 효과가 없고 경고를 남긴다. **지금 구현**(16-m5-plan M5-11, `pw_mcp::audit`): 스키마 둘째 판이다 — 첫째 판 파일은 열 때 올린다(SQLite 는 열의 `CHECK` 를 고치지 못해 표를 새로 만들고 행 · id 를 그대로 옮긴다). **행 id 는 다시 쓰이지 않는다**(`AUTOINCREMENT`) — 보관 정리 · 지우기가 가장 큰 id 까지 지워도 새 행은 더 큰 id 라, 쪽 넘기기 커서와 `mcp.activity` 의 id 가 다른 행을 가리키지 않는다. 선기록은 정책을 지난 `write` 이상의 호출과 **승인을 지난 호출**(등급과 무관 — 「이 연결 열기」 · 프로덕션 `ask` 의 조회처럼 승인을 청하는 `read` 툴이 있다, 메인 판정 2026-11-17)이 툴을 부르기 전에 쓴다(`pw_mcp::server` 의 `Session::run`). 승인 방식 · 계획 해시는 그 행에 남는다 — 응답을 기다리게 하지 않는 기록 큐를 지나지 않고 그 쓰기를 기다리며(앞서 큐에 든 기록을 먼저 비워 행 순서가 호출 순서다), 못 쓰면 툴을 부르지 않고 결과 `denied` · 까닭 `audit_unavailable` 이다. 끝 기록은 큐로 가고 그 세션의 `started` 행만 고친다(이미 지워졌으면 고치지 않고 경고). 승인 경로(16-m5-plan M5-12)는 사람이 답한 뒤 이 선기록을 걸고 승인 방식 · 계획 해시를 그 행에 쓴다 — 거절 · 시한 초과 · 창 없음은 툴이 돌지 않아 선기록 없이 `denied` 행 하나다. 보관 정리는 앱이 시작할 때와 하루에 한 번이고 그때마다 전역 설정을 다시 읽는다(`pw_mcp::audit::keep_pruned` — 짧게 사는 헤드리스 `pitwall mcp` · `pitwall tool` 은 지우지 않는다). 기한은 「지금 − 보관 일수」 보다 앞선 기록 시각이다(선기록 행은 시작 시각). 잘못된 `retention_days`(음수 · 정수 아님)는 기본 90일로 보고 경고를 남긴다. 프로젝트 `[mcp.audit]` 의 경고는 그 프로젝트의 `[mcp]` 를 읽는 자리(세션 프로젝트 · 대상 프로젝트 판정 · `mcp.tools.list` — `pw_mcp::exposure::Exposure::from_layers`)가 로그에 남긴다

  - **지금 구현**(16-m5-plan M5-12 — `pw_mcp::approval`): 창은 떠 있는 동안 `mcp.approvals { projectId? }`(스트림, owner)를 연다 — 프로젝트 창은 자기 프로젝트로(그 프로젝트 창의 연결만 — `git.prompts` 와 같은 판정), 웰컴 · 설정 창은 프로젝트 없이. 창 식별자가 없는 연결(창 없는 Host 범위 연결)은 프로젝트 없는 요청의 후보가 아니고, 창이 사라지면 앱이 포커스 순서에서 뺀다. 항목은 `open { request }`(요청 id · 대상 프로젝트 · `notThisProject` · 세션 · 클라이언트 · `cli` · 툴 · 등급 · 계획 · 받는 답 · 시한)과 `closed { id }` 다. 답은 `mcp.approval.answer { id, answer }`(write, owner — `deny` · `once` · `session` · `window` 가운데 그 요청이 받는 것)이고, 프로젝트 요청은 그 프로젝트 창의 연결만, 프로젝트 없는 요청은 그것을 받은 창의 연결만 답한다. 둘 다 에이전트 범위 연결은 거절한다(`agentSession`) — 에이전트가 자기 요청에 스스로 답하는 길이 없다. 프로젝트 없는 요청은 가장 최근에 앞에 온 창(앱이 창 포커스를 허브에 알린다 — 모르면 가장 최근에 듣기 시작한 창) 하나에 가고, 그 창이 닫히면 다음 창으로 옮긴다. 묻는 도중 그 프로젝트 창이 모두 닫히면 거절이다. 호출이 취소되거나 클라이언트가 끊으면 곧바로 요청을 거둔다 — 세션이 읽기의 끝을 보고 거두므로 rmcp 가 끊긴 뒤 5초 동안 핸들러를 돌리는 사이(「호출 취소」)에 [허용] 을 눌러도 돌지 않는다. 앱이 끝날 때는 대기를 모두 거두고 열린 세션의 감사 큐를 비운다 — 최대 2초 종료가 늦어질 수 있다. 창이 먼저 닫히는 보통 길에서는 그 프로젝트 창이 떠날 때 대기가 `needs_approval` 로 끝나고, 창이 남은 채 앱이 끝나면 `cancelled`(결과 `error`)다. **세션당 대기 상한**(16-m5-plan M5-14): 한 MCP 세션이 한꺼번에 기다리게 할 수 있는 요청은 8개(`pw_mcp::approval::MAX_PENDING_PER_SESSION`)다 — 넘는 호출은 창에 보이지 않고 곧바로 `approval_backlog` 로 거절되고(감사 행이 남는다), 앞의 요청 하나가 끝나면 다시 묻는다. 다른 세션에는 닿지 않는다
  - **지금 구현 — 다이얼로그 · OS 알림**(16-m5-plan M5-14 — `apps/desktop/src/mcp/`): 프로젝트 창 · 웰컴 창 · 설정 창이 떠 있는 동안 `mcp.approvals` 를 하나씩 열어 두고(`approvals-host.tsx`), 다이얼로그(`approval-dialog.tsx`)와 「에이전트 활동」 의 「승인 대기」 칸(`pending-approvals.tsx`)이 그 창 단위 저장소(`approvals.ts`) 하나를 읽는다. 다이얼로그는 한 번에 하나(「n개 중 k」 와 남은 시한), 처음 포커스는 [거절], 허용 계열 단추(이번만 · 세션 · CLI)는 사람이 그 요청을 볼 수 있게 된 순간부터 1초 잠기고(자물쇠 표지 — 뜸 · 다른 요청으로 바뀜 · 목록 · 알림으로 다시 엶(이미 떠 있던 요청이어도) · 창이 앞으로 옴 · 숨었던 창이 보임마다 다시 잠그고, 창이 뒤에 있거나 숨은 동안은 세지 않는다) 세는 동안 창에 키 · 포인터가 눌리면 처음부터 다시 센다 — 이름 칸에 치는 글자는 빼고, 포인터로 누른 허용은 풀린 뒤 그 단추에서 내려간 누름이어야 한다([거절] 은 잠그지 않는다. 치던 `Tab` … `Enter` · 더블클릭 · 앞 요청이 닫히는 순간의 클릭이 새 요청의 허용에 닿지 않게), `Esc` 는 다이얼로그만 닫고 요청은 「승인 대기」 에 남는다(줄을 누르면 다시 연다). 셋째 단추는 CLI 요청이면 「창이 열려 있는 동안 CLI 허용」(`window`), 아니면 「이 세션 동안 허용」(`session`)이고, `dangerous` · 기억하지 않는 계획(`open_with_upsert`)과 요청의 `answers` 에 없는 답은 그리지 않는다. 프로젝트 없는 요청은 「이 요청은 이 프로젝트의 것이 아니다」 를 보인다. 바뀔 것: 파일(`file` — 앞뒤 내용)은 git diff 뷰 부품, 글(`text`)은 이름과 원문, SQL(`sql` — 연결 이름 · 프로덕션 · read-only 표지, 파일이면 경로와 내용 해시, 문장마다 순서 · 줄 · 등급 · 원문, 「되돌릴 수 없다」 — 꼴은 메인 판정 2026-11-17, `db_execute`(M5-18)가 채운다)는 연결 표지 · 파일 경로(해시는 보이지 않는다) · 문장 목록이고 — 조회가 아닌 문장은 수와 상관없이 모두 보이고 조회 문장만 50개를 넘으면 접어 그 수를 보인다 — 파괴 등급 문장이 하나라도 있으면 그 연결 이름을 쳐야 허용 단추가 켜진다(창의 위험 쿼리 확인과 같은 칸 — `db/safety/name-confirm.tsx`). 에이전트가 보낸 글(클라이언트 이름 · 툴 · 요약 · 경로 · 바뀔 글 · 문장)은 DB 그리드와 같은 넓은 규칙으로 보이지 않는 글자(제어 · 양방향 제어 · 0폭 · 결합자 · BOM · 이형 선택자 · 태그 문자)를 `⟨U+XXXX⟩` 표지로 바꾸고(`agent-text.ts`), 한 줄 자리는 줄바꿈도 표지로 바꾸고 길이를 자르며, 테두리 친 칸 안에서만 그린다 — 단추 줄은 굴리는 본문 밖에 늘 있다. **OS 알림**(`tauri-plugin-notification`, `apps/desktop/src-tauri/src/approval_notice.rs`): 새 요청을 받은 창이 앞에 없으면 「<에이전트>가 <툴> 승인을 기다린다」 알림과 **함께 늘** 그 창의 주의 요청(Dock 아이콘 — 앱이 앞에 올 때까지 튄다)을 한다 — 창이 다시 앞에 올 때까지 창마다 한 번. 데스크톱 플러그인은 권한을 늘 「있음」 으로 답하고 보내기 결과를 돌려주지 않아(macOS · Windows 는 보내기를 다른 스레드에 맡긴다) OS 설정에서 끈 알림 · 보내지 못한 알림을 알 수 없다 — 그래서 알림의 대안이 아니라 둘 다 한다. 알림을 만들지도 못하면 주의 요청만 남는다. 알림을 누르면 그 창을 앞으로 가져오고 그 요청의 다이얼로그를 다시 연다(다시 열린 다이얼로그의 허용 단추도 다시 잠긴다)
- 원격 머신에서 도는 에이전트도 해당 Relay의 MCP 엔드포인트를 사용 → 같은 승인 흐름 — 그 세션은 그 머신의 로컬 세션이다: 그 머신 Relay 전역 설정(`$CONFIG/relay/settings.toml`)의 `auto_approve` 와 그 머신에서 사람이 본 구성으로 판정하고, 다이얼로그만 링크의 Desktop 에 뜬다. 붙은 owner Desktop 이 없는 동안은 헤드리스와 같다 — `write` 이상은 거절(18-m7-plan 결정 M7-D10)
- 확장(WASM 플러그인)이 추가한 MCP 툴은 `<ext-id>.<tool>` 이름으로 노출, 권한 등급은 확장 매니페스트에 선언

## 3-1. 툴 노출 설정 (툴별 on/off)

JetBrains IDE 내장 MCP 서버의 "Exposed Tools" 방식을 따른다. 권한 등급(3절)과 별개로 **툴 자체를 에이전트에게 보이지 않게** 할 수 있다.

| 항목 | 설계 |
|---|---|
| 단위 | 툴 단위 on/off (꺼진 툴은 `tools/list`에 나오지 않음 → 에이전트 컨텍스트 토큰도 절약) |
| 그룹 | 모듈 그룹(project / run / debug / db / git / code / open_with / 확장별) 일괄 on/off — `[mcp.groups]`(그룹 이름 = 켬 · 끔). 그룹은 툴의 선언이 싣는다(「툴 레지스트리」) |
| 프리셋 | `read-only`(조회 툴만) · `standard`(기본: 조회 + 설정) · `full`(실행 · DB 쓰기 포함) |
| 범위 | 전역 기본값 → 프로젝트별 덮어쓰기 (`.pitwall/project.toml` 또는 `.local.toml`, 개인 전용 프로젝트는 `$CONFIG/projects/<slug>/project.toml`). **커밋되는 공유 설정(`.pitwall/project.toml`)은 노출을 좁히기만 한다** — 프리셋을 넓히거나 꺼진 툴을 켜는 것은 전역 · `.pitwall/*.local.toml`(git 이 추적하거나 받아 오지 않은 것 — 「권한 모델」) · 개인 전용 설정만 한다. 저장소를 클론한 것만으로 에이전트에게 열리는 툴이 늘지 않게 한다. `auto_approve` 와 그룹 키도 같다 — 공유 설정은 자동 승인을 더하거나 그룹을 켜지 못한다. `[mcp.policy]` 는 공유 설정에서 아예 읽지 않는다(「권한 모델」). `[mcp.audit]` 는 전역 설정에서만 읽는다(「감사 로그」) |
| 자동 승인 | 등급별 "확인 없이 실행" 토글 (JetBrains의 brave mode에 해당). `dangerous` 등급은 자동 승인 불가. `open_with_upsert` 와 「이 연결 열기」 승인(「DB」)에도 적용하지 않는다 |
| 변경 반영 | 설정 변경 시 MCP `notifications/tools/list_changed` 전송 → 연결된 에이전트가 즉시 갱신 |
| 확장 툴 | 확장이 추가한 툴은 **기본 꺼짐**, 사용자가 켜야 노출 |
| UI | 설정 > MCP: 툴 목록(이름 · 설명 · 등급 · 최근 호출 수), 검색, 그룹 토글, 입력 스키마 미리보기 |

지금 구현(`crates/pw-mcp/src/exposure.rs`):
- 읽는 키는 `preset` · `[mcp.tools]` · `[mcp.groups]` 다. 전역 `[mcp]` 위에 프로젝트 `[mcp]` 를 설정 계층의 병합 규칙으로 덮는다(`[mcp.tools]` · `[mcp.groups]` 는 키별로 합쳐진다). 내장 기본값은 `preset = "standard"`
- 「공유 설정은 좁히기만」: 저장소 모드 프로젝트는 공유 레이어까지 읽은 노출과, 공유 레이어를 뺀(전역 + `.local.toml`) 노출이 **둘 다 켠 툴**만 켠다(`Exposure::narrowed_by`). 개인 전용 프로젝트의 `project.toml` 은 개인 설정이라 넓힐 수 있다
- `tools/list` 는 **세션 프로젝트**의 설정으로 정한다. 호출은 세션의 노출과 **대상 프로젝트의 노출**(프로젝트 툴의 `projectId` 가 세션 프로젝트가 아닐 때 그 프로젝트의 `[mcp]` — 공유 레이어는 좁히기만)을 둘 다 지나야 한다(16-m5-plan 결정 M5-D28, `pw_mcp::server` 의 `Session::call`). 대상 프로젝트가 끈 툴은 결과 `denied` · 까닭 `not_exposed` 다. 대상 프로젝트의 설정은 호출마다 **디스크에 쓰지 않고** 읽는다(`ConfigSource::without_writes`). `auto_approve` · `[mcp.policy]` 와 승인 창은 대상 프로젝트의 것으로 판정한다(16-m5-plan M5-12 — 「권한 모델」 의 「지금 구현」)
- 프리셋은 등급으로 고른다: `read-only` = `read`, `standard` = `read` · `write`, `full` = 전부
- 판정 순서: 툴 이름과 정확히 같은 키 → 맞는 glob(`*` 는 아무 글자열) 중 가장 긴 것 → 그룹(`[mcp.groups]`) → 프리셋
- 그룹은 툴의 선언이 싣는 칸이다(「툴 레지스트리」). glob 은 접두사 없는 이름(`diagnostics` · `settings_get`)을 놓치고 꺼 둔 그룹에 뒤에 더해진 툴을 켜진 채 내보내지만, 그룹 키는 그 그룹의 툴을 이름과 상관없이 모두 끈다. 공유 설정은 그룹 키로도 좁히기만 한다(같은 `Exposure::narrowed_by`)
- 잘못된 값은 버리고 경고 로그를 남긴다(모르는 그룹 이름, bool 이 아닌 툴 · 그룹 값). 모르는 프리셋은 가장 좁은 `read-only` 로 본다
- 변경 반영: 전역 · 세션 프로젝트의 설정 파일을 감시해 **보이는 툴 집합이 바뀌면** `notifications/tools/list_changed` 를 보낸다. 2025-11-25 까지의 클라이언트는 initialize 뒤 세션 알림으로, 2026-07-28 클라이언트는 `subscriptions/listen` 구독으로 받는다
- 판정은 켜졌는지와 **그것을 정한 규칙**을 함께 낸다(`Exposure::verdict` — `enabled` 는 이것의 값이다): `preset` · `tool`(정확한 키) · `glob` · `group` · `shared`(공유 레이어를 빼면 켜지는데 공유 설정이 껐다 — 공유 설정이 켜려다 상한에 막힌 툴은 상한의 규칙이다)와 그 키. 사람의 화면은 `mcp.tools.list { projectId? }`(read, owner — 16-m5-plan M5-10)로 카탈로그 전부(이름 · 설명 · 등급 · 그룹 · 입력 스키마)와 그 판정, 최근 30일 호출 수를 읽는다. `projectId` 를 주면 그 프로젝트의 설정(대상 프로젝트 판정과 같은 읽기 — `exposure::of_project`)과 그 프로젝트의 호출 수, 없으면 전역 설정과 전체 호출 수다. `mcp.*` RPC 에는 `mcp` 를 달지 않는다 — 에이전트가 자기 감사 로그 · 노출 설정을 읽는 툴은 없다. 툴 목록에 없는 것만으로 막지 않는다: `mcp.*` 는 모두 **에이전트 범위 연결(MCP 세션이 Host 에 붙는 연결)을 거절한다**(`PERMISSION_DENIED`, `data.reason = "agentSession"` — `project.setTrust` 와 같은 꼴, `pw_mcp::methods::WindowsOnly` 한 자리가 거절하고 뒤 행이 더하는 `mcp.*` 메서드도 그 자리를 지난다). 단일 파일 창 연결도 부르지 못한다
- **설정 > MCP 화면**(16-m5-plan M5-15 — `apps/desktop/src/settings/mcp-section.tsx`, Host 쪽 `pw_mcp::settings`): 프리셋 · 등급별 자동 승인(`dangerous` 칸은 없다) · 감사 보관 일수 · 그룹 토글(프리셋을 따름 · 켬 · 끔 — 「프리셋을 따름」 은 그 키를 지운다) · 툴 목록(이름 · 설명 · 등급 · 그룹 · 최근 30일 호출 수 · 켜진 까닭)과 검색 · 툴 하나 토글(그 툴의 키가 있으면 「기본값으로」) · 입력 스키마 미리보기, 에이전트 등록 문구의 복사(「클라이언트 자동 등록」). **편집은 전역 `[mcp]` 만**(결정 M5-D36) — 쓰기는 `mcp.settings.set { key, name?, value }`(write, owner)이고 키는 `preset` · `autoApprove` · `group` · `tool` · `retentionDays` 다섯이다(`value: null` 은 그 키를 지운다). 값은 Host 가 판정한다 — 모르는 프리셋 · 그룹 · 툴(glob 키는 쓰지 않는다), `auto_approve` 의 `dangerous` · 등급이 아닌 이름, 0 ~ 3650(`pw_mcp::settings::MAX_RETENTION_DAYS` — 10년, 메인 판정 2026-11-17) 정수가 아닌 보관 일수는 쓰지 않고 `INVALID_PARAMS`(`data` 는 `McpSettingRefused { key, reason }` — 창이 번역한다). 쓰기는 `pw_core::config::write::write_key` 로 그 키 하나만 고치고(주석 · 다른 키 보존) 전역 설정을 다시 읽어 열린 세션이 노출을 다시 읽는다(보이는 툴이 바뀌면 `tools/list_changed`). `[mcp.policy]` 는 이 화면이 고치지 않는다. 읽기는 `mcp.settings.get { projectId? }`(read, owner)이고 Host 가 판정에 쓰는 함수(`Exposure::from_layers` · `pw_core::config::mcp_policy` · `audit::retention_days`)의 값과 전역 설정 파일 경로, 읽다 버린 값의 경고를 싣는다. 툴 하나하나의 켜짐과 까닭은 `mcp.tools.list` 의 판정이다 — 화면은 판정하지 않는다. **프로젝트 덮어쓰기 보기**(읽기만 — 메인 판정 2026-11-17): 설정 창은 Host 범위라 화면이 등록된 프로젝트 하나를 고르게 한다. 고르면 `mcp.settings.get { projectId }` 가 그 프로젝트의 설정 파일(공유 · 개인 · 개인 전용 프로젝트의 파일 — 경로와 있는지)과 그 파일들이 `[mcp]` 아래에 적은 키 · 값 · 파일, 그 프로젝트의 자동 승인을 싣고, 툴 줄마다 그 프로젝트에서의 실제 판정(`mcp.tools.list { projectId }` 의 켜짐 · 까닭)을 「이 프로젝트에서: 켜짐/꺼짐 — 까닭」 으로 전역 판정 옆에 보이고, 두 판정이 다르면(켜짐 · 규칙 · 키 가운데 하나라도) 「전역과 다름」 표지를 단다. **전역 토글은 잠그지 않는다** — 전역의 정확한 툴 키는 프로젝트가 그룹 · 프리셋 · glob 으로 바꾼 판정에도 닿고(정확한 키가 앞선다), 프로젝트 파일의 정확한 키 · 공유 설정의 좁히기에는 닿지 않는다. 어느 쪽인지는 화면이 추론하지 않고 고친 뒤 Host 가 다시 낸 판정을 보인다(메인 판정 2026-11-17 — M5-15 리뷰). 프로젝트 설정 파일이 바뀌면 화면은 저절로 다시 읽지 않는다(설정 창은 그 프로젝트의 `config.changed` 를 듣지 않는다) — 창이 앞으로 오거나 프로젝트를 다시 고르면 맞춰진다. 「파일로 열기」 는 Host 가 준 경로(전역 `settings.toml` · 고른 프로젝트의 있는 설정 파일)만 단일 파일 창으로 연다(앱 명령 `open_file_window` 를 설정 창에도 연다 — 「Host 가 준 경로만」 은 화면의 약속이고, 명령은 웰컴 창과 같이 절대 경로의 파일인지만 본다). 두 RPC 도 `mcp.*` 의 문(`WindowsOnly`)을 지나 에이전트 범위 연결을 거절한다. 툴 설명은 영어 그대로 보인다
- 확장 툴 기본 꺼짐은 아직 없다(`auto_approve` 는 「권한 모델」 의 「지금 구현」)

```toml
# ~/.config/pitwall/settings.toml (전역) — 프로젝트에서 같은 키로 덮어쓰기 ([mcp.policy] · [mcp.audit] 는 아래 주석)
[mcp]
preset = "standard"
auto_approve = ["read", "write"]      # "exec" 추가 가능, "dangerous"는 불가

[mcp.tools]
db_query = true
run_start = false                      # 개별 툴 끄기
"dev.pitwall.ext-kafka.*" = true       # 확장 툴 켜기 (glob)

[mcp.groups]
db = false                             # 그룹 끄기 (project / run / debug / db / git / code / open_with)

# [mcp.policy] 는 전역 · .pitwall/*.local.toml · 개인 전용 project.toml 에서만 읽는다
# (커밋되는 .pitwall/project.toml 의 [mcp.policy] 는 효과가 없고 경고를 남긴다)
[mcp.policy]
approval_timeout_secs = 300            # 승인 시한
production = "block"                   # "ask" 면 사람이 연 프로덕션 연결을 매번 승인으로

# [mcp.audit] 는 전역 설정에서만 읽는다 — 감사 파일이 하나다
# (프로젝트 설정의 [mcp.audit] 는 공유든 개인이든 효과가 없고 경고를 남긴다)
[mcp.audit]
retention_days = 90                    # 감사 로그 보관. 0 은 지우지 않음
```

## 3-2. CLI (`pitwall tool`)

MCP 툴 전부를 같은 이름 · 같은 입력 · 같은 판정으로 명령줄에서도 부른다(06-roadmap.md 결정 D54). MCP 클라이언트가 없는 에이전트 · 셸 스크립트 · 사람이 쓰고, 툴 스키마를 컨텍스트에 싣지 않고 필요한 툴만 부르는 길이기도 하다.

구현: `apps/desktop/src-tauri/src/tool_cli.rs`(명령 · 플래그 · 종료 코드 · MCP 클라이언트), `mcp.rs`(앱 소켓에 붙기 `connect_app` · 헤드리스 세션 `Headless` — `pitwall mcp` 와 함께 쓴다).

| 명령 | 하는 일 |
|---|---|
| `pitwall tool list` | 이 세션에 노출된 툴의 이름 · 등급 · 설명 한 줄. 꺼진 툴은 나오지 않는다(`tools/list` 와 같은 집합) |
| `pitwall tool <툴> --help` | 그 툴의 설명 · 등급 · 입력 스키마(플래그 이름 · 타입 · 필수 여부) |
| `pitwall tool <툴> [--<키> <값>]... [--input <json>\|-]` | 툴 호출. 결과를 stdout 에 JSON 문서 하나로 쓴다 |

- **CLI 는 로컬 소켓에 붙는 MCP 클라이언트다.** `pitwall tool` 은 「로컬 소켓과 헤드리스」 절의 `pitwall mcp` 와 같은 길로 세션을 열고(소켓이 있으면 앱에, 없으면 같은 프로세스의 헤드리스 Host 에 프로세스 안 duplex 로) `initialize` → `tools/list` → `tools/call` 을 보낸다. 서버 쪽에 CLI 전용 경로를 두지 않는다 — 카탈로그 · 노출 · 권한 · 감사 로그가 MCP 와 한 벌이다. CLI 에만 있는 툴도, MCP 에만 있는 툴도 없다. 클라이언트는 rmcp 의 `client` 기능이다(서버와 같은 구현 — 버전 협상 · 취소 알림 · 쪽 넘기기)
  - **Why:** 경로가 둘이면 툴을 끈 설정 · 승인 정책을 CLI 로 돌아갈 수 있고, 두 판정이 조용히 갈린다(02-tech-stack.md 「DB 계층」 의 DBX 비교 — CLI 가 MCP 와 다른 쓰기 판정을 쓴다)
- **툴 이름**은 MCP 이름 그대로다(`pitwall tool git_status`). 「툴 레지스트리」 절의 규칙으로 RPC 선언에서 나오므로 툴이 늘면 CLI 도 함께 는다. 손으로 쓰는 서브커맨드 표는 없다. 툴 이름 `list` 는 명령과 겹쳐 쓰지 못한다(예약 플래그와 같은 카탈로그 시험이 막는다)
- **등급**(`list` · `--help` 의 `read` · `write` …)은 실행 파일에 링크된 카탈로그에서 읽는다 — MCP `tools/list` 에는 등급이 없다(`readOnlyHint` 뿐). 이 실행 파일이 모르는 툴이면 `readOnlyHint` 로 `read` 만 알고 나머지는 `?`
- **프로젝트**: `--project <path>`, 없으면 cwd 로 해석한다(「전송 방식」 절과 같은 규칙). 세션에 프로젝트가 있으면 `projectId` 는 서버가 채운다
- **입력**: 입력 스키마의 최상위 필드마다 플래그 하나(camelCase → kebab-case, `maxCount` → `--max-count`). 값은 스키마의 타입으로 읽는다 — 글자열은 그대로, 수 · 불리언 · 배열 · 객체는 JSON 으로. `--input <json>` 은 입력 객체 전체이고 `--input -` 는 stdin 에서 읽는다. 둘을 함께 주면 플래그가 덮는다. 스키마에 없는 플래그 · 타입이 안 맞는 값 · 빠진 필수 필드(세션 프로젝트가 채우는 `projectId` 는 빼고)는 호출하지 않고 사용법 오류다. 글자열과 다른 타입을 함께 받는 필드(`anyOf`)는 JSON 으로 읽히는 값이면 그 값, 아니면 글자열이다. 타입을 스키마로 알 수 없는 필드도 같다. `--project` · `--input` · `--help` 는 예약이다 — 툴 입력의 최상위 필드가 이 플래그 이름이 되면 카탈로그 시험이 실패한다. `--project` 는 `tool` 뒤 어디에나 둔다. 예약 플래그는 플래그 이름 자리에서만 가른다 — `--<플래그>` 바로 다음 자리는 값이라 `--message --project` · `--pattern -h` 의 뒤쪽은 값이다
- **비밀은 플래그로도 받지 않는다.** MCP 인자로 받지 않는 것(`db_connection_upsert` 의 비밀번호)은 CLI 에서도 UI 입력 요청 · env 참조뿐이다 — 플래그 값은 셸 기록과 프로세스 목록에 남는다
- **출력**: stdout 에는 결과 JSON 문서 하나만(`structuredContent` 가 있으면 그것, 없으면 텍스트 내용 — JSON 이 아닌 글이면 JSON 글자열로). 툴 오류 · 거절 이유 · 로그는 stderr. 사람이 읽기 좋은 표 출력은 두지 않는다 — `--help` 와 `list` 만 글이다. 로그 파일은 `$STATE/logs/cli.<날짜>.log`(03-architecture.md 「로그 · 진단」)
- **종료 코드**: 0 성공, 1 툴 오류 · 앱과의 연결 끊김, 2 사용법 오류(모르는 툴 · 플래그 포함. 툴 없이 `pitwall tool` 만 친 것도), 3 거절(노출되지 않은 툴 · 승인 거절 · 승인 시간 초과 · 헤드리스에서의 `write` 이상 · 앱이 있어야 하는 툴을 앱 없이 부름 · 툴의 관문이 `PERMISSION_DENIED` 로 거절 — 사람이 연 적 없는 DB 연결 · 미신뢰 · 프로덕션 등, 16-m5-plan M5-06), 128 + 신호 번호 — Ctrl+C 로 호출을 취소했다. 1 과 3 은 서버의 결과 표지로 가른다(「툴 레지스트리」 — `tools/call` 결과의 `_meta`, 노출 안 된 툴의 JSON-RPC 오류 `data`). 「앱이 있어야 하는 툴을 앱 없이」 는 CLI 가 가른다 — 실행 파일에 링크된 카탈로그에는 있고 헤드리스 Host 가 처리하지 않는 이름이면 부르지 않고 3 과 「Pitwall 앱을 실행한 뒤 다시」 다. 노출 설정이 끈 툴은 그대로 불러 서버가 거절하고 감사 행을 남긴다
- **취소**: Ctrl+C 면 그 호출을 MCP 취소 알림(`notifications/cancelled`)으로 거둔다 — 서버가 그 호출의 Host RPC 를 취소하는 「로컬 소켓과 헤드리스」 의 「호출 취소」 길이다. 알림을 보낸 뒤 130 으로 끝난다
- **승인**: `write` 이상은 MCP 와 같은 승인 요청이 그 프로젝트 창에 뜨고 CLI 는 답을 기다린다(시한은 「권한 모델」 절의 승인 타임아웃). 앱에 붙은 `write` 이상 호출의 답이 1초 안에 오지 않으면 stderr 에 「승인을 묻는다면 그 프로젝트 창에서 답하라」 한 줄을 쓴다(승인 경로 — 16-m5-plan M5-12). 헤드리스에는 코어 툴만 있고 승인 경로가 없어 그 가운데 `read` 툴만 성공한다(「로컬 소켓과 헤드리스」). `auto_approve` 는 CLI 호출에도 같은 뜻이다
- **CLI 의 「이 세션 동안 허용」**: CLI 는 호출마다 세션을 새로 열어 세션 허용이 다음 호출에 닿지 않는다. 그래서 CLI 호출의 승인에서 그 자리는 **「이 프로젝트 창이 열려 있는 동안 CLI 허용」**(그 프로젝트 · 그 툴)이다 — 앱이 기억하고 창을 닫으면 사라진다. 이 허용은 CLI 로 온 호출 전부에 닿는다: 서버는 CLI 를 클라이언트가 적는 이름으로만 알므로, 같은 기기의 다른 에이전트 · 스크립트가 CLI 를 불러도 그동안은 묻지 않는다. `dangerous` 에는 없다(매번). 「이 연결 열기」 승인도 CLI 에서는 같은 범위다(창이 열려 있는 동안 · 그 연결). 06-roadmap.md 결정 D61. **지금 구현의 한계**(16-m5-plan M5-17 — 메인 판정 2026-11-17, fail-closed 로 둔 이월): CLI 의 창 허용은 다음 CLI 호출의 `db_connection_test` 에만 닿고(승인 경로의 CLI 허용 — 그 툴 · 그 연결 열쇠), `pitwall tool db_schema` 처럼 다른 DB 툴에는 닿지 않는다 — CLI 는 호출마다 MCP 세션을 새로 열고 「승인받은 연결」 은 MCP 세션에 묶인다. CLI 로 연 적 없는 연결을 쓰려면 사람이 앱의 DB 탐색기에서 그 연결을 한 번 연다
- **감사 로그**: 호출마다 MCP 와 같은 행이 남고 클라이언트는 `pitwall-cli <버전>` 이다. 「에이전트 활동」 패널에 함께 보인다
- **CLI 에 없는 것**: Resources · Prompts(「리소스 & 프롬프트」 절 — 같은 내용은 조회 툴로 읽는다), `tools/list_changed` 알림(호출마다 세션을 새로 열어 그때의 노출을 본다), Streamable HTTP
- 명령줄에서의 자리(`tool` 이 서브커맨드가 되는 규칙)는 04-features.md 「F2. 파일로 앱 실행」 절의 명령줄 규칙

## 4. 리소스 & 프롬프트 (MCP Resources/Prompts)

- Resources: `pitwall://project/{id}/config`, `pitwall://project/{id}/run/{name}/log`, `pitwall://project/{id}/db/{conn}/schema`
- Prompts: `setup_project` — "이 프로젝트의 실행 구성과 DB 연결을 감지해서 설정해줘" 워크플로 템플릿
- M5 에 없다 — 실행 구성이 생기는 M6 뒤에 정한다(16-m5-plan 결정 M5-D33)

## 5. 설계 메모

- 툴 입력 스키마는 코어 Rust 타입에서 `schemars`로 생성 → UI 폼과 MCP 검증이 동일
- 응답은 토큰 절약을 위해 기본 요약 + `detail` 옵션 (예: `run_logs`는 기본 마지막 200줄). 한 건의 상한과 목록 `limit` 의 기본은 「툴 레지스트리」 의 「응답 크기」
- 설정 변경은 결국 `.pitwall/*.toml` 파일 변경이므로, 에이전트가 파일을 직접 고쳐도 동일하게 반영됨 (파일 감시). MCP 툴은 **검증 · 승인 · 자동감지**라는 부가가치를 제공
