# 17. M6 (실행 · 디버그) 작업 분할

M6 목표: **「IntelliJ 의 실행 · 디버그를 열 이유를 없앤다」 — 프로젝트의 실행 구성(`.pitwall/run/*.toml`)과 감지된 태스크를 한 번에 돌리고, 콘솔에서 로그를 보고, DAP 로 멈춰서 변수를 본다. 에이전트는 같은 구성을 MCP · CLI(`run_*` · `debug_*` 툴)로 만들고 돌리고 로그를 읽되, 사람이 본 적 없는 명령은 승인을 지나야 돈다.** 디버거는 특정 언어에 맞춘 작업 없이 확장 정의 위의 범용 구조(D6 · 06-roadmap.md 「마일스톤」 아래 「주력 언어 미정」 줄)이고, 어댑터 설치는 M4 의 Mason registry 설치기(`pw-tools`)를 넓혀 쓴다. 실행 구성의 `sql` 종류(F6-14 ② — D55)도 이 단계다 — 프로세스를 띄우지 않고 `pw_db::script` 의 실행 경로를 지난다.

이 문서는 **초안**이다(2026-11-18). 사람이 정해야 하는 결정 여섯(M6-D1 ~ D6)이 「결정 필요」 이고, 메인 판정(제안)은 계획 리뷰 뒤 메인이 확정한다. 결정을 기다리는 행은 「2. 순서」 에 적었다 — 나머지는 결정과 상관없이 시작할 수 있다.

완료 시 할 수 있는 것(사람이 손으로 확인하는 시나리오 — 1 ~ 6 은 「실행 선」 까지, 7 ~ 10 은 그 뒤. 「선」 은 결정 M6-D1 이 둘지 정한다):

1. 신뢰한 Node 프로젝트를 열면 실행 선택기(`▶ ▾`)에 `package.json` 의 scripts 와 `mise.toml` 의 tasks 가 「감지됨」 으로 보이고, `dev` 를 고르고 `⌃R` 하면 하단 「실행」 툴 윈도우에 그 구성의 탭이 생겨 색 있는 출력이 흐른다. 출력의 `src/app.ts:12:5` 를 ⌘+클릭하면 에디터가 그 줄로 간다. 탭 머리에 `:5173` 이 보인다(M6-02 · M6-04 · M6-05 · M6-06 · M6-08).
2. 실행 중인 `dev` 를 「다시 실행」 하면 손자 프로세스(vite 의 esbuild 등)까지 끝난 뒤 다시 뜨고, 「중지」 하면 `ps` 에 그 트리가 남지 않는다. 같은 구성을 두 번 띄우면 탭 둘이다. 창을 다시 불러와도(`⌘R` 개발 빌드 · 창 다시 열기) 앞 출력이 그대로 보인다(M6-02 · M6-06).
3. 실행 선택기 「구성 편집」 에서 `shell` 구성을 폼으로 만들고(이름 · 명령 · 작업 폴더 · env · `.env` 파일) 저장하면 `.pitwall/run/<id>.toml` 이 생기고 「TOML 보기」 가 같은 내용이다. `.env.local` 의 값이 프로세스에 들어가고, 로그 파일에는 변수 이름만 남는다(M6-01 · M6-03 · M6-07).
4. `sql` 구성(연결 `local-pg`, 파일 `db/seed.sql` · `db/fixtures.sql`, 트랜잭션 「전부 하나」)을 실행하면 프로세스 없이 콘솔에 문장마다 번호 · 줄 · 영향 행 수 · 소요가 찍힌다. 파일에 `DELETE` 가 있으면 실행 전에 SQL 콘솔과 같은 위험 확인이 뜬다. 둘째 파일에서 실패하면 첫째 파일의 변경도 롤백됐다고 적힌다(M6-09).
5. 클론한 저장소를 신뢰하지 않은 채 열면 감지 목록에 `package.json` 의 scripts 는 보이되 실행하면 「이 프로젝트를 신뢰해야 실행한다」 와 신뢰 액션이 뜨고, `mise` · `gradle` 은 돌지 않는다(`ps` 로 확인 — M6-02 · M6-05, F1-7).
6. Claude Code 에 「dev 서버 띄우고 로그 봐 줘」 라고 하면 `run_config_list` → `run_start` → `run_logs` 로 이어지고, 사람이 그 구성을 앞서 UI 에서 돌린 적이 있으면 묻지 않고 돈다. 에이전트가 `run_config_upsert` 로 새 구성을 만들면 diff 승인이 뜨고, 그 구성의 첫 `run_start` 는 명령 · 작업 폴더 · env 이름을 보이는 승인이 한 번 더 뜬다(결정 M6-D6). 에이전트가 `.pitwall/run/dev.toml` 을 파일 시스템에서 직접 고친 뒤 `run_start` 하면 다시 묻는다. `pitwall tool run_logs --run-id … --grep ERROR` 도 같다(M6-10 ~ 14).
7. 기본 번들 언어(결정 M6-D2) 프로젝트에서 줄 번호 옆을 눌러 브레이크포인트를 두고 `⌃D` 하면 어댑터가 없을 때 처음 한 번 출처 · 라이선스를 묻고 설치한 뒤, 그 줄에서 멈춘다 — 에디터에 현재 줄, 「디버그」 툴 윈도우에 스레드 · 콜스택 · 변수(펼칠 때 읽는다) · 워치, 디버그 콘솔에서 식을 평가한다. `F8` · `F7` · `⇧F8` · `⌘⌥R` 로 스텝 · 계속(M6-15 ~ 19).
8. 조건(`i > 3`) · 로그포인트(`i = {i}`) · hit count 브레이크포인트가 그대로 돈다. 파일을 고쳐 줄이 밀리면 브레이크포인트도 따라 밀리고, 앱을 다시 열어도 남아 있다(M6-17 · M6-18).
9. 이미 `--inspect` 로 떠 있는 Node 프로세스(JVM 이면 JDWP 포트 5005 — 결정 M6-D3)에 attach 구성으로 붙어 같은 화면을 본다(M6-17 · M6-19).
10. 에이전트가 `breakpoint_set` 을 부르면 승인 뒤 에디터 거터에 그 브레이크포인트가 보이고, 멈춘 동안 `debug_state` 가 정지 위치 · 스택 · 지역 변수 요약을 돌려준다(M6-20).

**「실행 선」**(결정 M6-D1 — 권고안): 실행 구성 · 감지 · 콘솔 · `sql` 종류 · MCP 실행 툴(**M6-01 ~ 14**)이 병합된 때다. 사람이 이 단계에서 직접 물은 것(실행 구성 실행 · 로그 · SQL 파일 되풀이 실행 — 16-m5-plan.md 「3. M5 에서 하지 않는 것」 의 첫 행)이 선 위에 있다. 그 뒤가 DAP · 디버그 화면 · 디버그 툴 · 복합 구성이다(M6-15 ~ 21). 디버그 행은 선과 상관없이 선행이 되면 나란히 돈다 — 선은 「여기까지면 실행은 쓸 수 있다」 는 표지이고 순서를 막지 않는다.

M6 이 끝났을 때 MCP 툴은 33개다: M5 의 22 + 실행 구성 8(`run_config_list` · `run_config_upsert` · `run_config_delete` · `run_start` · `run_stop` · `run_restart` · `run_status` · `run_logs`) + 디버그 3(`breakpoint_list` · `breakpoint_set` · `debug_state`). 05-mcp.md 「실행 구성」 · 「디버그」 표 그대로다.

대상 플랫폼: macOS(개발 · 검증), Linux/Windows 는 CI 빌드 · 시험(06-roadmap.md 「결정 기록」 D38). 프로세스 트리 끝내기 · 포트 감지는 플랫폼마다 다른 구현이고 macOS 를 먼저 맞춘다 — Windows 의 PTY · 트리 끝내기는 지금 터미널과 같은 수준(ConPTY · Job object 는 이 단계의 시험 밖, 「3. M6 에서 하지 않는 것」).

M5 까지 된 것은 다시 계획하지 않는다 — 내장 터미널의 PTY 세션(`crates/pw-run` 의 `pty` · `tree` · `shell` · `integration`, 셸 세션 통째로 끝내기 · 앱 종료 때 `pw_run::shutdown`), 런타임 환경(`pw-runtime` — 로그인 셸 · mise 의 `mise env --json` · 디렉터리 캐시 · 신뢰 게이트 `Runtime::with_trust`), 프로젝트 신뢰(`pw_core::registry::trust` — 워크트리는 메인 저장소 프로젝트의 신뢰를 따른다), 실행의 연결 범위(`pw_core::registry::exec::exec_grant` — 그 프로젝트 창만, MCP 세션은 아무것도 띄우지 못한다), 터미널 출력의 `파일:줄` 링크(`apps/desktop/src/terminal/terminal-links.ts`), 툴 윈도우 자리 `run` · `debug`(`apps/desktop/src/layout/project-layout.ts` — 지금은 빈 자리), 설정 계층(`.pitwall/run/` 한 단계를 이미 읽는다 — 03-architecture.md 「설정 계층」)과 한 키 쓰기(`pw_core::config::write`), 확장 매니페스트(`pw-ext` — `[contributes.language_servers]` 까지), 언어 서버의 실행 파일 해석(`pw-lsp-servers::resolve` — 결정 M4-D2 · D7 의 순서), LSP 의 틀(`pw-lsp::transport` — `Content-Length` 머리 · 본문 상한), Mason registry 설치기(`pw-tools` — `github` · `generic` · `npm` · `pypi`, 고정 해시 · 동의 · 되돌리기), MCP 의 카탈로그 · 그룹(`run` · `debug` 그룹 이름은 이미 받는다) · 노출 · 세션 범위 `ConnectionScope::Agent` 와 관문 `agent_grant`, 계획과 승인 해시(`pw_core::registry::plan` — `ToolPlan` · `PlanRules` · `Planned`), 승인 경로 · 다이얼로그 · OS 알림(`pw_mcp::approval`, `apps/desktop/src/mcp/`), 감사 로그 둘째 판(선기록 · 보관), CLI `pitwall tool`, DB 의 에이전트 SQL 파이프라인(`pw_db::script` — 파일 읽기 · 분류 · 트랜잭션 하나 · 취소 · 감사 상세)과 그 관문(`pw_db::gate` — 사람이 연 연결만 · 프로덕션 표지), 작업(`Task`) · 알림 · 상태바 자리 표(`STATUS_SLOTS`). 아래 표는 그 위에 얹는 것이다.

앞 계획의 「하지 않는 것」 표에서 M6 으로 넘어온 것은 모두 아래 행에 있다: 실행 구성 툴과 `sql` 종류(16-m5-plan.md — M6-09 · M6-12 ~ 14), `exec` 등급의 정책(16-m5-plan.md — M6-10 · M6-11), 디버그 툴(16-m5-plan.md — M6-20), `db_execute` 가 트랜잭션 안에서 못 도는 문장을 따로 돌리는 입력(16-m5-plan.md 결정 M5-D35 — `sql` 구성의 트랜잭션 방식 `none`, M6-09), 디버거 어댑터 설치 · `openvsx` 설치기(15-m4-plan.md — M6-16). `.superpowers/handoff/m5-carry-notes.md` 의 이월 가운데 M6 에 닿는 것은 하나다 — 「끊긴 뒤 5초 동안 Host 의 핸들러가 돈다(rmcp 의 drain, R3)」 가 `run_start` 의 승인에도 같다(M6-14 ⑥). 그 밖의 이월(흔들리는 시험 · git 의 repack 경쟁 · 실기 관찰 O-1 ~ O-3 · M5-13b 리뷰 권고)은 실행 · 디버그와 상관없어 넣지 않았다.

## 1. 작업 목록

「결정 M6-Dn」 은 아래 「4. 착수 전 준비물 · 결정」 의 결정이다. 행의 내용은 그 결정을 따르고, 결정을 바꾸면 그 결정을 가리키는 행을 함께 고친다. 「(결정 대기)」 를 붙인 행은 사람의 답이 오기 전에 시작하지 않는다. 새 파일 · 타입 · 메서드 이름에 「가칭」 을 붙인 것은 그 행이 정한다. 모든 행은 자기가 바꾼 것의 03-architecture.md · 05-mcp.md 「지금 구현」 · 「아직 없다」 문장을 같은 PR 에서 고친다.

**완료 기준의 시험은 「되돌리면 실패하는 시험」 이다** — 그 행의 핵심 판정(관문 · 순서 · 상한 · 거절)을 걷어 내거나 뒤집으면 실패하는 시험을 하나 이상 단다. 리뷰는 그 판정을 한 줄 되돌려 시험이 실패하는지 본다(M5 와 같은 방식). 웹뷰 시험(Vitest)은 0개가 돌아도 실패하지 않는다 — 완료를 보고할 때 `Tests  N passed` 줄의 수를 읽어 적는다(CONTRIBUTING.md 「명령」). 웹뷰 시험은 앱처럼 StrictMode 로 그린다(`apps/desktop/src/test-support`).

| **M6-22** | 성능 확인 | 「가벼움」 은 제품 목적이다(D56). ① 실행 · 디버그를 쓰지 않는 프로젝트의 유휴 메모리 · 콜드 스타트가 M5 끝 측정과 같은 범위(`mise run perf`) — 실행 관리자 · 포트 폴링 · 감지가 빈 프로젝트에서 아무것도 띄우지 않는다 ② 초당 10 MB 를 쓰는 실행 하나에서 콘솔이 프레임을 놓치지 않고(웹뷰 프레임 측정 하네스) Host 메모리가 링 버퍼 상한 + 상수에 머문다 ③ 어댑터는 `debug.start` 때만 뜨고 세션이 끝나면 2초 안에 끝난다 | 실행 선 이후 · 디버그 행 이후 두 번 | 측정 보고(CONTRIBUTING.md 「성능 기준선」) — 판정은 M5 의 측정과 같은 표, 넘으면 원인 행에 되돌린다 |

- 병렬 묶음: (M6-01 · 10 · 15 · 16) → (M6-02 · 03 · 04 · 11) → (M6-05 · 06 · 08 · 09 · 12 · 13 · 17) → (M6-07 · 14) → 실행 선 → (M6-18 · 19 · 20 · 21) → (M6-22). 묶음은 「앞 묶음이 다 끝나야 시작」 이 아니다 — 각 행은 자기 선행이 병합되면 바로 시작한다. **디버그 갈래(M6-15 · 16 · 17)는 첫 묶음부터 실행 갈래와 나란히 돈다** — 실행 선은 순서를 막지 않는다
- **좁은 목은 M6-01(구성 모델)과 M6-02(실행 관리자)다.** 실행 갈래의 모든 행이 둘을 기다린다. 둘은 건드리는 파일이 같은 크레이트(`pw-run`)라 한 워크트리에서 차례로 하되, M6-01 이 병합되면 M6-03 · 04 · 11 이 M6-02 와 나란히 돈다
- **결정을 기다리는 행은 셋이다**: M6-11(M6-D6), M6-19(M6-D2 · D3), M6-21(M6-D5). M6-D4(서비스 뷰)는 권고안이면 행이 없고, 다른 안이면 행이 하나 이상 늘어 「실행 선」 뒤에 선다. M6-D1 은 선을 둘지만 정해 행의 시작을 막지 않는다. 결정이 늦어도 M6-01 ~ 10 · 12 · 13 · 15 ~ 18 · 20 은 돈다 — M6-14 는 M6-11 을 기다리므로 M6-D6 이 실행 선의 마지막 문이다
- M6-10 은 MCP 의 틀을 바꾸는 행이라 실행 툴(M6-13 · 14) · 디버그 툴(M6-20)보다 앞이다. 가짜 툴 메서드로 끝까지 시험하고, 툴 행은 그 위에서 자기 크레이트의 함수만 잇는다(M5 의 틀 셋과 같은 방식)
- 쓰기 · 실행 툴 행(M6-13 · 14 · 20)의 Rust 시험은 가짜 승인 경로로 끝나지만 손으로 하는 확인은 실기 시나리오(「6. 실기 확인」)에서 한다
- 워크트리 단위로 나누기 좋은 경계: 구성 · 실행(01 · 02 · 03) / 감지(04 · 05) / 실행 화면(06 · 07 · 08) / sql(09) / MCP 틀(10 · 11) / 실행 툴(12 · 13 · 14) / DAP(15 · 17) / 설치(16 · 19) / 디버그 화면(18) / 디버그 툴(20) / 복합(21) / 측정(22)

### 공유 부품의 주인

앞 단계와 같이 미리 정한다 — 같은 파일을 크게 건드리는 행은 같은 묶음에 두지 않았고, 여럿이 한 줄씩 더하는 곳은 아래 주인이 틀을 만들고 나머지는 그 틀에 한 줄씩 끼운다. **표에 없는 공유 부품이 필요해지면 만들기 전에 코디네이터에게 묻는다.**

## 4. 착수 전 준비물 · 결정

### 준비물

- **DAP 규격**: Debug Adapter Protocol 의 현재 판(메시지 · 역요청 `runInTerminal` · `startDebugging`)을 M6-15 가 착수 때 확인하고 판을 적는다. 이 초안은 규격 문서를 열어 보지 않았다(추정 — 위 메시지 목록은 널리 쓰는 부분이다)
- **Mason registry 의 DAP 패키지**: 고정 판 2026-11-01 의 `registry.json` 을 받아 확인했다(2026-11-18) — codelldb(`pkg:github/vadimcn/vscode-lldb@v1.12.3`, MIT, `.vsix` 자산, `exec:` bin), js-debug-adapter(`pkg:github/microsoft/vscode-js-debug@v1.140.0`, MIT, `node:js-debug/src/dapDebugServer.js`), debugpy(`pkg:pypi/debugpy@1.8.22`, MIT, `pyvenv:` bin), java-debug-adapter(`pkg:openvsx/vscjava/vscode-java-debug@0.59.0`, **EPL-1.0**, `share` 의 플러그인 jar 만), kotlin-debug-adapter(`pkg:github/fwcd/kotlin-debug-adapter@0.4.4`, MIT), delve(`pkg:golang/…`, MIT). java-debug 의 EPL-1.0 은 jdtls(EPL-2.0)와 같이 사람이 보고 받는 별도 도구라 D10 의 대상 밖으로 보되(D51 의 jdtls 판단과 같다), 설치 확인 창의 라이선스 문구는 M6-19 가 정한다
- **새 의존과 라이선스**(CONTRIBUTING.md 「의존성과 라이선스」): 포트 감지(M6-08 — libproc 바인딩 등을 쓰면), `.env` 파서를 들이면(M6-03 — 손으로 쓰는 것도 길이다). DAP 타입은 직접 정의해 새 의존이 없다(M6-P7)
- **CI**: 새 잡 `dap-live`(M6-19 — ubuntu, 어댑터마다 단계). `db-live` 의 실행 개수 하한을 M6-09 가 올린다
- **사람 확인 한 번씩**: 「6. 실기 확인 시나리오」 — 맥미니 agent-desktop 에서

### 결정 — 사람이 정할 것(결정 필요) · 메인 판정(제안)

M6-D1 ~ D6 은 **결정 필요**다 — 사람의 답을 기다린다. 각 칸의 「권고」 는 메인의 권고이고 사람이 고르기 전까지 확정이 아니다. 이미 사람이 정한 것(D-번호)은 다시 묻지 않는다 — D48 · D55 · D57 · D60 · D61 은 그대로 따른다. M6-P1 ~ P19 는 **메인 판정(제안)** 이다 — 기술 선택이라 사람에게 묻지 않고, 계획 리뷰 뒤 메인이 확정한다. 수치(버퍼 · 시한 · 상한)는 출발값이고 행이 고친다.

## 6. 실기 확인 시나리오 (맥미니 agent-desktop)

계획 끝에 둔다 — 실행 선이 병합된 뒤 1 ~ 7, M6 끝에 8 ~ 12 를 맥미니의 agent-desktop 으로 release 번들에서 확인하고 보고서(`~/pitwall-e2e/m6-e2e-<n>-report.md`)를 남긴다. 각 단계는 화면 · `ps` · 감사 로그 중 무엇으로 확인하는지 함께 적는다.

1. **감지 · 실행 · 링크**: Node 샘플(scripts `dev` · `build`, `mise.toml` 의 tasks 둘)을 신뢰해 연다 → 선택기에 감지됨 넷 → `dev` 를 `⌃R` → 콘솔 색 · `:5173` 포트 → 오류 줄의 `파일:줄` ⌘+클릭 → 에디터 이동(화면)
2. **중지 · 다시 실행 · 트리**: `dev` 를 다시 실행 · 중지 → `ps -o pid,pgid,command` 에 그 트리가 남지 않는다. 같은 구성 둘 띄우기 → 탭 둘
3. **창 수명**: 실행 중에 창을 닫으면 확인(처음 포커스 [취소]) → [끝내고 닫기] → `ps` 로 끝남. 다시 열고 실행한 뒤 웹뷰를 다시 불러오면(개발 메뉴) 앞 출력이 남는다
4. **신뢰**: 같은 샘플을 다른 폴더로 클론해 신뢰하지 않고 연다 → scripts 는 보이고 실행은 「신뢰해야 실행」, `mise` · `gradle` 프로세스가 뜨지 않는다(`ps`)
5. **구성 편집 · env**: 폼으로 `shell` 구성 + `.env.local` → 파일 내용 · 「TOML 보기」 일치, 프로세스의 env(`env` 를 찍는 명령) 확인, `$STATE/logs/` 에 값이 없다(`grep`)
6. **`sql` 구성**: 로컬 PG 에 시드 두 파일 · `all` → 콘솔 형식, 둘째 파일에 오류를 넣어 첫 파일 롤백 확인(`psql`), 파일에 `DELETE` 를 넣어 위험 확인이 뜨는지, `per_file` 로 바꿔 첫 파일이 남는지
7. **에이전트**: Claude Code 에서 「dev 서버 띄우고 로그 봐 줘」 → 화면에서 돌린 적 있는 구성은 승인 없이(감사 로그 `approval = policy`), `run_config_upsert` 로 새 구성 → diff 승인 → 첫 `run_start` 승인 한 번 더 → 터미널에서 그 TOML 의 `command` 를 고친 뒤 `run_start` → 다시 묻는다. `pitwall tool run_logs --run-id … --grep ERROR` 와 종료 코드. `sql` 구성(조회만)은 묻지 않고, `UPDATE` 가 든 것은 매번 묻는다
8. **디버그 설치 · 멈춤**: 결정 M6-D2 의 언어마다 샘플 하나 — 거터에 브레이크포인트 → `⌃D` → 어댑터 설치 확인 창(출처 · 라이선스) → 그 줄에서 멈춤 → 스레드 · 스택 · 변수(펼침) · 워치 · 콘솔 evaluate → `F8` · `F7` · `⇧F8` · `⌘⌥R`
9. **브레이크포인트 종류 · 이동**: 조건 · 로그포인트 · hit count, 위에 줄을 넣어 따라 밀리는지, 앱을 다시 켜도 남는지
10. **attach**: `node --inspect` 로 띄운 프로세스에 attach 구성으로 붙기, JVM 이면 JDWP 5005(결정 M6-D3)
11. **에이전트 디버그 툴**: `breakpoint_set`(조건 있음 — 승인 등급 `exec`) → 거터에 보임 → 멈춘 동안 `debug_state` 의 상한 안 응답
12. **가벼움**: 실행 · 디버그 없이 연 프로젝트의 유휴 메모리를 M5 측정 표와 견준다(M6-22), 디버그 세션을 끝내고 2초 안에 어댑터 프로세스가 없다(`ps`)
