# 17. M6 (실행 · 디버그) 작업 분할

M6 목표: **「IntelliJ 의 실행 · 디버그를 열 이유를 없앤다」 — 프로젝트의 실행 구성(`.pitwall/run/*.toml`)과 감지된 태스크를 한 번에 돌리고, 콘솔에서 로그를 보고, DAP 로 멈춰서 변수를 본다. 에이전트는 같은 구성을 MCP · CLI(`run_*` · `debug_*` 툴)로 만들고 돌리고 로그를 읽되, 사람이 본 적 없는 명령은 승인을 지나야 돈다.** 디버거는 특정 언어에 맞춘 작업 없이 확장 정의 위의 범용 구조(D6 · 06-roadmap.md 「마일스톤」 아래 「주력 언어 미정」 줄)이고, 어댑터 설치는 M4 의 Mason registry 설치기(`pw-tools`)를 넓혀 쓴다. 실행 구성의 `sql` 종류(F6-14 ② — D55)도 이 단계다 — 프로세스를 띄우지 않고 `pw_db::script` 의 실행 경로를 지난다.

이 문서는 **확정판**이다(2026-11-18 — 계획 리뷰를 반영했고, 사람에게 물은 결정 일곱(M6-D1 · D2 · D4 ~ D8)을 모두 사람이 권고안대로 정했으며, 메인 판정 M6-P1 ~ P20(P13 · P19 는 결정 M6-D8 · D7 로 올라가 비었다)도 리뷰를 거쳐 확정이다. D3 은 메인 판정 M6-P20 으로 내렸다). 미정 결정은 없다 — 각 행은 자기 선행이 병합되면 바로 시작할 수 있다(「2. 순서」).

완료 시 할 수 있는 것(사람이 손으로 확인하는 시나리오 — 1 ~ 6 은 「실행 선」 까지, 7 ~ 10 은 그 뒤. 「선」 은 결정 M6-D1):

1. 신뢰한 Node 프로젝트를 열면 실행 선택기(`▶ ▾`)에 `package.json` 의 scripts 와 `mise.toml` 의 tasks 가 「감지됨」 으로 보이고, `dev` 를 고르고 `⌃R` 하면 하단 「실행」 툴 윈도우에 그 구성의 탭이 생겨 색 있는 출력이 흐른다. 출력의 `src/app.ts:12:5` 를 ⌘+클릭하면 에디터가 그 줄로 간다. 탭 머리에 `:5173` 이 보인다(M6-02 · M6-04 · M6-05 · M6-06 · M6-08).
2. 실행 중인 `dev` 를 「다시 실행」 하면 손자 프로세스(vite 의 esbuild 등)까지 끝난 뒤 다시 뜨고, 「중지」 하면 `ps` 에 그 트리가 남지 않는다. 같은 구성을 두 번 띄우면 탭 둘이다. 창을 다시 불러와도(`⌘R` 개발 빌드 · 창 다시 열기) 앞 출력이 그대로 보인다(M6-02 · M6-06).
3. 실행 선택기 「구성 편집」 에서 `shell` 구성을 폼으로 만들고(이름 · 명령 · 작업 폴더 · env · `.env` 파일) 저장하면 `.pitwall/run/<id>.toml` 이 생기고 「TOML 보기」 가 같은 내용이다. `.env.local` 의 값이 프로세스에 들어가고, 로그 파일에는 변수 이름만 남는다(M6-01 · M6-03 · M6-07).
4. `sql` 구성(연결 `local-pg`, 파일 `db/seed.sql` · `db/fixtures.sql`, 트랜잭션 「전부 하나」)을 실행하면 프로세스 없이 콘솔에 문장마다 번호 · 줄 · 영향 행 수 · 소요가 찍힌다. 파일에 `DELETE` 가 있으면 실행 전에 SQL 콘솔과 같은 위험 확인이 뜬다. 둘째 파일에서 실패하면 첫째 파일의 변경도 롤백됐다고 적힌다(M6-09).
5. 클론한 저장소를 신뢰하지 않은 채 열면 감지 목록에 `package.json` 의 scripts 는 보이되 실행하면 「이 프로젝트를 신뢰해야 실행한다」 와 신뢰 액션이 뜨고, `mise` · `gradle` 은 돌지 않는다(`ps` 로 확인 — M6-02 · M6-05, F1-7).
6. Claude Code 에 「dev 서버 띄우고 로그 봐 줘」 라고 하면 `run_config_list` → `run_start` → `run_logs` 로 이어지고, 사람이 그 구성을 앞서 UI 에서 돌린 적이 있으면 묻지 않고 돈다. 에이전트가 `run_config_upsert` 로 새 구성을 만들면 diff 승인이 뜨고, 그 구성의 첫 `run_start` 는 명령 · 작업 폴더 · env 의 이름과 값(비밀 키는 가린다)을 보이는 승인이 한 번 더 뜬다(결정 M6-D6). 에이전트가 `.pitwall/run/dev.toml` 이나 `.env.local` 을 파일 시스템에서 직접 고친 뒤 `run_start` 하면 다시 묻는다. 「이 세션 동안 허용」 은 그 구성의 그 내용에만 닿는다. `pitwall tool run_logs --run-id … --grep ERROR` 도 같다(M6-10 ~ 14).
7. 기본 번들 언어(결정 M6-D2) 프로젝트에서 줄 번호 옆을 눌러 브레이크포인트를 두고 `⌃D` 하면 어댑터가 없을 때 처음 한 번 출처 · 라이선스를 묻고 설치한 뒤, 그 줄에서 멈춘다 — 에디터에 현재 줄, 「디버그」 툴 윈도우에 스레드 · 콜스택 · 변수(펼칠 때 읽는다) · 워치, 디버그 콘솔에서 식을 평가한다. `F8` · `F7` · `⇧F8` · `⌘⌥R` 로 스텝 · 계속(M6-15 ~ 19). Java 는 attach 구성으로 — 대상은 JDWP 를 켜고 띄운 프로세스다(9 와 같다 — 메인 판정 M6-P20).
8. 조건(`i > 3`) · 로그포인트(`i = {i}`) · hit count 브레이크포인트가 그대로 돈다. 파일을 고쳐 줄이 밀리면 브레이크포인트도 따라 밀리고, 앱을 다시 열어도 남아 있다(M6-17 · M6-18).
9. 이미 `--inspect` 로 떠 있는 Node 프로세스(JVM 이면 JDWP 포트 5005 — 메인 판정 M6-P20)에 attach 구성으로 붙어 같은 화면을 본다(M6-17 · M6-19). — **Node 는 후속 M6-19b**: js-debug v1.140.0 의 attach 자식 세션이 브레이크포인트를 묶지 않는다(원시 DAP 로도 — M6-19 보고). JVM attach 는 M6-19 에서 확인했다
10. 에이전트가 `breakpoint_set`(조건 · 로그가 있으면 `breakpoint_set_expr`)을 부르면 승인 뒤 에디터 거터에 그 브레이크포인트가 보이고, 멈춘 동안 `debug_state` 가 정지 위치 · 스택 · 지역 변수 요약을 돌려준다(M6-20).

**「실행 선」**(결정 M6-D1): 실행 구성 · 감지 · 콘솔 · `sql` 종류 · MCP 실행 툴(**M6-01 ~ 14**)이 병합된 때다. 사람이 이 단계에서 직접 물은 것(실행 구성 실행 · 로그 · SQL 파일 되풀이 실행 — 16-m5-plan.md 「3. M5 에서 하지 않는 것」 의 첫 행)이 선 위에 있다. 그 뒤가 DAP · 디버그 화면 · 디버그 툴 · 복합 구성이다(M6-15 ~ 21). 디버그 행은 선과 상관없이 선행이 되면 나란히 돈다 — 선은 「여기까지면 실행은 쓸 수 있다」 는 표지이고 순서를 막지 않는다.

M6 이 끝났을 때 MCP 툴은 34개다: M5 의 22 + 실행 구성 8(`run_config_list` · `run_config_upsert` · `run_config_delete` · `run_start` · `run_stop` · `run_restart` · `run_status` · `run_logs`) + 디버그 4(`breakpoint_list` · `breakpoint_set` · `breakpoint_set_expr` · `debug_state`). 05-mcp.md 「실행 구성」 · 「디버그」 표에 `breakpoint_set_expr` 하나를 더한 것이다(메인 판정 M6-P17 — 「5」 13).

대상 플랫폼: macOS(개발 · 검증), Linux/Windows 는 CI 빌드 · 시험(06-roadmap.md 「결정 기록」 D38). 프로세스 트리 끝내기 · 포트 감지는 플랫폼마다 다른 구현이고 macOS 를 먼저 맞춘다 — Windows 의 PTY · 트리 끝내기는 지금 터미널과 같은 수준(ConPTY · Job object 는 이 단계의 시험 밖, 「3. M6 에서 하지 않는 것」).

M5 까지 된 것은 다시 계획하지 않는다 — 내장 터미널의 PTY 세션(`crates/pw-run` 의 `pty` · `tree` · `shell` · `integration`, 셸 세션 통째로 끝내기 · 앱 종료 때 `pw_run::shutdown`), 런타임 환경(`pw-runtime` — 로그인 셸 · mise 의 `mise env --json` · 디렉터리 캐시 · 신뢰 게이트 `Runtime::with_trust`), 프로젝트 신뢰(`pw_core::registry::trust` — 워크트리는 메인 저장소 프로젝트의 신뢰를 따른다), 실행의 연결 범위(`pw_core::registry::exec::exec_grant` — 그 프로젝트 창만, MCP 세션은 아무것도 띄우지 못한다), 터미널 출력의 `파일:줄` 링크(`apps/desktop/src/terminal/terminal-links.ts`), 툴 윈도우 자리 `run` · `debug`(`apps/desktop/src/layout/project-layout.ts` — 지금은 빈 자리), 설정 계층(`.pitwall/run/` 한 단계를 이미 읽는다 — 03-architecture.md 「설정 계층」)과 한 키 쓰기(`pw_core::config::write`), 확장 매니페스트(`pw-ext` — `[contributes.language_servers]` 까지), 언어 서버의 실행 파일 해석(`pw-lsp-servers::resolve` — 결정 M4-D2 · D7 의 순서), LSP 의 틀(`pw-lsp::transport` — `Content-Length` 머리 · 본문 상한), Mason registry 설치기(`pw-tools` — `github` · `generic` · `npm` · `pypi`, 고정 해시 · 동의 · 되돌리기), MCP 의 카탈로그 · 그룹(`run` · `debug` 그룹 이름은 이미 받는다) · 노출 · 세션 범위 `ConnectionScope::Agent` 와 관문 `agent_grant`, 계획과 승인 해시(`pw_core::registry::plan` — `ToolPlan` · `PlanRules` · `Planned`), 승인 경로 · 다이얼로그 · OS 알림(`pw_mcp::approval`, `apps/desktop/src/mcp/`), 감사 로그 둘째 판(선기록 · 보관), CLI `pitwall tool`, DB 의 에이전트 SQL 파이프라인(`pw_db::script` — 파일 읽기 · 분류 · 트랜잭션 하나 · 취소 · 감사 상세)과 그 관문(`pw_db::gate` — 사람이 연 연결만 · 프로덕션 표지), 작업(`Task`) · 알림 · 상태바 자리 표(`STATUS_SLOTS`). 아래 표는 그 위에 얹는 것이다.

앞 계획의 「하지 않는 것」 표에서 M6 으로 넘어온 것은 모두 아래 행에 있다: 실행 구성 툴과 `sql` 종류(16-m5-plan.md — M6-09 · M6-12 ~ 14), `exec` 등급의 정책(16-m5-plan.md — M6-10 · M6-11), 디버그 툴(16-m5-plan.md — M6-20), `db_execute` 가 트랜잭션 안에서 못 도는 문장을 따로 돌리는 입력(16-m5-plan.md 결정 M5-D35 — `sql` 구성의 트랜잭션 방식 `none`, M6-09), 디버거 어댑터 설치 · `openvsx` 설치기(15-m4-plan.md — M6-16). `.superpowers/handoff/m5-carry-notes.md` 의 이월 가운데 M6 에 닿는 것은 하나다 — 「끊긴 뒤 5초 동안 Host 의 핸들러가 돈다(rmcp 의 drain, R3)」 가 `run_start` 의 승인에도 같다(M6-14 ⑥). 그 밖의 이월(흔들리는 시험 · git 의 repack 경쟁 · 실기 관찰 O-1 ~ O-3 · M5-13b 리뷰 권고)은 실행 · 디버그와 상관없어 넣지 않았다.

## 1. 작업 목록

「결정 M6-Dn」 은 아래 「4. 착수 전 준비물 · 결정」 의 결정이다. 행의 내용은 그 결정을 따르고, 결정을 바꾸면 그 결정을 가리키는 행을 함께 고친다. 결정은 모두 확정이다(2026-11-18). 새 파일 · 타입 · 메서드 이름에 「가칭」 을 붙인 것은 그 행이 정한다. 모든 행은 자기가 바꾼 것의 03-architecture.md · 05-mcp.md 「지금 구현」 · 「아직 없다」 문장을 같은 PR 에서 고친다.

**완료 기준의 시험은 「되돌리면 실패하는 시험」 이다** — 그 행의 핵심 판정(관문 · 순서 · 상한 · 거절)을 걷어 내거나 뒤집으면 실패하는 시험을 하나 이상 단다. 리뷰는 그 판정을 한 줄 되돌려 시험이 실패하는지 본다(M5 와 같은 방식). 웹뷰 시험(Vitest)은 0개가 돌아도 실패하지 않는다 — 완료를 보고할 때 `Tests  N passed` 줄의 수를 읽어 적는다(CONTRIBUTING.md 「명령」). 웹뷰 시험은 앱처럼 StrictMode 로 그린다(`apps/desktop/src/test-support`).

## 4. 착수 전 준비물 · 결정

### 준비물

- **DAP 규격**: Debug Adapter Protocol 의 현재 판(메시지 · 역요청 `runInTerminal` · `startDebugging`)을 M6-15 가 착수 때 확인하고 판을 적는다. 이 계획은 규격 문서를 열어 보지 않았다(추정 — 위 메시지 목록은 널리 쓰는 부분이다). **확인함(2026-11-18, M6-15)**: 규격은 1.71.x(`microsoft/debug-adapter-protocol` 의 `debugAdapterProtocol.json` — 저장소 HEAD `1b52c204`, 그 파일의 마지막 바뀜 `1d5bfe02` 2026-11-01). 위 메시지 목록은 모두 규격에 있다. 1.71 이 `RunInTerminalRequest.cwd` 를 URI 로도 받게 적었으나 그것은 클라이언트가 `pathFormat = "uri"` 를 알린 때다 — Pitwall 은 `path` 를 알린다. 어댑터의 연결: codelldb v1.12.3 은 `--port` · `--connect` 없이 띄우면 **stdio** 다(`src/codelldb/src/lib.rs` — `--port` 는 127.0.0.1 에 고정으로 묶는다) — 계획의 「포트를 쓰는 어댑터(codelldb · js-debug)」 추정 중 codelldb 는 stdio 로 쓴다. js-debug v1.140.0 의 `dapDebugServer.js` 는 stdio 가 없고 인자가 `[port|socket path=8123] [host=localhost]` 다 — 첫 인자가 수가 아니면 그 소켓 경로에서 받으므로 `{socket}` 으로 정의한다(M6-15 리뷰 F1 — 포트면 `{port} {host}` 로 127.0.0.1 에 묶지만 같은 기기의 다른 사용자를 막지 못한다). java-debug 의 `vscode.java.startDebugSession`(jdtls 플러그인 명령)은 `microsoft/java-debug` main 의 `JavaDebugServer` 가 `new ServerSocket(0, 1)` 로 **모든 주소**에 묶는다(소스로만 봄 — 최신 태그 0.53.2 와 main 의 그 파일이 같다고 M6-15 리뷰가 확인했다. 0.59.0 번들의 판은 M6-19 가 실제로 본다). M6-15 리뷰가 더 본 것: ① **연결을 계속 받는다** — `while (true) { accept() }` 로 동시에 100 개까지, ② **jdtls 수명 내내 열린다** — 싱글턴이고 `stop()` 을 부르는 곳이 없어, 처음 디버그를 시작한 때부터 그 jdtls 가 끝날 때까지 디버그 세션이 끝나도 닫히지 않는다, ③ **인증 없는 `launch` 로 원격 실행** — 같은 네트워크의 다른 기기가 붙어 `launch`(`javaExec` · `vmArgs` · `classPaths` · `mainClass`)로 그 사용자 권한의 임의 실행, `attach` 로 그 기기에서 닿는 JDWP 안의 코드 실행이 된다. jdtls 쪽 설정으로 주소를 바꾸는 길은 없다. **정함(2026-11-18, 사용자 — 06 결정 D71)**: `JavaDebugServer` 를 loopback 에 묶는 한 줄(`new ServerSocket(0, 1, InetAddress.getLoopbackAddress())`)만 고친 포크 jar 를 직접 빌드해 번들한다(EPL-1.0). 버린 대안: 기본 꺼짐 + 위험 고지 후 켬, 디버그 뒤 jdtls 재시작 + 고지, Java 를 번들 디버거에서 빼기. 상류 PR 은 사람이 따로 정한다(외부에 올리는 일). **실측(2026-11-19, M6-19 `dap-live` — macOS arm64)**: 듣는 TCP 주소는 모두 loopback 이다 — codelldb 는 표준 입출력(터미널 에이전트의 포트도 127.0.0.1 — v1.12.3 `terminal.rs`), js-debug 는 소켓 경로 + 디버그 대상의 inspector `127.0.0.1`, debugpy 는 어댑터 · 런처 포트 둘 다 `127.0.0.1`, 패치한 java-debug 는 `127.0.0.1:<포트>`(LAN 주소로 붙으면 거절). 상류 jar 는 `*:<포트>` 에 묶이고 LAN 주소로 붙은 연결에 DAP 로 답했다(D71 의 근거 실측). 0.59.0 vsix 가 묶는 플러그인은 `com.microsoft.java.debug.plugin-0.53.2.jar`(클래스 major 65 — Java 21)

## 6. 실기 확인 시나리오 (맥미니 agent-desktop)

계획 끝에 둔다 — 실행 선이 병합된 뒤 1 ~ 7, M6 끝에 8 ~ 12 를 맥미니의 agent-desktop 으로 release 번들에서 확인하고 보고서(`~/pitwall-e2e/m6-e2e-<n>-report.md`)를 남긴다. 각 단계는 화면 · `ps` · 감사 로그 중 무엇으로 확인하는지 함께 적는다.

1. **감지 · 실행 · 링크**: Node 샘플(scripts `dev` · `build`, `mise.toml` 의 tasks 둘)을 신뢰해 연다 → 선택기에 감지됨 넷 → `dev` 를 `⌃R` → 콘솔 색 · `:5173` 포트 → 오류 줄의 `파일:줄` ⌘+클릭 → 에디터 이동(화면)
2. **중지 · 다시 실행 · 트리**: `dev` 를 다시 실행 · 중지 → `ps -o pid,pgid,command` 에 그 트리가 남지 않는다. 같은 구성 둘 띄우기 → 탭 둘
3. **창 수명**: 실행 중에 창을 닫으면 확인(처음 포커스 [취소]) → [끝내고 닫기] → `ps` 로 끝남. 다시 열고 실행한 뒤 웹뷰를 다시 불러오면(개발 메뉴) 앞 출력이 남는다
4. **신뢰**: 같은 샘플을 다른 폴더로 클론해 신뢰하지 않고 연다 → scripts 는 보이고 실행은 「신뢰해야 실행」, `mise` · `gradle` 프로세스가 뜨지 않는다(`ps`)
5. **구성 편집 · env**: 폼으로 `shell` 구성 + `.env.local` → 파일 내용 · 「TOML 보기」 일치, 프로세스의 env(`env` 를 찍는 명령) 확인, `$STATE/logs/` 에 값이 없다(`grep`)
6. **`sql` 구성**: 로컬 PG 에 시드 두 파일 · `all` → 콘솔 형식, 둘째 파일에 오류를 넣어 첫 파일 롤백 확인(`psql`), 파일에 `DELETE` 를 넣어 위험 확인이 뜨는지, `per_file` 로 바꿔 첫 파일이 남는지
7. **에이전트**: Claude Code 에서 「dev 서버 띄우고 로그 봐 줘」 → 화면에서 돌린 적 있는 구성은 승인 없이(감사 로그 `approval = policy`), `run_config_upsert` 로 새 구성 → diff 승인 → 첫 `run_start` 승인 한 번 더 → 터미널에서 그 TOML 의 `command` 를 고친 뒤 `run_start` → 다시 묻는다. 구성 A 에 「이 세션 동안 허용」 뒤 `.env.local` 의 값 하나만 바꾸거나 구성 B 를 부르면 → 다시 묻는다. `pitwall tool run_logs --run-id … --grep ERROR` 와 종료 코드. `sql` 구성(조회만)은 묻지 않고, `UPDATE` 가 든 것은 매번 묻는다
8. **디버그 설치 · 멈춤**: 결정 M6-D2 의 언어마다 샘플 하나 — 거터에 브레이크포인트 → `⌃D` → 어댑터 설치 확인 창(출처 · 라이선스) → 그 줄에서 멈춤 → 스레드 · 스택 · 변수(펼침) · 워치 · 콘솔 evaluate → `F8` · `F7` · `⇧F8` · `⌘⌥R`. Java 는 attach 구성으로 — 대상은 JDWP 를 켜고 띄운 프로세스다(실기 10 과 같다)
9. **브레이크포인트 종류 · 이동**: 조건 · 로그포인트 · hit count, 위에 줄을 넣어 따라 밀리는지, 앱을 다시 켜도 남는지
10. **attach**: `node --inspect` 로 띄운 프로세스에 attach 구성으로 붙기, JVM 이면 JDWP 5005(메인 판정 M6-P20)
11. **에이전트 디버그 툴**: `breakpoint_set`(조건 없음 — `write`)과 `breakpoint_set_expr`(조건 있음 — `exec`) → 거터에 보임 → 멈춘 동안 `debug_state` 의 상한 안 응답
12. **가벼움**: 실행 · 디버그 없이 연 프로젝트의 유휴 메모리를 M5 측정 표와 견준다(M6-22), 디버그 세션을 끝내고 2초 안에 어댑터 프로세스가 없다(`ps`)
