# 06. 로드맵 · 리스크 · 미결정 사항

## 1. 마일스톤

| 단계 | 목표 | 포함 기능 |
|---|---|---|
| **M0. 기반** | 뼈대 | cargo/pnpm 워크스페이스, Tauri 셸(macOS), RPC + 타입 생성(+role 메타데이터), Host 추상, 이벤트 버스, 프로젝트 레지스트리, 단일 인스턴스/CLI, **확장 레지스트리 구조 · 테마 토큰 · i18n 기반** |
| **M1. 탐색** | "열어서 본다" | F2 파일→프로젝트, F3 파일 트리/검색, F4-1·2 에디터, F8 다른 도구로 열기, F11 레이아웃/팔레트/키맵 |
| **M2. Git** | IntelliJ git 대체 | F5 그래프·필터·커밋·스테이징·체크아웃·머지·충돌 해결·blame·파일 히스토리, 에디터 거터 |
| **M3. 실행** | IntelliJ 실행 대체 | F7 실행 구성·태스크 감지·콘솔·터미널, DAP(Node/Python/JVM attach) |
| **M4. DB** | DataGrip 대체 (기본) | F6 PG/MySQL/SQLite, 스키마 탐색, 콘솔, 그리드, 안전장치, SSH 터널 |
| **M5. LSP** | 코드 탐색 | F4-3 LSP 핵심, 서버 관리자, 심볼 인덱스 |
| **M6. MCP** | 에이전트 연동 | F10 전체 |
| **M7. 원격** | Relay | F9 — `pw-link`, Relay 데몬 · 설치 · 페어링, 직접/SSH 연결, 이후 Hub |
| **M8. 모바일** | 컴패니언 | F12 P0 — iOS 우선, 알림 · MCP 승인 · 실행 제어 · git 조회 |
| **M9. 확장 공개** | 외부 확장 | F13 — 테마/언어 팩/코드 언어 확장 설치, VS Code 테마 import, 이후 WASM 플러그인 |
| v1.0 | 안정화 | P1 항목, 자동 업데이트. macOS 정식 출시 → Linux/Windows 순차 |

- **MVP = M0~M4 + M6 일부(조회 툴)**. 순서는 "IntelliJ를 여는 이유" 빈도순(git → 실행/디버그 → DB)으로 배치
- LSP를 M5로 미룬 이유: 에이전트 중심 워크플로에서 코드 탐색 빈도가 상대적으로 낮고, 구현 범위가 큼. 그동안은 tree-sitter 하이라이트 + 텍스트 검색으로 커버
- MCP를 M6에 두지만, RPC 계약을 M0에서 확정하므로 툴 추가 비용은 낮음 — 필요 시 앞당김
- 원격 · 모바일 · 확장은 뒤 단계지만 **M0에서 구조를 먼저 깔아둔다**: Host 추상 + 전송 독립 RPC + 메서드별 role 메타데이터 + 확장 레지스트리. 내장 기능을 처음부터 이 구조 위에 올려 나중에 리팩터링하지 않게 함
- 플랫폼: M0~M6는 macOS에서 개발 · 검증, Linux/Windows는 CI 빌드 유지. Relay는 Linux도 1급

## 2. 성능 목표 (검증 기준)

| 항목 | 목표 |
|---|---|
| 콜드 스타트 → 프로젝트 창 표시 | < 1.5s |
| 유휴 메모리 (LSP 제외, 프로젝트 1개) | < 300MB |
| git 그래프 첫 화면 (10만 커밋 저장소) | < 500ms, 스크롤 60fps |
| 파일 퍼지 검색 (10만 파일) | 키 입력당 < 30ms |
| 쿼리 결과 10만 행 그리드 | 스크롤 60fps, 스트리밍 표시 |

## 3. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| Linux WebKitGTK 렌더링 성능/버그 | UI 끊김 | canvas 렌더링 + 가상화, 조기 벤치마크(M1). 최악엔 UI만 Electron 교체(코어 헤드리스라 가능) |
| DAP 어댑터별 편차 (특히 Java) | 디버깅 품질 | JVM은 우선 attach 모드(JDWP)만 보장, launch는 jdtls 통합 후 |
| LSP 서버 메모리 (jdtls, kotlin) | "가벼움" 훼손 | 언어 서버 지연 기동, 유휴 종료, 프로젝트별 on/off |
| Relay 배포 복잡도 (OS/arch/glibc) | 원격 실패 | musl 정적 빌드, 버전 고정 · 해시 검증, 버전 협상 |
| Relay Hub 운영 부담(공용 Hub 제공 시) | 비용 · 보안 책임 | 셀프호스팅 우선, 직접 연결(Tailscale 등) 권장, 공용 Hub는 이후 검토 |
| 모바일 푸시의 E2E 암호화 | 구현 복잡 | iOS Notification Service Extension에서 복호화, 초기에는 "알림 있음"만 보내고 앱에서 조회하는 방식으로 시작 가능 |
| 확장 API 조기 고착 | 하위 호환 부담 | 공개 전까지 내부 전용, WIT 인터페이스 버전 관리 |
| 범위 팽창 (IntelliJ 재구현 유혹) | 일정 | 01-product 비목표 목록을 기준으로 리뷰 |

## 4. 미결정 사항 (확인 필요)

1. **Orca 연동 방식** — Orca의 CLI/딥링크 스펙 확인 필요. worktree 기반이라면 F5-15(worktree)와 연계해 "worktree를 Orca로 열기" 제공 가능
2. **주력 언어/프레임워크** — 초기 DAP/LSP 우선순위 결정용 (JVM 비중이 높다면 jdtls/Kotlin LSP를 M3/M5에서 우선)
3. **편집 기능 수위** — 자동완성/포맷까지 P1로 둘지, 뷰어 + 간단 편집으로 고정할지
4. **DB 드라이버 우선순위** — 사용하는 DB 종류 (Oracle/MSSQL 필요 여부)
5. **`.pitwall/` 커밋 정책** — 팀 공유를 전제할지, 개인 전용(기본 gitignore)으로 할지
6. **라이선스/공개 여부** — 오픈소스 여부에 따라 번들 가능한 디버그 어댑터/LSP 결정, 확장 레지스트리 운영 방식
7. **Relay Hub 운영** — 셀프호스팅만 지원할지, 공용 Hub를 제공할지 (모바일 푸시 전송 주체와 연결됨)
8. **모바일 플랫폼** — iOS만 먼저 출시할지, Android 동시 지원할지

## 5. 결정 기록
- OS: 멀티 OS 지원, **macOS 우선** (Tier 1)
- 확장: 테마 · UI 언어 · 코드 언어 · 플러그인 확장을 고려하여 설계 (07)
- 원격: 원격 머신에 **Relay 설치** 방식 (SSH는 설치 보조 · 대체 수단) (08)
- 모바일: 내용 확인 + 간단 조작 컴패니언 앱 (08)
