# 워크트리를 지울 때

## 워크트리를 지우기 전에 두 관문을 통과시킨다

**하나라도 걸리면 지우지 않는다.**

```bash
git merge-base --is-ancestor <워크트리브랜치> <기준브랜치>   # 미병합 커밋이 있으면 거부
git -C <워크트리> status --porcelain                        # 미커밋 변경이 있으면 거부
```

- **Why:** 둘은 서로를 대신하지 못한다. **병합됐는데도 미커밋 변경이 남아 있는 워크트리가 실제로 나온다** — 병합 여부만 보고 일괄 정리하면 그 작업이 사라진다. 반대로 마지막 정리 커밋이 병합 뒤에 붙는 일도 있다.
- **How to apply:**
  - 기준 브랜치가 틀리면 관문은 **덜 지우는 쪽으로** 틀린다(미병합으로 보여 거부) — 안전한 방향으로 실패한다.
  - **일괄 정리와 강제 우회를 함께 쓰지 않는다.** 한 명령이 저장소의 모든 워크트리에서 미병합 커밋과 미커밋 파일을 확인 없이 버리게 된다. 먼저 dry-run 으로 보고, 버릴 것을 정했으면 **하나씩 지목해서** 우회한다.
  - 우회할 때는 **무엇을 버리는지 목록을 먼저 출력한다.**

## 「병합됐고 미커밋 없음」은 「다 썼다」가 아니다

위 두 관문은 **git 이 아는 것**만 본다. 사람이 아직 쓰는 중인 워크트리는 그 관문을 **통과한다.**

- **Why:** 커밋이 전부 들어갔고 미커밋도 0이라 관문을 통과해 지워졌는데 **사용자가 계속 쓰던 작업 환경**인 경우가 실제로 있다. 코드 손실이 없어도 체크아웃과 터미널이 사라져 사용자가 다시 만들어야 한다. **「다 썼다」는 판단은 사람만 할 수 있다.**
- **How to apply:** 쓰는 중인 워크트리에는 **마커 파일을 두어 보호하고**, 정리 도구가 그것을 **다른 무엇보다 먼저** 보게 한다. 보호된 것은 **강제 우회로도 지우지 않는다** — 먼저 보호를 푸는 것이 사람의 명시적인 행동이어야 한다.
