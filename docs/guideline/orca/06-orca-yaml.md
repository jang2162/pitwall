# orca.yaml

## orca.yaml 은 저장소 루트에 두고 아는 키만 쓴다

Orca 가 읽는 최상위 키는 여섯 개다. 그 밖의 키는 무시된다.

| 키 | 내용 |
| --- | --- |
| `scripts.setup` | 새 워크트리를 만든 직후 그 워크트리 안에서 도는 스크립트 |
| `scripts.archive` | 워크트리를 보관하거나 지우기 전에 도는 스크립트 |
| `setupAgentStartupPolicy` | `wait-for-setup` 또는 `start-immediately` |
| `worktree.sharedDirectories` | 주 체크아웃에서 새 워크트리로 나눠 줄 경로 목록 |
| `defaultTabs` | 새 워크트리에 열 터미널 탭. 항목마다 `title`·`command`·`color`(`#rgb` 또는 `#rrggbb`) |
| `issueCommand` | 연결된 이슈·PR 로 워크스페이스를 시작할 때 쓰는 명령 틀. 이슈·PR 주소 자리는 `{{artifact_url}}` |

환경별 일회용 런타임(`environmentRecipes`)은 이 문서가 다루지 않는다. 절차는 `orca skills get orca-per-workspace-env` 가 갖는다.

- **Why:** 문법 오류나 중복 키가 있으면 **파일 전체가 조용히 무시된다.** 부분만 적용되지 않고, 셋업이 안 도는데 워크트리 생성은 성공한다. 크기 한계도 같은 결과다 — 파일 256KB, 필드 하나 64KB, 목록 항목 256개 넘으면 읽지 않는다.
- **How to apply:**
  - 파일은 **저장소 루트의 주 체크아웃**에서 읽는다. 워크트리 브랜치에서만 고친 `orca.yaml` 은 그 브랜치가 주 체크아웃에 들어오기 전에는 적용되지 않는다.
  - 쓴 뒤 앱의 저장소 설정에서 `orca.yaml` 을 쓰는 중으로 보이는지 확인한다. 「구문 분석할 수 없습니다」 로 보이면 YAML 을 고친다.
  - 파일은 팀과 공유되는 설정이므로 커밋한다. 개인 머신에서만 다른 값은 넣지 않는다.

## 셋업 스크립트는 런타임을 먼저 맞추고 의존성을 설치하며, 실패하면 멈춘다

`scripts.setup` 은 새 워크트리 디렉터리에서 돈다. 환경 변수 셋을 쓸 수 있다.

| 변수 | 값 |
| --- | --- |
| `$ORCA_ROOT_PATH` | 주 체크아웃 경로 |
| `$ORCA_WORKTREE_PATH` | 만들어지는 워크트리 경로 |
| `$ORCA_WORKSPACE_NAME` | 워크스페이스 이름(보통 브랜치 이름에서 온다) |

- **Why:** 순서가 바뀌거나 앞 단계가 실패하고도 다음 줄이 돌면 의존성이 **지금 PATH 에 있는 런타임**으로 깔린다(`base` 스택 「워크트리를 만들 때」). 그리고 gitignore 된 로컬 설정은 워크트리로 따라오지 않아, 빌드가 샘플 값으로 조용히 채우면 앱이 엉뚱한 대상을 본다.
- **How to apply:**
  - 런타임을 맞추는 명령을 첫 줄들에, 의존성 설치를 그 뒤에 둔다. 스크립트 맨 위에 `set -e` 를 둔다.
  - 로컬 설정은 `$ORCA_ROOT_PATH` 에서 **디렉터리째** 복사한다. 이미 샘플로 채워진 경우를 고치려면 덮어쓰는 복사여야 한다.
  - 여러 줄은 `|` 블록으로 쓴다.
    ```yaml
    scripts:
      setup: |
        set -e
        <런타임을 맞추는 명령>
        <의존성 설치 명령>
        cp -R "$ORCA_ROOT_PATH/<로컬 설정 디렉터리>" "$ORCA_WORKTREE_PATH/"
    ```
  - 워크트리를 만든 뒤에는 런타임 버전과 의존성이 실제로 맞는지 직접 잰다(`orca-worker` 스킬 「셋업 훅이 무엇을 했는지 믿지 말고 잰다」).

## 에이전트가 셋업 결과에 기대면 `setupAgentStartupPolicy: wait-for-setup` 으로 둔다

`wait-for-setup` 은 셋업이 종료 코드 0 으로 끝난 뒤에 에이전트를 시작한다. `start-immediately` 는 셋업과 동시에 시작한다.

- **Why:** 의존성을 설치하는 셋업이면 `start-immediately` 에서는 에이전트가 **설치 중인 워크트리**에서 일을 시작해, 반쯤 깔린 상태로 빌드·테스트를 돌린다. 셋업이 0 이 아닌 코드로 끝나거나 기다리는 시간 안에 끝나지 않으면 「충족하지 못함」 으로 처리된다.
- **How to apply:** 셋업이 에이전트의 작업 전제(런타임·의존성·로컬 설정)를 만들면 `wait-for-setup`. 셋업이 짧은 알림이나 정리뿐이면 `start-immediately` 로 둬도 된다. 정책은 새 워크스페이스를 만들 때 사람이 바꿀 수도 있다.

## 아카이브 스크립트에는 워크트리를 지우기 전에 내릴 것을 둔다

`scripts.archive` 는 워크트리를 보관하거나 지우기 전에 돈다. 그 워크트리가 띄운 컨테이너·볼륨처럼 **지운 뒤에는 찾기 어려운 것**을 거기서 정리한다.

- **Why:** 컨테이너만 내리는 명령은 named volume 을 남겨, 워크트리를 지우고 나면 볼륨이 고아로 쌓인다(`base` 스택 「워크트리를 만들 때」).
- **How to apply:** 정리 명령은 `$ORCA_WORKTREE_PATH` 안의 것만 건드리게 쓴다. 경로를 기준으로 하지 않는 전역 정리(`prune` 류)는 넣지 않는다 — 다른 워크트리의 것까지 지운다.

## `worktree.sharedDirectories` 에는 워크트리가 쓰기 대상으로 삼지 않는 디렉터리만 넣는다

저장소 루트 기준 상대 경로 목록이다. 새 워크트리를 만들 때 각 경로를 macOS(APFS)에서는 가능하면 복제 복사하고, 그렇지 않으면 주 체크아웃의 것을 **심볼릭 링크**로 건다.

- **Why:** 링크가 되는 환경에서는 워크트리에서 쓴 내용이 **주 체크아웃의 그 디렉터리에 그대로 쓰인다.** 환경마다 복사와 링크로 갈리므로, 같은 설정이 어떤 머신에서는 격리되고 어떤 머신에서는 공유된다.
- **How to apply:**
  - 워크트리가 읽기만 하거나 어느 쪽에 써도 무방한 큰 디렉터리(캐시처럼 다시 만들 수 있는 것)에 쓴다.
  - 경로는 `a/b` 꼴로 쓴다. 절대 경로, `..`, `.git`, 경로 중간의 `.` 이나 빈 칸은 버려진다. 항목은 100개까지 읽는다.
  - 로컬 설정처럼 워크트리마다 달라질 수 있는 파일은 여기 말고 셋업에서 복사한다.

## 스크립트 출처가 갈리는 것을 사람에게 알린다

Orca 는 `orca.yaml` 의 스크립트와 개발자 앱 설정의 로컬 스크립트를 함께 알고, 출처 정책(`orca.yaml` 만 / 로컬만 / 둘 다)으로 고른다. 정책을 정한 적이 없고 로컬 스크립트가 있으면 **로컬만** 쓴다.

- **Why:** 앱에 로컬 셋업을 넣어 둔 개발자에게는 `orca.yaml` 의 셋업이 **조용히 돌지 않는다.** 저장소만 봐서는 보이지 않는다.
- **How to apply:**
  - `orca.yaml` 을 새로 넣었으면 팀원에게 앱의 저장소 설정에서 스크립트 출처를 `orca.yaml` 로 맞추라고 알린다. 앱 설정은 CLI 로 바꿀 수 없다.
  - 셋업을 돌릴지는 저장소 설정(묻기 / 자동 / 고를 때만)이 정한다. 한 번만 강제하려면 `orca worktree create --setup run|skip|inherit`.
  - `defaultTabs` 의 `command` 는 셋업과 같은 정책을 따른다. 로컬만 쓰는 설정이면 돌지 않는다. 신뢰할 수 없는 명령을 넣지 않는다.
  - `issueCommand` 는 저장소의 `.orca/issue-command` 파일(개인용)이 있으면 그것이 우선한다. 그 파일은 커밋하지 않는다.
