# 터미널을 끄고 워크트리를 회수할 때

## 터미널을 끌 때 평문 목록을 grep 하지 않는다

핸들이 필요하면 **범위를 좁힌 JSON** 에서 꺼낸다.

```bash
orca terminal list --worktree "id:<repoId>::<path>" --json | jq -r '.result.terminals[].handle'
```

- **Why — 둘이 동시에 어긋난다.** ① **그 목록은 머신 전역이다.** 저장소 경계가 없어 다른 프로젝트의 터미널이 같은 목록에 섞인다. ② **한 항목이 여러 줄이고 길이가 가변이다**(핸들 줄 + 미리보기 + 빈 줄). `grep -B`/`-A` 로 창을 잡으면 그 창이 **앞뒤 항목을 통째로 삼키고** 삼킨 항목의 핸들까지 딸려 나온다. 미리보기 길이가 화면 내용에 따라 달라지므로 **맞는 창 크기 자체가 없다.**
  그렇게 만든 루프는 **조용히 성공한다** — 껐다는 것만 알고 무엇을 껐는지는 모른다. 끈 것이 다른 프로젝트의 워커든 자기 자신의 세션이든 출력이 같고, 전부가 아니라 창에 걸린 **연속 구간**만 꺼지므로 일부가 살아남아 「내 필터가 들었다」로 읽힌다.
- **How to apply:**
  - 파괴 명령에는 **정확 일치 셀렉터**만 준다(`orca terminal stop --worktree "id:<repoId>::<path>"`).
  - ⚠ **함정은 빈 셀렉터다.** `--worktree ""` 는 오류가 아니라 **전역 목록을 그대로 낸다** — 셀렉터를 변수로 조립할 때 **그 변수가 비면 범위가 조용히 전역으로 넓어진다.** 셀렉터를 만들기 전에 repo id 가 비었는지 보고, 비면 멈춘다.
  - `id:` 셀렉터는 정확 일치다. 없는 경로를 주면 **0건**이고, 실패했다고 해서 더 넓은 셀렉터로 **물러나지 않는다.**
  - **자기가 서 있는 워크트리는 끄지 않는다.**
  - **「전부」와 「도는 워커도 끊어라」를 함께 쓰지 않는다.** 합치면 한 번에 전부 끊고 종료코드 0 이 되어, 코드는 남지만 진행 중인 워커의 문맥이 전부 사라지고 **출력만 보고는 무엇을 끊었는지 알 수 없다.** 먼저 dry-run 으로 보고, 끊을 것을 정했으면 하나씩 지목한다.

## 회수는 회수 가능한 것에만 부른다 — 「회수 N건」이 사실이어야 한다

판정은 `worker-list` 항목의 **`terminalState`** 로 한다. 그것이 런타임 자신의 회수 회계 어휘다.

| `terminalState` | 부르는가 | 왜 |
| --- | --- | --- |
| `reclaimable` | **부른다** | 우리가 쥐었고 아직 회수하지 않은 settled 워커다 |
| `released` | 안 부른다 | 이미 끝났다 |
| `retained` | 안 부른다 | 서버가 거절한다(사용자가 넘겨받았거나 신원이 증명되지 않은 터미널) |
| `active` | 안 부른다 | settled 가 아니다 — **지금 돌고 있는 워커이고, 자기 자신일 수도 있다** |
| 그 밖의 값·모르는 값 | 안 부른다 | 판정할 수 없다 — **fail closed** |

- **Why:** `retained` 와 `released` 에 회수를 불러도 **아무 프로세스도 닫히지 않는다.** 그런데 종료코드는 0이라, **부른 횟수를 그대로 세면 아무것도 회수하지 않고도 「회수 N건」이 찍힌다.** 다음 사람은 그것을 「회수됐구나」로 읽는다.
- **How to apply:**
  - 출력은 **회수한 것 / 건너뛴 것과 그 이유 / 실패한 것**을 나눠 센다.
  - **모르면 부르지 않는다.** `worker-list` 는 **머신 전역**이라, 여기서 한 번 느슨해지면 그 대상이 남의 프로젝트가 된다.
  - **소유 증명과 회수 대상 판정은 다른 일이다.** 증명은 「이 워크트리 것인가」를, 판정은 「부르면 무엇이 닫히는가」를 묻는다. 증명 단계에서 상태로 걸러 버리면 **건너뛴 것과 그 이유를 볼 방법이 없어진다.**
  - 항목에 워크트리 id 가 최상위 필드로 **없다.** 증명하는 길은 둘이고 둘 다 정확 일치다 — 자원 기록의 워크트리 id 가 같거나, 에이전트 터미널 핸들이 그 워크트리의 핸들 집합에 있거나. **없는 필드로 거르면 항상 0건이 되어 회수가 조용히 생략되고, 느슨하게 거르면 남의 프로젝트 워커를 회수한다 — 둘 다 종료코드로는 성공으로 보인다.**

## 폐기 순서가 곧 요구사항이다

**회수 → 터미널 정지 → 폐기 → 잔해 제거** 순으로 한다.

- **Why:** 터미널이 살아 있으면 워크트리 제거가 실패한다. 마지막 잔해 제거가 빠지면 빌드 데몬이 되살린 껍데기 디렉터리가 쌓이는데, **그것은 `git worktree list` 에도 Orca 목록에도 없어서 열거되지 않는다** — 그래서 실제로 쌓인 잔해에는 아무것도 닿지 못한다.
- **How to apply:**
  - **Orca 가 만들었거나 인식한 워크트리는 Orca 로 지운다**(`orca worktree rm --worktree id:<fullId>`). git 으로만 지우면 **Orca 메타데이터에 유령 항목이 남는다.**
  - **`orca worktree rm` 은 삭제가 끝나기 전에 `ok: true` 를 돌려준다.** 곧바로 `git branch -d` 를 부르면 「브랜치가 워크트리에서 쓰이는 중」으로 실패한다. `git worktree list` 에서 그 경로가 사라졌는지 확인한 다음 브랜치를 다룬다. Orca 가 지운 워크트리의 브랜치는 Orca 가 함께 지우므로, 사라진 뒤 「브랜치 없음」이 나오는 것은 정상이다.
  - **잔해 디렉터리에도 터미널이 붙어 있을 수 있다.** 워크트리 등록이 사라져도 그 디렉터리에서 돌던 터미널은 남고, 워크트리 기준으로는 세지지 않아 **전역 터미널 목록을 경로로 세어야만 보인다.** 하나라도 붙어 있으면 **강제 옵션으로도 지우지 않는다** — **여기서 세지 못한 것을 0으로 넘기면 워커가 도는 작업 디렉터리가 통째로 지워진다.** 그래서 **셀 수 없을 때도 「붙어 있다」로 친다.**
  - 심볼릭 링크를 사이에 둔 두 표기가 같은 디렉터리를 가리키므로 **양쪽을 실물 경로로 맞춘 뒤 비교한다** — 글자만 비교하면 같은 디렉터리를 다른 것으로 보고 0을 내고, **그 0이 곧 삭제 허가가 된다.**
  - **자기가 서 있는 워크트리는 건너뛴다** — 워크트리 안의 워커가 일괄 정리를 돌리는 일이 실제로 생기고, 가드가 없으면 자기 발밑이 무너진다.
