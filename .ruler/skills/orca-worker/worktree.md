# Orca 로 워크트리를 만들 때

## 기준 브랜치를 넘기지 않으면 원격 기본 브랜치에서 시작한다

`--base-branch` 를 **반드시 명시**하고, 넘길 값은 **「지금 세션이 서 있는 브랜치」**다.

- **Why:** 기본값이 원격 기본 브랜치(`origin/main`)다. 로컬에서 커밋만 하고 push 가 드문 저장소에서 그것은 **상시 낡아 있고 시간이 갈수록 벌어진다.** 옵션을 빼면 워크트리가 그만큼 낡은 코드로 시작하고, **워커는 방금 쓴 스펙 문서조차 찾지 못한다.** 기본 브랜치 이름을 박아 넘기는 것도 같은 사고다 — 메인 세션이 다른 브랜치에 서 있으면 **그 세션이 방금 만든 커밋이 통째로 빠진다.**
- **How to apply:**
  - 값은 물어보지 말고 받아서 넘긴다.
    ```bash
    BASE=$(git branch --show-current)
    ```
  - **워크트리를 만드는 경로가 둘이면 양쪽 다 넘긴다** — 생성 명령에도, 워커 기동 명령이 워크트리를 함께 만드는 형태일 때도 같은 옵션이 있다.
  - 넘겼더라도 **워커를 띄우기 전에 재는 것이 가장 싸다.**
    ```bash
    git reflog show <브랜치> | tail -1          # "Created from refs/heads/<기준>" 이어야 한다
    git rev-list --count <브랜치>..<기준브랜치>  # 0 이어야 한다
    ```
  - **0 이 아니면 워커를 띄우기 전에 되감는다**(`git -C <워크트리> reset --hard <기준브랜치>`). **이미 워커가 돌고 있었다면 커밋이 있어도 버리고 다시 띄우는 쪽이 싸다** — 낡은 기준에서 만든 커밋은 리베이스가 충돌 범벅이 된다.
  - ⚠ **이 옵션을 요약 문서에서 빼지 않는다.** 상세에 적혀 있어도 요약만 보고 만든 워크트리가 전부 옛 기준이 되는 사고가 실제로 난다 — `base` 스택 「인용과 문서」의 「가르치는 자리가 여럿이면 전부 맞아야 한다」.

## 셋업 훅이 무엇을 했는지 믿지 말고 잰다

`--setup run` 이 성공해도 워크트리가 쓸 수 있는 상태라는 뜻은 아니다.

- **Why:** 훅은 저장소의 `orca.yaml` 과 **Orca 앱 설정**(개발자 로컬) 두 곳에서 오고, 로컬 스크립트가 있으면 `orca.yaml` 을 가릴 수 있어 저장소만 봐서는 무엇이 도는지 알 수 없다. 게다가 훅이 **순서를 어기고 있을 수 있다** — 런타임을 신뢰하기 전에 의존성을 설치하면 어느 런타임으로 깔렸는지 보장되지 않는다.
- **How to apply:**
  - 생성 직후 **런타임 버전과 의존성이 실제로 맞는지 직접 잰다.** 아니면 워크트리 안에서 손으로 돌린다 — **런타임을 먼저**, 그 다음 의존성(`base` 스택 「워크트리를 만들 때」).
  - **gitignore 된 로컬 설정은 따라오지 않고, 「없음」으로 남지도 않는다.** 빌드가 샘플 값으로 조용히 채우면 워크트리의 앱이 **엉뚱한 대상을 본다** — 로그에는 접속 실패 스택만 찍혀 설정이 바뀐 것이 보이지 않는다. 최상위에서 **디렉터리째** 복사하고, 이미 샘플로 채워졌으면 그대로 덮어쓴다(「없을 때만 복사」는 그 경우를 고치지 못한다).
  - 훅 자체를 고치려면 공유 훅은 `orca.yaml` 을 고치고(`orca` 스택 「orca.yaml」), 로컬 훅과 스크립트 출처는 **앱 설정에서 고친다** — 앱 설정은 CLI 로 바꿀 수 없다.

## 워크트리가 생기는 자리는 만든 뒤에 반환 경로로 잰다

설정을 미리 들여다보지 말고, 만든 뒤 반환 JSON 의 `path` 가 `<저장소>/.worktrees/` 아래인지 잰다.

- **Why:** 생성 위치는 Orca 앱 설정이 정하고, 그 값은 저장소 설정에도 전역 설정에도 있을 수 있다. 저장소 설정(`orca repo show` 의 `worktreeBasePath`)만 보면 **전역 설정으로 맞게 만들어지는 저장소를 「설정 없음」으로 잘못 멈춘다.** 반대로 설정이 비어 있으면 워크트리가 저장소 루트 밖에 생기고, 그렇게 생긴 워크트리는 **다른 에이전트가 찾지 못하고 `.gitignore` 도 덮지 못한다.** 도구가 「워크트리 생성 실패」로 끝나도 **워크트리는 실제로 만들어져 엉뚱한 자리에 잔해로 남을 수 있다.** 어느 경우든 실제로 생긴 자리를 재는 것이 유일하게 확실하다.
- **How to apply:**
  - 만든 직후 반환 JSON 의 `path` 를 본다. `.worktrees/` 아래이고 `git check-ignore -q <path>/x` 가 성공하면 맞다.
    ```bash
    git check-ignore -q "<path>/x" && echo ignored
    ```
  - **아니면 워커를 붙이기 전에** `orca worktree rm` 으로 지우고, 사람에게 앱 설정(저장소 또는 전역)의 워크트리 위치를 고쳐 달라고 알린다. CLI 로 우회하려다 엉뚱한 자리에 다시 만들지 않는다 — `worktree create` 에는 생성 위치를 받는 옵션이 없다(`--name` 은 이름이지 경로가 아니다). 잘못된 자리에 워커를 붙이고 나면 그 워커가 만든 커밋까지 함께 옮겨야 한다.
  - 「생성 실패」로 끝났으면 `orca worktree list --json` 으로 잔해가 생겼는지 보고, 있으면 지운다.
