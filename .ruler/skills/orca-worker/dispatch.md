# 일을 맡기고 기다릴 때

## 역할이 기본 모델을 정하고, 모델은 별칭으로만 쓴다

워커의 모델을 정하는 방식을 바꾸는 스택이 프로젝트 지침에 있으면 그 스택을 따른다. 아래 표는 그런 스택이 없을 때의 기본이다.

| 역할 | 기본 모델 | 맡기는 일 |
| --- | --- | --- |
| `implement` | 상위 | 설계 판단이 섞인 구현 |
| `review` | 상위 | 리뷰어. **판단이 곧 산출물이라 낮추지 않는다** |
| `verify` | 하위 | 정해진 검증을 실행하고 결과를 보고(테스트·스모크) |
| `chore` | 하위 | 정해진 패턴의 기계적 일괄 변경, 문서 갱신 |

- **Why — 기본값을 두는 이유:** 매번 고민하지 않게 하되 **예외는 명령줄에 명시로 남기기** 위해서다. `--model` 이 붙어 있으면 「왜 기본과 다르게 골랐나」가 그 자리에 기록된다.
- **Why — 별칭만 쓰는 이유:** 별칭은 항상 그 계열의 최신 세대에 붙는다. 모델 ID 를 박으면 **다음 세대가 나온 날 스크립트와 문서가 전부 낡는다.**
- **How to apply:** 역할로 부르고, 다르게 골라야 하면 `--model` 로 덮는다. 모델 ID 는 쓰지 않는다.

## 워커를 띄웠으면 곧바로 수신 대기에 들어간다

제출을 확인했으면 바로 `check --wait --types worker_done,escalation,question` 으로 기다린다.

- **Why:** 워커가 물어봐도 코디네이터가 수신하고 있지 않으면 **타임아웃까지 방치되고**, 워커는 스스로 가정을 세워 진행하거나 멈춘다. 브리프 오류를 발견한 워커의 질문이 무응답으로 흘러 워커가 독자 판단으로 진행한 사례가 있다.
- **How to apply:**
  - **타임아웃은 실패가 아니라 체크포인트다.** 긴 코딩 작업은 15~60분이 예사다. 타임아웃을 보고 워커가 죽었다고 판단하지 말고 **같은 명령을 다시 부른다.**
  - 대기하지 못할 상황이면, 최소한 **워커가 물어볼 만한 지점**(브리프에 확신이 없는 값, 기존 코드와 충돌 가능성)을 **디스패치 spec 에 미리 판단해 넣어 둔다.**

## `escalation` 과 `worker_done` 을 같은 턴에 보내면 승인 후 보고 경로가 사라진다

승인을 보내기 **전에** dispatch 상태를 본다.

- **Why:** `worker_done` 은 dispatch 를 `completed` 로 끝낸다. 코디네이터가 승인을 회신하고 워커가 구현을 이어가도 **그 dispatch 로는 더 이상 보고할 수 없다** — 워커는 멀쩡히 일을 끝내는데 코디네이터는 오지 않을 완료 보고를 기다린다.
- **How to apply:** `orca orchestration dispatch-show --task <task_id> --json` 으로 상태를 보고, `completed` 면 **보고 전용 dispatch 를 새로 건다.** 그 spec 첫 줄에 **「새 작업이 아니다. 하던 것을 이어서 하라」**를 박지 않으면 **워커가 처음부터 다시 시작한다.**
