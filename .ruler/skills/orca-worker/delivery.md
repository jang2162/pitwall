# 배달은 조용히 막힌다 — `ok: true` 는 상대가 봤다는 뜻이 아니다

아래는 전부 **에러 없이 실패해서 타임아웃까지 방치된다.**

## `reply` 는 큐에만 넣고 워커를 깨우지 않는다

- **Why:** `dispatch --inject` 는 터미널 입력에 직접 쓰지만 `reply` 는 **메시지 큐에만** 넣는다. 워커가 escalation 을 보내고 **턴을 끝낸** 상태면 스스로 `check` 하지 않으므로, 승인을 보내고 `ok: true` 를 받아도 워커는 계속 대기만 한다.
- **How to apply:** 회신 뒤 `terminal send` 로 「큐의 회신을 읽고 진행하라」고 깨우고, **제출됐는지 터미널을 읽어 확인한다**(`base` 스택 「워커에게 브리프를 보낼 때」).

## 대기자가 도는 중에 `check` 를 또 돌리지 않는다

- **Why:** 둘이 같은 배달을 두고 경쟁해서 **한쪽이 가져가면 다른 쪽은 못 받는다.**
- **How to apply:** 대기자를 백그라운드로 띄웠으면 그 출력만 읽는다. 알림이 와도 손으로 `check` 하지 않는다 — **하트비트는 대기자의 필터에 안 걸리므로 알림만 반복되는 것이 정상**이고 대응할 것이 없다.

## ack 은 delivery id 를 명시한다

- **Why:** 바인딩된 Run 은 ack 전까지 **같은 배달을 계속 재생한다.** ack 하지 않으면 큐가 막혀 다음 메시지가 오지 않고, **먼저 끝난 워커의 보고가 다음 대기에서 그대로 다시 나와 아직 도는 워커를 끝난 것으로 오인한다.**
- **How to apply:** `check` 응답의 `result.deliveryId` 를 `--ack` 로 넘긴다. **배달 하나에 메시지가 여럿 들어 있으니 전부 처리한 뒤** ack 한다.

## `--wait` 출력을 한 번에 파싱하면 죽는다

- **Why:** keepalive 를 **stderr 에 한 줄씩** 뱉는다. `2>&1` 로 합치면 결과 JSON 과 섞여 파싱이 깨진다.
- **How to apply:** **stderr 를 합치지 않는 것이 정답**이고, 이미 합쳐진 스트림은 앞에서부터 잘라 읽는다.
  ```python
  dec, s, objs = json.JSONDecoder(), text.lstrip(), []
  while s:
      obj, end = dec.raw_decode(s)
      objs.append(obj); s = s[end:].lstrip()
  ```

## 폴링 루프를 만들지 말고 대기자는 하나만 유지한다

- **Why:** `check` 는 배달을 **소비**하는 명령이라, 백그라운드 루프가 살아 있으면 그것이 `worker_done` 을 가로채고 대기자는 빈손으로 기다린다. **둘 다 조용히 성공해서 어느 쪽도 에러를 내지 않는다.**
- **How to apply:** 새 대기자를 띄우기 전에 매번 기존 것을 죽이고, **ack 을 먼저 하고 대기자를 띄운다** — 순서가 바뀌면 새 대기자가 이미 처리한 배달을 다시 가져간다. 이상하면 `pgrep -fl 'orchestration check'` 로 무엇이 도는지부터 본다.

## 대기자는 이 세션만의 것이 아니다

- **Why:** 같은 머신의 **다른 저장소 세션**도 자기 대기자를 돌린다. 뭉뚱그린 `pkill -f` 는 남의 대기자까지 끊고, 그쪽이 새로 띄우는 사이 내 배달이 그쪽으로 갈 수도 있다 — **양쪽 다 에러를 내지 않는다.**
- **How to apply:** `pgrep -fl 'orchestration check'` 로 보고 **PID 를 지목**해 끊는다. 대기자 **하나가 프로세스 셋**으로 뜨고 저장소 경로는 래퍼 줄에만 보이므로, **줄 수를 대기자 수로 읽지 말고** 소유자는 `lsof -a -p <pid> -d cwd` 로 확인한다.

## 대기자를 버렸으면 기상 장치를 대체한다

- **Why:** 코디네이터는 **턴이 들어와야만** 동작한다 — 백그라운드 `check --wait` 가 끝나며 만드는 턴이 **유일한 자체 기상 장치**였다. 수동 폴링으로 갈아타면 폴링은 턴 안에서만 도니 **깨워 주는 것이 없다.**
- **How to apply:** **`dispatch-show` 는 읽기 전용이라 배달을 뺏지 않는다** — 이것을 폴링해 `completed` 에서 끝나는 명령을 기상 장치로 쓴다.
  ```bash
  for t in <task_id> ...; do
    until orca orchestration dispatch-show --task "$t" --json | grep -q '"status": *"completed"'; do sleep 60; done
  done
  ```
  - 이 폴러는 **하네스가 추적하는 백그라운드 실행으로 띄운다** — 셸에서 `&`·`nohup` 으로 detach 하면 끝나도 턴이 안 생긴다.
  - 출력이 pretty-print 라 **공백 없는 패턴으로 쓰면 영영 안 맞는다.**
  - **「기다리겠습니다」라고 말하기 전에 기상 장치가 추적되는 형태로 떠 있는지 확인한다** — 없으면 영원히 안 깨어난다.

## 닫힌 Dispatch 의 워커에게 이어서 일을 시키면 완료 신호가 막힌다

`worker_done` 을 보낸 워커의 터미널에 `terminal send` 로 수정 회차를 보내면, 워커는 일은 하지만 **Dispatch 는 이미 닫혀 있다.**

- **Why:** 그 워커의 `ask` 는 활성 Dispatch 가 없다며 거절되고, `worker_done` 은 거절(`Rejected`)로 표시된다. 거절된 완료가 대기자에게 배달될 때도 있고 오지 않을 때도 있어서, 대기자만 믿으면 **끝난 회차를 타임아웃까지 기다린다.** 질문이 막히므로 워커는 판단이 필요한 자리에서 묻지 못하고 자기 판단으로 진행한다.
- **How to apply:**
  - 질문 경로가 필요한 회차는 **새 Task 를 세워 그 터미널에 붙인다**(`worker-start.md` 「붙이기가 실패해도 워크트리를 버리지 않는다」 절 — 그 터미널의 직전 Dispatch 가 성공이면 재시도로 잇지 않는다).
  - `terminal send` 로 보낼 때는 완료를 **보고서 파일의 표식**으로 받는다 — 보내는 글에 「끝나면 보고서 끝에 `<표식>` 한 줄」을 적고, `until grep -q '<표식>' <보고서>; do sleep 10; done` 을 **하네스가 추적하는 백그라운드 실행으로** 띄운다(「대기자를 버렸으면 기상 장치를 대체한다」).
  - 거절된 `worker_done` 이 배달되면 그것도 결과로 읽고 ack 한다.

## 배달이 안 오는데 dispatch 가 이미 `completed` 면

**메시지는 이미 소비된 것이다.** 기다리지 말고 `git log`·`git diff`·워크트리 `git status`·터미널 스크롤백으로 **결과를 직접 확인**해 판정한다.

**커밋·워크트리 변화가 `dispatch` 상태보다 앞선 신호다** — `dispatch` 는 워커가 `worker_done` 을 보내야 바뀌므로 일이 끝났는데도 한동안 `dispatched` 로 남는다. 판정은 셋을 함께 본다 — `dispatch-show` 상태 · 브랜치 커밋 · 터미널(입력창과 활동).
