# guideline-export

**이 스킬은 지침을 올릴 프로젝트에서 실행한다.** 이 프로젝트의 지침을 읽어 다른 프로젝트에서도 참인 절을 가려내고, 사용자가 고른 것만 지침 서버에 제안으로 올린다.

## 전제 확인

1. **원본을 받는다.** 빈 임시 폴더를 정해(예: `mktemp -d` 아래의 `src`) `guideline source <폴더>` 를 실행한다. 이 프로젝트의 `guideline.json` 에 출처가 둘 이상이면 어느 출처(지침 서버)에 올릴지 사용자에게 묻고 `guideline source <폴더> --source <이름>` 으로 받는다. 이하 「원본 폴더」 다. 「로그인 필요」 가 나오면 `! guideline login --server <URL>` 을 안내하고 멈춘다.
2. **보내면 어떻게 되는가.** 올리기 전에 `guideline propose --from <원본 폴더> --dry-run --json` 의 `mode` 로 판단한다(글 출력이면 「보내면 바로 반영됨」·「보내면 검토를 기다리는 제안이 됨」 줄). 실제로 보낼 때와 같은 토큰·서버로 묻는 것은 이 dry-run 뿐이다. `guideline status` 의 「토큰:」 줄은 참고만 한다 — 출처가 여럿이거나 `GUIDELINE_TOKEN` 이 있으면 `status` 와 `propose --from` 이 다른 토큰을 쓸 수 있다.
   - `mode` 가 `apply` 면 `guideline propose` 는 **제안 대신 바로 반영한다** — 검토 없이 원본이 그 자리에서 바뀐다. 보내기 전에 사용자에게 「검토 없이 바로 반영된다」 고 알린다. 사용자가 검토를 받겠다고 하면 `guideline propose --from <원본 폴더> --title <제목> --review` 로 제안으로 올린다.
   - `mode` 가 `proposal` 이면 제안으로 올라가고, 관리자가 웹 「제안」 에서 수락해야 원본이 된다. 「토큰 범위를 확인하지 못해 제안으로 보냄」 경고가 함께 나오면 범위를 몰라 제안으로 가는 것이다 — 바로 반영할지는 사용자에게 묻고, 원하면 `--apply` 를 붙인다.
   - 올릴 때 「제안 권한이 없는 토큰」 가 나오면 관리자에게 범위 `propose` 토큰을 받아 `guideline login --server <URL> --token-stdin` 으로 넣으라고 안내하고 멈춘다.
3. `<원본 폴더>/docs/authoring.md` 에 `## 서브에이전트`, `## MCP 서버` 절이 없으면 서브에이전트나 MCP 를 올리기 전에 멈추고, 지침 관리자에게 그 절을 원본에 더해 달라고 알린다. README 로 만드는 MCP 서버를 올릴 때는 `### 반영할 때 항목을 만드는 서버` 절도 본다.
4. `<원본 폴더>/docs/authoring.md` 에 `## 칸 — 상시와 참조` 절이 없으면 지침 파일을 올리기 전에 같은 방법으로 멈춘다. 칸을 정하는 기준이 그 절에 있다. `다른 스택을 바꿈` 을 올릴 때는 `## 다른 스택을 바꿀 때` 절도 본다.
5. **받은 사본을 고친 것은 이 스킬이 아니다.** `guideline status` 에 「프로젝트에서 고침」 으로 나오는 사본은 `guideline propose` 로 올린다(사본을 원본 모양으로 되돌려 준다). 이 스킬은 프로젝트 고유 지침을 새로 올린다. `propose` 는 처음 받을 때부터 원본과 달랐던 사본(할 일 `adopted`)을 빼는데, 옛 판을 올리면 원본 변경을 되돌리기 때문이다.

## 절차

1. **이 프로젝트의 지침을 모은다.** 형태를 가리지 않는다.
   - `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.ruler/`, `.claude/rules/`, `.cursor/rules/`, `.github/copilot-instructions.md`, 하위 디렉터리의 지침 파일, 프로젝트 스킬(`.claude/skills/`, `.agents/skills/`, `.ruler/skills/`)
   - 서브에이전트: `.claude/agents/`, `.codex/agents/`, `.cursor/agents/`, `.github/agents/`, `.ruler/agents/`
   - MCP 설정: `.mcp.json`, `.codex/config.toml`, `.cursor/mcp.json`, `.ruler/ruler.toml` 의 `[mcp_servers]`·`[agents.<에이전트>.mcp_servers]`, `.ruler/mcp.json`
   - `sync-guideline`·`guideline-sync` 가 쓴 사본은 원본의 사본이므로 스택 후보로 다시 올리지 않는다: `.ruler/<스택>/`(원본 스택과 같은 이름), `docs/guideline/`, 색인(`.ruler/<스택>/99-reference.md`, 지침 파일의 `## <스택> 참조 지침` 절), 관리 지침(`.ruler/guideline.md`, 지침 파일의 `## 공용 지침 관리` 절), 지침 파일의 `guideline:begin`~`guideline:end` 블록과 `guideline.json`·`guideline-lock.json`. 세팅 문서 사본(`docs/guideline/<스택>/SETUP.md`)도 `docs/guideline/` 에 든다. frontmatter 를 뗀 원본과 다르면 그 차이를 `이미 있음 / 충돌` 표에 보고한다.
   - 프로젝트 바꿈(`.ruler/<스택>/override.md`, `.ruler/<스택>/override.d/*.md`, 지침 파일의 `## <스택> 프로젝트 바꿈` 절)은 그 프로젝트가 원본을 의도적으로 바꾼 것이다. 스택 후보로 올리지 않고 4번의 「프로젝트 바꿈」 표에 보인다.
   - 생성물과 원본이 함께 있으면(ruler 를 쓰는 프로젝트의 `CLAUDE.md`, `.claude/agents/`, `.mcp.json`) 원본(`.ruler/`)만 읽는다. 두 파일이 서로 사본이면 하나만 읽는다.

2. **원본의 구성을 파악한다.** `guideline list <원본 폴더>` 를 돌려 스택(지침 파일과 칸)·스킬·서브에이전트·MCP 를 보고, 관련 있는 파일과 `docs/authoring.md` 를 읽는다.

3. **절(`##`/`###`) 단위로 분류한다.** 스킬·서브에이전트·MCP 서버는 하나씩 분류한다.

   | 분류 | 기준 |
   | --- | --- |
   | 스택 후보 | 이 프로젝트만의 이름(스크립트, 패키지, 클래스, 컬럼, 포트, 사람)이 없고 다른 프로젝트에서도 참인 절. 어느 스택에 넣을지 정한다. 맞는 스택이 없으면 새 스택을 제안한다. 어느 프로젝트에서나 참인 규칙은 `base` 같은 범용 스택에 넣는다. 칸(`always`·`reference`)도 `docs/authoring.md` 의 기준으로 정한다 |
   | 다른 스택을 바꿈 | 후보 절이 다른 스택의 절과 같은 주제를 **특정 환경에서** 다르게 가르친다(예: Orca 가 살아 있으면 워크트리를 Orca 로 만든다). 대상에 바꾸는 절과 바뀌는 절을 함께 적는다. 환경 조건 없이 다르면 `원본과 충돌` 이다 |
   | 스킬 후보 | 다른 프로젝트에서도 쓸 만한 이 프로젝트의 스킬 |
   | 서브에이전트 후보 | 다른 프로젝트에서도 쓸 만한 이 프로젝트의 서브에이전트 |
   | MCP 후보 | 다른 프로젝트에서도 쓸 만한 MCP 서버. 특정 프로젝트의 호스트·DB·저장소를 가리키면 프로젝트 고유로 둔다. 다만 그 값이 프로젝트마다 다를 뿐 프로젝트 안에서 알아낼 수 있으면(예: GitLab 호스트는 `git remote` 에서) README 로 만드는 MCP 후보로 올릴 수 있다 |
   | 이미 있음 | 원본의 어느 파일 어느 절과 같은 취지인지 적는다 |
   | 원본과 충돌 | 같은 주제인데 규칙이 다르다. 어느 쪽이 맞는지는 사용자가 판단한다 |
   | 프로젝트 고유 | 나머지. 개수만 보고한다 |

4. **표로 보고하고 사용자가 고른 항목만 올린다.**

```
## 지침 내보내기 — <프로젝트> → 지침 서버

### 후보
| 출처 파일 · 절 | 분류 | 대상 | 칸 | 근거 |
| --- | --- | --- | --- | --- |
| CLAUDE.md · 「검증 없이 완료 보고 금지」 | 스택 후보 | rules/base/05-verification.md | always | 프로젝트 이름 없음, 일반 원칙 |
| CLAUDE.md · 「Orca 가 살아 있으면 워크트리도 Orca 로 만든다」 | 다른 스택을 바꿈 | rules/orca/05-switch.md 「…」 → base/01-git.md 「워크트리는 저장소 안에 만들고, 하나의 작업이 하나를 갖는다」 | always | Orca 가 떠 있을 때만 워크트리 생성 명령·위치가 다르다 |
| .mcp.json · jira | MCP 후보 | mcp/jira/ | — | 팀 공용 Jira. headers.Authorization 에 값이 박혀 있어 참조로 바꾼다 |
| .mcp.json · gitlab | MCP 후보 (README 로 만듦) | mcp/gitlab/README.md | — | url 의 호스트가 git remote 의 호스트와 같다. 다른 GitLab 을 쓰는 프로젝트가 있어 반영할 때 만든다 |

### 이미 있음 / 충돌
| 출처 파일 · 절 | 원본 | 내용 |
| --- | --- | --- |

### 프로젝트 바꿈
| 바꿈 | 바꾸는 절 | 제안 |
| --- | --- | --- |
| .ruler/base/override.md 「워크트리는 ~/worktrees 에 만든다」 | base/06-worktree-setup.md 「워크트리는 저장소 안에 만들고, 하나의 작업이 하나를 갖는다」 | 프로젝트에 둠 |

프로젝트 고유 절: N개
```

   「프로젝트 바꿈」 의 제안은 셋 중 하나다: **원본을 고침**(그 바꿈이 어느 프로젝트에서나 맞다), **스택 사이 바꿈으로 올림**(특정 환경에서만 다르다 — `다른 스택을 바꿈` 으로 처리한다), **프로젝트에 둠**. 사용자가 고른 것만 반영한다.

5. **원본 폴더에 쓴다.** `docs/authoring.md` 규칙에 따라 범용 문구로 다듬어 `rules/<스택>/` 이나 `skills/` 에 쓴다.
   - 프로젝트 이름, 스크립트 경로, 포트, 사람 이름을 지운다.
   - 규칙 → Why → How to apply 순서를 맞춘다. Why 가 원문에 없으면 사용자에게 묻고 지어내지 않는다.
   - 파일이 200줄을 넘으면 나눈다.
   - 새 지침 파일 맨 위에 frontmatter 로 `load` 를 달고, `reference` 면 `when` 도 단다(`docs/authoring.md` 「칸 — 상시와 참조」). 기존 파일에 절을 더할 때 그 절의 칸이 파일의 칸과 다르면 다른 파일에 둔다.
   - `다른 스택을 바꿈` 은 바꾸는 절을 좁은 스택의 `load: always` 파일에 쓰고, 그 스택 `README.md` 의 `## 다른 스택을 바꾸는 것` 표에 행을 더한다(`docs/authoring.md` 「다른 스택을 바꿀 때」). 바뀌는 넓은 스택의 파일에는 좁은 스택을 가리키는 글을 쓰지 않는다.
   - 서브에이전트는 `agents/<이름>.md` 로 쓴다. frontmatter 는 `name`·`description`·`tools`·`model` 만 남기고, 값에 `: ` 가 있으면 큰따옴표로 감싼다. Codex `.toml` 에서 올리면 `developer_instructions` 를 본문으로 옮긴다.
   - MCP 는 `mcp/<이름>/server.json` 과 `README.md` 로 쓴다. `docs/authoring.md` 의 MCP 절대로 변수 참조를 쓴다. Codex 설정에서 올리면 `env_vars = ["X"]` 는 `env` 의 `"X": "${X}"` 로, `bearer_token_env_var = "X"` 는 `headers` 의 `"Authorization": "Bearer ${X}"` 로, `env_http_headers` 의 `"H" = "X"` 는 `headers` 의 `"H": "${X}"` 로, `http_headers` 는 `headers` 의 고정값으로 옮긴다.
   - 값이 프로젝트마다 달라 README 로 만드는 MCP 는 `server.json` 을 쓰지 않고 `README.md` 에 `## 반영할 때 항목 만들기` 절을 쓴다(`docs/authoring.md` 의 「반영할 때 항목을 만드는 서버」). 값을 어디서 읽어 어떻게 뽑는지 지어내지 않는다. 출처 프로젝트에서 그 값이 어디서 왔는지 확인되지 않으면 사용자에게 묻는다.
   - 다 쓴 뒤 `guideline list <원본 폴더>` 를 돌려 이번에 쓴 파일이 `무시됨`·`경고`(칸·바꿈 경고 포함) 에 없는지 확인한다. 있으면 고치고, 고정값 경고처럼 그대로 둘 것이면 사용자에게 알린다. README 로 만드는 MCP 는 `MCP` 절에 `반영할 때 README 로 만듦` 로 나오는지 본다.

6. **올린다.** 먼저 `guideline propose --from <원본 폴더> --dry-run` 으로 올라갈 변경과 차이, 보내면 바로 반영되는지 제안이 되는지(2번)를 보여 주고, 맞다고 하면 올린다. 바로 반영되는데 사용자가 검토를 원하면 `--review` 를 붙인다.

```bash
guideline propose --from <원본 폴더> --title "rules: <주제> 를 <스택> 스택 지침으로 올림" --message "<본문>"
```

   본문에는 출처(`<프로젝트>` `<파일>` 「<절 제목>」)와 범용화하며 바꾼 것을 한 줄씩 적는다. 서브에이전트·MCP 를 올렸으면 제목을 `agents: <이름> 추가`, `mcp: <이름> 추가` 로 쓰고 본문에 필요한 환경 변수 이름을 적는다(값은 적지 않는다). 제안이 됐으면 제안 번호와 주소를 알린다. 관리자가 웹 「제안」 에서 검토해 수락하면 원본이 된다. 바로 반영됐으면(「반영 완료: r<번호>」) 리비전 번호를 알린다. 어느 쪽이든 각 프로젝트는 `guideline update` 로 받는다.

## 지킬 것

- 후보를 **넉넉하게 잡지 않는다.** 사용처 수로 거르지 않는다 — 스택은 새 프로젝트에 적용할 공통 지침이기도 하다. 그 스택을 쓰는 어느 프로젝트에서나 참이라고 확신할 수 없는 절(특정 프로젝트의 선택·환경에 기대는 절)만 프로젝트 고유로 둔다.
- 절을 요약하지 말고 **절 제목을 그대로** 표에 적는다.
- 사용자가 고르지 않은 절을 함께 올리지 않는다.
- **이 프로젝트의 파일을 고치지 않는다.** 올린 절을 이 프로젝트에서 지울지는 다음에 `guideline-sync` 를 돌려 중복으로 잡힐 때 사용자와 정한다.
- 원본 폴더의 파일을 다른 길로 서버에 쓰지 않는다. 늘 `guideline propose --from` 으로 올린다.
- **비밀값을 옮기지 않는다.** 프로젝트 설정에 박힌 토큰·비밀번호·키는 `${변수}` 참조로 바꿔 올린다. 그 값을 원본 폴더 파일, 대화 출력, 보고 표, 제안 본문 어디에도 옮기지 않는다. 표에는 "`env.DB_PASSWORD` 에 값이 박혀 있음" 처럼 위치만 적는다.
- MCP `README.md` 의 발급 방법을 지어내지 않는다. 모르면 사용자에게 묻는다.
- `args`·`url` 에 토큰이 박힌 MCP 는 참조로 바꿀 수 없다(`list` 도 잡지 못한다). 그 서버가 같은 값을 환경 변수로 받는지 서버 문서에서 확인해 `env` 로 옮긴다. 옮길 수 없으면 올리지 않고 프로젝트 고유로 두고 사용자에게 알린다.
